     5→     5→## Project Overview
     6→     6→
     7→     7→Kottaby is a Next.js 16 (App Router) full-stack application using:
     8→     8→- **Runtime**: Bun (not Node.js)
     9→     9→- **Frontend**: React 19, MUI v9, Apollo Client v4, Zustand
    10→    10→- **Backend**: Pothos GraphQL, Drizzle ORM, PostgreSQL
    11→    11→- **Testing**: Bun test runner, Vitest for Storybook, Playwright for E2E
    12→    12→- **i18n**: **Custom compile-time TypeScript system** in `shared/locale/` (replaces legacy `next-intl`; see `shared/AGENTS.md` for rules). Next.js native `[locale]` routing preserved.

    14→    14→## Essential Commands
    15→    15→
    16→    16→All commands use Bun. The specific binary path `~/.bun/bin/bun` is required in some environments.
    17→    17→
    18→    18→```bash
    19→    19→# Development
    20→    20→bun run dev                    # Start dev server with Turbopack on port 3000
    21→    21→bun run dev:safe               # Safe dev mode via scripts/safe-dev.ts
    22→    22→bun run debug                  # Same as dev (alias for debugging workflows)
    23→    23→bun run dev:inspect            # Start dev server with Node inspector enabled (--inspect)
    24→    24→
    25→    25→# Build & Type Check
    26→    26→bun run build                  # Next.js production build
    27→    27→bun run tsgo                   # Fast TypeScript checking (tsgo, not tsc)
    28→    28→
    29→    29→# Linting & Formatting (in-process serialized lint service)
    30→    30→bun run lint                   # Full-repo ESLint; in-process serialized lint service — safe for parallel sub-agents
    31→    31→bun run lint:fix               # Full-repo ESLint with auto-fix
    32→    32→bun lint:type-aware            # Type-aware ESLint (sonarjs rules requiring type context); use --fix to auto-fix
    33→    33→bun run format                 # Biome formatter
    34→    34→bun run biome:check            # Biome lint + format + unsafe fixes
    35→    35→
    36→    36→# GraphQL Code Generation (REQUIRED after schema/document changes)
    37→    37→bun run generate:gqlSchema     # Generate GraphQL schema from Pothos
    38→    38→bun codegen                    # Generate TypeScript types from schema
    39→    39→
    40→    40→# Testing (layer-specific)
    41→    41→bun run build:test             # Build production bundle for UI/E2E tests (.next-test-prod) — REQUIRED before test:ui:e2e
    42→    42→bun run test                   # All tests
    43→    43→bun run test:db                # Database repository tests (parallel via test/scripts/run-db-tests-parallel.ts)
    44→    44→bun run test:db:sequential     # Database tests (sequential, for debugging)
    45→    45→bun run test:integration       # Provider integration smokes (parallel via test/scripts/run-integration-tests-parallel.ts)
    46→    46→bun run test:integration:sequential  # Integration tests (sequential, for debugging)
    47→    47→bun run test:live-comm         # Communication provider integration subset
    48→    48→bun run test:live-fx           # FX provider integration subset
    49→    49→bun run test:services          # Backend services tests (parallel via test/scripts/run-services-tests-parallel.ts)
    50→    50→bun run test:services:sequential # Backend services tests (sequential, for debugging)
    51→    51→bun run test:graphql           # GraphQL integration tests (dev server via test/scripts/run-server-tests.ts)
    52→    52→bun run test:ui:components     # UI component tests (Happy DOM, no server)
    53→    53→bun run test:ui:e2e            # End-to-end tests (dev/production server — test/scripts/run-server-tests.ts --e2e)
    54→    54→bun run test:ui                # All UI tests (components + e2e + static)
    55→    55→bun run test:ui:kill           # Kill test servers on port 3099 only (never dev:3000 or start:4000)
    56→    56→
    57→    57→# Run database tests with log capture (AI agents MUST use this instead of raw `bun test`)
    58→    58→bun run test/scripts/run-test.ts <test-path>        # Run with log capture
    59→    59→bun run test/scripts/run-test.ts --last <path>      # View last result (AI-optimized)
    60→    60→bun run test/scripts/run-test.ts --last --focus "<pattern>" <path>  # Filtered view
    61→    61→
    62→    62→# Quality Gates
    63→    63→bun quality-gate               # Automated quality verification (tsgo → oxlint → biome → lint → duplicates)
    64→    64→bun quality-gate:fresh         # Reset state and run fresh
    65→    65→
    66→    66→# Database
    67→    67→bun run db                      # Database actions via scripts/dbActions/ (generate, push, migrate, seed, studio — reset & cleanGenerate disabled by repo policy)
    68→    68→```

    99→    99→## Non-Obvious Patterns & Gotchas
   100→   100→
   101→   101→### Next.js 16 Breaking Changes
   102→   102→This is NOT standard Next.js. APIs and conventions differ from training data. **Always read `node_modules/next/dist/docs/` before writing Next.js code.**
   103→   103→
   104→   104→### Logging
   105→   105→- **NEVER use `console.*` directly** - ESLint will error
   106→   106→- Always use: `import { logger } from '@/frontend/utils/logger'` (frontend) or `@/backend/lib/logger` (backend)
   107→   107→- Methods: `logger.info`, `logger.warn`, `logger.error`, `logger.debug`, `logger.logDomainError`
   108→   108→- **Domain / Expected Rejections**: Use `logger.logDomainError(msg, ctx)` when handling business rejections, 4xx equivalents, `NotFoundError`, or `ValidationError`. It automatically logs as `debug` in test mode (`TEST_SERVER=1`) to keep test logs compact and as `warn` in production.
   109→   109→
   110→   110→### MUI v9 Breaking Changes
   111→   111→- Style props (`fontWeight`, `textAlign`, `mb`, `mt`, `p`, `display`, etc.) are NOT valid direct props on Typography, Stack, Box, Grid
   112→   112→- Always use `sx` prop: `<Typography sx={{ fontWeight: 700, mb: 1 }}>`
   113→   113→- Icon naming changed: `*Outline` → `*Outlined` (e.g., `ErrorOutline` → `ErrorOutlined`)
   114→   114→- See `frontend/AGENTS.md` for complete list
   115→   115→
   116→   116→### React 19 Changes
   117→   117→- `FormEvent` is deprecated/removed. Use `React.SubmitEvent` or `React.SyntheticEvent<HTMLFormElement>`
   118→   118→- Cast FormData results: `(formData.get("name") as string | null) ?? ""`
   119→   119→
   120→   120→### Path Aliases
   121→   121→- The `@/*` path alias maps to the project root (`./`), configured in `tsconfig.json` under `compilerOptions.paths`
   122→   122→- All imports use this pattern: `import { logger } from "@/backend/lib"` (never relative paths)
   123→   123→- Examples: `@/backend/services/` → `./backend/services/`, `@/frontend/views/` → `./frontend/views/`
   124→   124→
   125→   125→### Barrel Files (`index.ts`) Conventions
   126→   126→- **Shortest import path**: Always import from the highest available barrel (e.g. `@/backend/services`, not `@/backend/services/communication/channels/whatsapp/cloud-api`). If a barrel doesn't exist at the needed level, create one.
   127→   127→- **Nested barrels**: Every nested subdirectory that has exportable modules MUST have its own `index.ts`. Parent barrels re-export from nested barrels (`export * from "./subdir"`), never from nested files directly (`export * from "./subdir/file"` is prohibited).
   128→   128→- **Prefer `export *`**: Use `export * from "./module"` exclusively. Avoid named re-exports (`export { A, B } from "./module"`) unless two source files export the same symbol name (collision) — in that case, rename the function in the source file so `export *` works, rather than aliasing in the barrel.
   129→   129→- **`./` not `@/` in barrels**: `index.ts` files MUST use relative `./` paths, not `@/` path aliases. Example: `export * from "./requests"`, not `export * from "@/backend/services/.../requests"`.
   130→   130→- **No `../` in barrels**: `index.ts` files MUST NOT use `../` or `./../` — only `./` paths to files/subdirs in the same directory or one level down.
   131→   131→- **Max one `/` per path**: Each `export * from` path in an `index.ts` MUST NOT contain more than one `/`. Example: `export * from "./requests"` (one `/`) is allowed; `export * from "./requests/get-phone-number.request"` (two `/`) is prohibited — use `export * from "./requests"` and let the `requests/index.ts` barrel handle the rest.
   132→   132→- **No imports in barrels**: `index.ts` files contain ONLY `export *` (or collision-disambiguation `export { }`) statements — never `import` statements. The only exception is GraphQL mutation/query layers where imports register types in the GraphQL schema (not re-exported).
   133→   133→- **Unique export names**: When multiple files in the same directory export functions with the same generic name (e.g. `buildRequest`, `parseResponse`), rename them to unique descriptive names in the source files (e.g. `buildGetPhoneNumberRequest`, `parseGetPhoneNumberResponse`) so the barrel can use `export *` without aliasing.
   134→   134→- **Collision registry**: When `export *` causes a naming collision (TS2308 or ESLint `import-x/export`), keep `export { }` for the colliding symbol and document the exception in `ai/plans/reexport-elimination/outcome/collisions-registry.md`. See `docs/architecture/import-export-conventions.md` for full rules.
   135→   135→- **`export type { }` stays**: `export type { X } from "./file"` is NOT converted to `export *` — type-only re-exports are intentional and keep type semantics explicit.
   136→   136→- **No re-export shims**: Files that only re-export from another directory (`export { X } from "@/other/dir/file"`) are prohibited. Consumers must import directly from the original source. Delete shim files and update consumers.
   137→   137→
   138→   138→### Shared Layer
   139→   139→- `shared/` is used by both frontend and backend — it must **never** import from `@/frontend/**`, `@/backend/**`, or `@/app/**` (ESLint enforced).
   140→   140→- Cross-layer enums and constants belong in `shared/constants/`; utilities in `shared/lib/`. See `shared/AGENTS.md`.
   141→   141→
   142→   142→### Database Testing Critical Rules
   143→   143→- **ALWAYS use `runInRollback` wrapper** for database tests
   144→   144→- **ALWAYS pass `tx` to ALL repository methods** inside transactions - mixing `tx` queries with `db`-backed repo calls causes deadlocks
   145→   145→- **NEVER use `expect(...).rejects.toThrow()` inside `runInRollback`** - causes deadlocks. Use try/catch helper pattern instead
   146→   146→- **NEVER query seed data** - always create test data using helpers in `entity-setup.ts`
   147→   147→- Verify entity-setup helper signatures before use - they vary significantly
   148→   148→
   149→   149→### GraphQL Document Conventions
   150→   150→- Documents live in `frontend/graphql/sharedDocuments/<domain>.documents.ts`
   151→   151→- Naming: `{entityName}QueryDocument`, `{entityName}MutationDocument`
   152→   152→- **Always include `id` field** on every object type for Apollo cache normalization
   153→   153→- **NO `useLazyQuery`** - use stateful `useQuery` exclusively
   154→   154→- Import hooks from `"@apollo/client/react"`, not `"@apollo/client"`
   155→   155→
   156→   156→### Type Definition Pattern (CRITICAL)
   157→   157→All layers use types from `backend/types/{entity}.types.ts`:
   158→   158→- `{Entity}SelectType`, `{Entity}InsertType` - database types
   159→   159→- `{Entity}ReturnType`, `{Entity}SubmitInput` - service/API types
   160→   160→- `DBTransaction`, `DBQueryExecutor` - database transaction/executor types (now in `@/backend/types`, moved from `@/backend/db/db.types`)
   161→   161→- **Never create local type definitions in Pothos files** - always import from `@/backend/types`
   162→   162→- **Service-layer `.types.ts` files are prohibited** - all types live in `backend/types/`; split runtime code into `.helpers.ts`/`.constants.ts`
   163→   163→- Single canonical GraphQL object type per entity
   164→   164→
   165→   165→### i18n / Localized Errors
   166→   166→- All user-facing error messages must use the **compile-time translation system** in `shared/locale/`
   167→   167→- **Server Components**: use `getTranslations(locale, "namespace")` from `@/shared/locale/server`
   168→   168→- **Client Components**: use `useAppTranslation("namespace")` from `@/shared/locale/client`
   169→   169→- **GraphQL Resolvers**: use `ctx.t("namespace")` — already bound to `ctx.locale`
   170→   170→- **API Routes / Scripts / Tests**: use `getServerTranslations(locale, "namespace")` from `@/shared/locale/server-graphql`
   171→   171→- **Pluralization**: define as `(count: number) => string` in type schema, implement in each locale file
   172→   172→- **Interpolation**: define as `(param: string, ...) => string` in type schema, implement with template literals
   173→   173→- **Never hardcode error strings** — always use typed translation functions
   174→   174→- The legacy `next-intl` package has been removed; all translation namespaces now live in `shared/locale/`. Never import `next-intl`, `getBackendTranslations`, or from `shared/messages/` (the directory no longer exists).
   175→   175→
   176→   176→### Theme & Styling
   177→   177→- **NO hardcoded colors** - all colors from theme palette
   178→   178→- Use theme callback: `sx={(theme) => ({ color: theme.palette.primary.main })}`
   179→   179→- Use Material 3 `on<Color>` siblings for contrast (e.g., `theme.palette.onPrimary`)
   180→   180→- See `frontend/THEME_PALETTE.md` for tokens

   182→   182→## Code Quality Workflow
   183→   183→
   184→   184→After making changes:
   185→   185→1. Run `bun quality-gate` - it handles tsgo, oxlint, biome, lint, duplicates sequentially
   186→   186→2. If DUPLICATES fails: run `bun run check:duplicates` to see cross-file clones. Fix by extracting shared scaffolds/utilities (see `docs/frontend/duplication-elimination-patterns.md`). NEVER add `jscpd:ignore` comments or modify `.jscpd.json`.
   187→   187→3. Re-run `bun quality-gate` to resume from last failed stage
   188→   188→4. Use `bun quality-gate:fresh` only for clean-slate verification
   189→   189→
   190→   190→**⚠️ NEVER CLEAR CACHES.** Neither `quality-gate` nor `quality-loop` may ever clear cache files.
   191→   191→This includes:
   192→   192→- ESLint cache (`.eslintcache`, `.eslintcache-type-aware`) — always preserved by `lint-service.ts`
   193→   193→The `quality-gate:fresh` / `--fresh` flag only clears the quality-gate **state file**
   194→   194→(`.quality-gate-state.json`), which tracks stage progress — it does NOT touch any cache.
   195→   195→Never manually delete cache files either.

   197→   197→## Lint Service (In-Process Serialized ESLint)
   198→   198→
   199→   199→The project uses a unified lint service (`scripts/lint-service.ts`) that provides both a CLI and programmatic API. It runs ESLint with serialized execution to prevent CPU/memory contention when multiple callers (e.g., sub-agents, quality-gate stages) lint concurrently within the same process. No HTTP server, no port binding — everything is in-process TypeScript.
   200→   200→
   201→   201→### Running lint from the command line
   202→   202→
   203→   203→**Full-repo lint** (via `eslint.config.js` `files`/`ignores` block):
   204→   204→```bash
   205→   205→bun run lint
   206→   206→```
   207→   207→
   208→   208→**File-scoped lint** (faster when you only touched specific files):
   209→   209→```bash
   210→   210→bun run scripts/lint-service.ts -f <file1> -f <file2> --id <caller-id>
   211→   211→```
   212→   212→
   213→   213→**Auto-fix mode**:
   214→   214→```bash
   215→   215→bun run lint:fix
   216→   216→```
   217→   217→
   218→   218→**JSON output** (for scripting/automation):
   219→   219→```bash
   220→   220→bun run scripts/lint-service.ts -f <file> --json --id <caller-id>
   221→   221→# Returns: { success: boolean, output: string, exitCode: number, metrics: {...} }
   222→   222→```
   223→   223→
   224→   224→The CLI exits with ESLint's exit code (0 = clean, 1 = lint errors, 2 = config/usage errors), so CI pipelines and quality gates detect failures correctly.
   225→   225→
   226→   226→### Programmatic API (from TypeScript)
   227→   227→
   228→   228→Import and call directly from scripts or tests:
   229→   229→
   230→   230→```typescript
   231→   231→import { requestLint, requestFullRepoLint } from "@/scripts/lint-service";
   232→   232→
   233→   233→// Lint specific files
   234→   234→const result = await requestLint("sub-loop", ["backend/types/foo.types.ts"]);
   235→   235→// Returns: { success: boolean, output: string, exitCode: number }
   236→   236→
   237→   237→// Full-repo lint (empty files array)
   238→   238→const fullResult = await requestFullRepoLint("cli");
   239→   239→```
   240→   240→
   241→   241→**When to use programmatic vs CLI:**
   242→   242→- Use the programmatic API when your script already runs in a Bun/Node process and can import TypeScript (e.g., `sub-loop.ts`, orchestrator scripts).
   243→   243→- Use the CLI when invoking from shell commands or external tools (e.g., GitHub Actions, pre-commit hooks, extensions).

   245→   245→### Environment Variables
   246→   246→
   247→   247→- `LINT_QUEUE_CONCURRENCY` — ESLint `--concurrency` value (default `4`; set to `auto` to let ESLint decide).
   248→   248→- `LINT_QUEUE_TIMEOUT_MS` — Per-request timeout in milliseconds (default: 300000 for file-scoped, 1200000 for full-repo).
   249→   249→
   250→   250→### Other quality commands are safe to run in parallel
   251→   251→
   252→   252→- `bun tsgo` — Safe to run concurrently (read-only type checker)
   253→   253→- `bun biome:check` — Safe to run concurrently (lightweight formatter/linter)
   254→   254→- `bun run test:*` — Safe to run concurrently (isolated test runners)
   255→   255→- `bun run lint` — Safe to run directly; uses the in-process service (no server startup required). When multiple callers import `requestLint()` in the same process, requests serialize through an in-memory FIFO queue.
   256→   256→- `bun run check:duplicates` — Uses process lock with dedicated `duplicates` namespace; serialized via `run-locked-cmd.ts`. Exempt from 5-minute timeout (full-repo scan of 3,000+ files). Sub-loop's per-file jscpd calls `bunx jscpd` directly (no lock needed for intra-file scans).

   258→   258→## Verification Loop (Per-File Level)
   259→   259→
   260→   260→When refactoring or creating code, run a per-file verification loop **BEFORE** using the result elsewhere:
   261→   261→
   262→   262→1. **After extracting a function** from one file to another: run tsgo + oxlint + biome + lint on the **new file containing the extracted function** BEFORE importing or using it elsewhere.
   263→   263→2. **After creating a new file**: run tsgo + oxlint + biome + lint on the new file BEFORE importing it anywhere.
   264→   264→
   265→   265→```bash
   266→   266→bun tsgo                          # Type check (safe to run concurrently)
   267→   267→bun oxlint                         # Oxlint (fast linter, fails on warnings)
   268→   268→bun biome:check                   # Biome (safe to run concurrently)
   269→   269→# Lint the specific file:
   270→   270→bun run scripts/lint-service.ts -f <the-file> --id verify
   271→   271→```
   272→   272→
   273→   273→This catches issues early at the file level before they propagate to the full quality gate.

   288→   288→## Parallel Subagent Quality Gate Workflow
   289→   289→
   290→   290→When running `bun quality-gate`, the orchestrator dispatches **parallel subagents** to fix files
   291→   291→within each lifecycle stage. Key rules:
   292→   292→
   293→   293→### Lifecycle Isolation (No Cross-Stage Interleaving)
   294→   294→
   295→   295→- Subagents are dispatched **per lifecycle stage only** — no mixing stages in the same wave
   296→   296→- Each stage must fully complete before advancing to the next
   297→   297→- Stage order: `tsgo` → `oxlint` → `biome:check` → `lint` → `duplicates`
   298→   298→
   299→   299→### Subagent Dispatch Model
   300→   300→
   301→   301→- **One subagent per file** — maximum parallelism
   302→   302→- **tsgo uses grouped parallel**: bundle related files (same import chain, same directory, same type
   303→   303→  dependency) into batches. Fix a batch in parallel, verify, then move to the next batch
   304→   304→- **oxlint/biome/lint/duplicates**: full parallel — all files at once
   305→   305→
   306→   306→### Per-File Verification via `scripts/health/sub-loop.ts`
   307→   307→
   308→   308→Each subagent calls the automation script to verify its file:
   309→   309→
   310→   310→```bash
   311→   311→bun run scripts/health/sub-loop.ts <file-path> --lifecycle <stage>
   312→   312→```
   313→   313→
   314→   314→The script runs a **progressive loop** (tsgo → oxlint → biome → lint → duplicates) and
   315→   315→**short-circuits at the first failing check**. The subagent fixes the errors and re-runs until
   316→   316→the script exits 0. The `--lifecycle` arg controls the target stage:
   317→   317→
   318→   318→| `--lifecycle` | Checks run (in order) |
   319→   319→|---------------|----------------------|
   320→   320→| `tsgo` | tsgo only |
   321→   321→| `biome` | tsgo → oxlint → biome |
   322→   322→| `lint` | tsgo → oxlint → biome → lint (via queue client) |
   323→   323→| `duplicates` | tsgo → oxlint → biome → lint → check:duplicates |
   324→   324→
   325→   325→**Progressive enforcement**: no skipping ahead. If tsgo fails, only fix tsgo — don't run
   326→   326→oxlint/biome/lint/duplicates until tsgo passes.
   327→   327→
   328→   328→### Instruction File & AGENTS.md Discovery (Per-File)
   329→   329→
   330→   330→The `scripts/health/sub-loop.ts` script automatically discovers and prints which instruction
   331→   331→files and AGENTS.md files apply to the target file. Subagents MUST read ALL listed files before
   332→   332→fixing. The mapping is:
   333→   333→
   334→   334→**Instruction files** (`.github/instructions/*.instructions.md`):
   335→   335→

   363→   363→### Fix-Or-Report Rule for Cross-File Violations
   364→   364→
   365→   365→After reading the applicable instruction files and AGENTS.md, subagents check for rule violations:
   366→   366→- **Fix within the SAME file**: if the violation can be fixed in the assigned file, fix it directly.
   367→   367→- **Report cross-file dependencies**: if fixing requires modifying ANOTHER file, do NOT modify it.
   368→   368→  Report to the orchestrator using:
   369→   369→  ```
   370→   370→  CROSS-FILE DEPENDENCY:
   371→   371→    Target file: <this file>
   372→   372→    Blocked by: <other file that needs changes>
   373→   373→    Rule violated: <which rule from instruction file or AGENTS.md>
   374→   374→    Required fix: <description of what the other file needs>
   375→   375→  ```
   376→   376→- **Never modify a file you were not assigned to.** The orchestrator coordinates multi-file changes
   377→   377→  by dispatching a follow-up subagent wave for the dependency files.
