## 5. Root Cause of the Pre-Existing Failures (cross-file, REPORTED not fixed)

Both failure families share one mechanism: **the PGlite pool shim hands every "connection" the SAME single-connection WASM Postgres session** (`backend/db/pglite-pool.ts:12-16, 277-289` — `connect()` returns a stateless forwarding client; "PGlite is single-connection"). Drizzle compounds this: `NodePgSession.transaction` only acquires a dedicated pool client when the client is a real `Pool` (`node_modules/drizzle-orm/node-postgres/session.js:50-52` — `isPool` check); the shim's plain object is not, so **every `db.transaction()` runs BEGIN/COMMIT on the one shared session**.

1. **Steps 1/3/4 — intermittent `25001` on `begin isolation level repeatable read`:** the admin list reads NEST a second top-level transaction inside the first — `listPendingWithdrawalsForAdmin`/`listStudentPaymentsForAdmin` call `withTransaction(outerTx, …)` (top-level tx) and then `readInSnapshot(outerTx, …)` (`backend/services/billing/admin-financial-auditing.service.read.helpers.ts:66-74, 147-168, 262-284`), which — when `outerTx` is undefined, as in every journey call — opens ANOTHER `db.transaction(fn, { isolationLevel: "repeatable read" })` while the outer one is still active. On a real pool these are two different server sessions (safe); on the shim both BEGINs hit the same session → `25001` when the inner composite BEGIN lands after the outer transaction has already executed a query. Pure timing → intermittent.
2. **Step 6 (and sibling steps A/B/D) — true-concurrency races corrupt on one session:** `Promise.allSettled([approveWithdrawal, approveWithdrawal])` runs two concurrent top-level transactions (guarded settle + audit insert) through the single session; statement-level interleaving yields outcomes impossible under a real pool (observed deterministically: 1 audit row + status still `pending`; the loser's ROLLBACK can undo the winner's uncommitted writes on the shared session). Step 7's race (approve ∥ fresh request) happens to tolerate the interleaving and passes; the sibling's races (double-spend, drain) corrupt the same way.

**Why not fixed here:** (a) the failing step bodies are byte-frozen by the 1.1.SR acceptance criterion (steps 1–7 byte-identical); (b) the mechanism lives in production code (`backend/db/pglite-pool.ts`, `backend/services/billing/admin-financial-auditing.service.read.helpers.ts`, drizzle's `isPool` detection) and this plan is verification-scoped — "zero new production code except one journey-test leg" (tasks.md header); (c) the sub-loop Fix-Or-Report rule forbids crossing the file boundary. **Fix-or-report resolution: reported.**

**Carry-forward options for the orchestrator (owner decision, NOT executed in this plan):**
- Run the Phase 3.3 journey re-runs (and any future full-journey gate) against `DB_PROVIDER=postgres` (a real TCP pool), where the nested-snapshot and race semantics execute exactly as designed — the service code is correct; only the sandbox provider cannot honor it.
- Or scope a follow-up plan item: make `readInSnapshot` join the outer transaction's session (or make the shim acquire per-transaction sessions) and re-validate the race journeys.
- Environmental note: the failures reproduce on the current PGlite data dir across many runs; a fresh `./db/pglite` (re-migrate + re-seed) does NOT remove the structural hazard (nested same-session BEGIN), so a DB reset is not a fix, only timing noise reduction.
