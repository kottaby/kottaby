## 4. 3.2.SEC — Security & Tenancy Audit

- **Governance gate:** `assertActorAdminActive(actorUserId, locale, tx)` arms at `admin-financial-auditing.service.ts:194` (approve — first statement inside the transaction, BEFORE the probe read and settle) and `:281` (reject — after the pre-DB reason normalization at `:278`, before any ledger/wallet write). A suspended admin is denied FORBIDDEN with zero audit rows (SVC `:298-317`); the fail-closed behavior matches `backend/services/AGENTS.md` permission-ordering (authorization before any data work).
- **Audit-row-fate invariants:** both audit writes (`:233-243` approve, `:319-330` reject) execute inside the SAME `withTransaction` block as the settle → single commit/rollback fate. Proven both directions: exactly-one on success (`:344`, `:406`, `:935`), zero on every denial (`:243, :292, :316, :370, :820, :839, :872, :892`), zero residue on mid-flight failure (`:846-874`) and on a not-found reject (`:876-894`).
- **Reason leakage:** raw reason text NEVER persisted — only `reasonPresent: true` (`:327`; test `:419-420` + unicode fuzz test assert the details JSON contains no raw text).
- **Identity:** actor id arrives as a service parameter from the authenticated caller chain (ctx-derived at the GraphQL layer); no client-supplied actor identity exists on this surface. No tenancy filters involved (single-tenant financial tables; wallet/ledger access is id-scoped through the guarded predicates). Wire-level BFLA re-proof stays with task 3.3 (REQ-502 full tier).
- **Immutability as tamper defense:** DB triggers reject UPDATE/DELETE/type-relabel on ledger rows even from raw SQL inside a transaction (IMM `:364-478`; ADM `:573-654`), and the repo exposes no update/delete primitive (`wallet.repository.test.ts:419-443`) — the compensating-row doctrine (`:457`) is the sanctioned correction path.
