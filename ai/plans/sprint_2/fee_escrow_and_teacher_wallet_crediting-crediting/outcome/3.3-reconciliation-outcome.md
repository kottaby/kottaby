## Ruling 1 — Hold-AS-Debit: the ticket's "held, not decremented" wording is superseded

**Superseded ticket wording.** Fee Escrow says "the student's balance is held (not decremented yet)" at request (`docs/planning/TICKETS.md:1722`) and "the student's balance is decremented by 1" at dual confirmation (:1726), with cancellation releasing "no decrement" (:1733).

**Binding ruling.** "Hold" = a **guarded debit of one unit lane at request time** (trial lane first, then the intent lane), with provenance recorded in `held_balance_lane`. Dual confirmation does NOT debit anything — it flips `fee_held = false` and credits the teacher's wallet. Cancellation/timeout/arbitration-cancel re-increments the SAME lane that funded the hold.

Segregated Session Balance plan, decision D1 "Ratify hold-as-debit timing (REQ-024)": `ai/finished_plans/sprint_1/segregated_session_balance-crediting/plan.md:54-56` — refactoring to debit-at-confirmation "reintroduces the double-booking race the escrow killed"; shipped timing ratified. **Path relocation note:** this plan's own artifacts cite `ai/plans/sprint_1/segregated_session_balance-crediting/`; the plan has since finished and moved to `ai/finished_plans/sprint_1/…` (the plan-review-R1 lesson — resolve cross-plan paths with `ls`).

## Ruling 2 — Unit lanes (student side) vs EGP decimal-string fee (teacher side): a two-sided model that reconciles at settlement

**Ticket implication.** Both tickets describe "balance" as one money pool decremented/credited symmetrically (Fee Escrow :1726/:1733; Wallet Crediting :1774-1775).

**Shipped model.** The two sides use different units BY DESIGN:
- **Student side — integer unit lanes:** `balance_trial`/`balance_hifz`/`balance_tajweed` move by ±1 via `decrementLaneIfAvailable`/`incrementLane` (`student.repository.ts:404-419,433-441`). No currency ever touches these columns.
- **Teacher side — EGP decimal strings:** the wallet (`balance`/`total_earning`, `backend/db/schema/billing/wallet.ts:36-38`) and the ledger row carry the platform fee `"25.00"` verbatim — `creditEarningOnce` inserts `amount` never re-parsed or re-rounded (`wallet.repository.ts:78-110`, amount at :94, verbatim rule in the :70-74 docblock) and increments by SQL addition (:103-110). `session.fee` is `decimal(10,2)` (`session.ts:63`); constants `shared/constants/session-fees.constants.ts:27-33` (`SESSION_FEE_HIFZ`/`SESSION_FEE_TAJWEED` = `"25.00"`, `SESSION_FEE_CURRENCY = "EGP"`).
- **The reconciliation is the settlement event:** exactly ONE held session ⇒ exactly ONE `earning` row of `amount = session.fee` with `wallet_id`/`session_id` linked (`confirmation.ts:48-59,129`; `wallet.repository.ts:91-96`). One consumed unit lane on the student side maps to one fee-string credit on the teacher side; the two sides are never arithmetically compared at any other point, and release paths touch only lanes (journey `session-dual-confirmation…:561` and sweep-won :686-688: zero ledger rows, wallet static, lane +1).

**Boundary hand-off:** the end-to-end money audit (does every earning trace to a consumed hold, and every refund to a released hold?) is owned by the Sprint 4 Financial Safety Verification ticket (`docs/planning/TICKETS.md:2985-3026`) — this plan's REQ-7 evidence is its entry criterion (specs.md REQ-8).

**Test proof:** fee is a decimal STRING verbatim (svc:1109); credit exactness (journey :451 — `walletTotal` delta `= Number(SESSION_FEE_HIFZ)` :476, ONE ledger row :479, `amount` string-equal :480, `TransactionType.Earning` :481); ledger immutability (triggers `backend/db/migration/3-immutability-triggers.sql:87-113`).

## Ruling 3 — Dispute-from-`completed` divergence (dual-confirmation plan D-2 stands)

**Ticket implication.** Fee Escrow's decision refs include B.18 (disputed status) with prose implying a dispute can follow a confirmation.

**Shipped machine.** `disputed` is reachable only from `scheduled` or `started` — never from `completed`: state machine docblock `backend/db/schema/classes/session.ts:15-20` (`scheduled → started → completed | cancelled`, both live states may pass through `disputed`, every admin resolution exits to one terminal state); enum `backend/db/schema/enums.ts:23`. The open-dispute guarded UPDATE matches only live participant rows — terminal and already-disputed rows are "structurally unreachable" (`openDisputeOnce`, `session.repository.ts:248-262`, predicate via `buildLiveParticipantTransitionPredicate` :259). The escrow hold stays frozen through the dispute (`openDisputeOnce` docblock :243-244) until arbitration releases (CANCEL) or consumes it (COMPLETE — no wallet credit; the settlement window is over): `resolveDisputeCancelOnce` `session.repository.ts:280-290`, arbitration-COMPLETE classification `session-lifecycle.service.ts:633-640` (never-started disputes VALIDATION-denied pre-write), hold-consumption test svc:1793, refund arms svc:1726/:1766. Arbitration is ADMIN-only at the GraphQL gate (`session-lifecycle.mutation.ts:270-275`) with service-side governance re-check (`session-lifecycle.service.ts:622-624`).

**Ruling source:** dual-confirmation plan decision D-2 — "Dispute predicate NOT widened to `completed`": `ai/finished_plans/sprint_2/dual-confirmation-completion-handshake/plan.md:23` (widening would create a second arbitration path with a different escrow state; disputes stay pre-completion). **No code change** by this plan; any redesign belongs to the Sprint 3 Dispute Resolution plan (`ai/plans/sprint_3/dispute-resolution-with-admin-arbitration/`, plan.md D4 reference).

## Ruling 4 — Escrow idempotency-key contract: type-level pin only; deferral D1 (exactly-once rests on the guard predicate)

**Facts.** `EscrowTriggerContract` / `WalletCreditContract` / `EscrowReleaseContract` each declare an `idempotencyKey` (`backend/types/contracts/session-completion-escrow.contract.types.ts:34-38,46-55,63-80`), but the runtime credit path (`confirmation.ts:48-59,129`) consumes none of them — the exactly-once guarantee rests entirely on the `fee_held = true` statement predicate (`session.repository.ts:448`), which is race-proven both directions (repo:1582 confirm-then-sweep, :1617 sweep-then-confirm; journey `session-dual-confirmation…:620` exactly-ONE-financial-outcome partition).

**Why deferral is safe today (behavioral substitutes already pinned):**
- Request-level idempotency: the `session_request_idempotency` claim rides the HTTP header into `ctx.idempotencyKey` (`session-lifecycle.mutation.ts:135-139`, propagation-only); replay-by-throw `DUPLICATE_REQUEST` with zero rows (`booking.ts:205-238`); key released on failure and reusable after funding (journey `session-lifecycle-denials…:236`); missing key → pre-DB `VALIDATION` (wire :395-402).
- Settlement-level idempotency: replay arms return the current row with zero financial writes (`confirmation.ts:86-104`; svc:2441/:2471; journey :492; teacher confirm is a no-op that cannot self-credit — T2 §4).

**Disposition.** Deferred as ledger row D1 (`deferred-items.md`, status ❌ Blocked, exempt from this plan's in-plan gate — target is external): **Financial Safety Verification ticket** (`docs/planning/TICKETS.md:2985-3026`). Adopting a runtime key now would touch the race-proven money path for no behavioral gain — the textbook change-for-change's-sake this verification plan exists to prevent (plan.md D3). The contract types remain as type-level pins of the intended future wire shape.
