```typescript
NotificationRepository.markReadOnce(id: number, userId: number, tx?: DBTransaction): Promise<NotificationSelectType | null>

NotificationRepository.markAllReadForUser(userId: number, type: NotificationType | null, tx?: DBTransaction): Promise<number>
// single set-based UPDATE … WHERE user_id AND is_read = false [AND type = ?];
// returns the AFFECTED count (rows actually flipped); 0 on empty set (CA-8/J2 step 6);
// repeat sweeps report 0 (is_read=false guard).
```

**Engine consumption notes (2.6/2.7):**
- The `filters` param is the **structural** `Pick<NotificationListFilterInput, "type" | "isRead">` — passing a whole `NotificationListFilterInput` **variable** compiles (structural subtyping; excess `limit`/`offset` props are fine for non-literal values); a fresh object **literal** must carry only `type`/`isRead`. `null` and `undefined` are both "no filter".
- `listForUser` returns FULL `$inferSelect` rows (no projection/stripping) — J1 step 9's field-for-field `toEqual` against a raw DB listing holds by construction (pinned green in the repo test's oracle-equality case).
- Reads have a genuine non-tx branch (raw SQL via `queryDb` — Neon HTTP eligible): the engine's inbox methods (plan §4.1 signatures take no `tx`) get it automatically; emit paths that pass `tx` run on the caller's transaction and see uncommitted rows.
- Writes fall back to the global `db` handle only when `tx === undefined` — the engine's own-commit path composes its transaction (DEV1-002 `withTransaction` pattern) and passes `tx` through.
- `markAllReadForUser`'s count comes from the awaited update's `rowCount` (no `.returning()` materialization).

## 6. SEC — Security & Tenancy Audit (2.4.SEC)

## 9. Deviations

- **D-1 — read params typed `tx?: DBTransaction`, not the siblings' `DBQueryExecutor`.** Plan §4.2 and the task mandate `tx?: DBTransaction` LAST on every method; `UserRepository.findByEmail` / `ApplicantRepository.findByUserId` instead widen reads to `DBQueryExecutor` + `isDBTransaction`/`isPoolClient` guards. The binding instruction wins: a plain truthiness branch selects the executor, and Pool/PoolClient executors are not part of this namespace's contract (the engine only ever passes a `DBTransaction` or `undefined`).
- **D-2 — dual-form single predicate builder.** The sibling read pattern runs the Drizzle builder on `tx` but raw SQL on the fast path, so one predicate must exist in two execution forms. Rather than two builders (drift risk), ONE decomposition (`buildUserScopedPredicate`) emits both forms per active filter in the same pass — REQ-026's "share ONE predicate builder" is honored at the decomposition level, and list/count coherence holds on BOTH branches.
- **D-3 — `createManyReturning([])` returns `[]` without executing.** Degenerate-input contract ("zero rows in, zero rows out"); prevents Drizzle's "values() must be called with at least one value" library error. Not business logic — the engine still owns non-empty-recipient validation pre-DB (plan §4.1).
- **D-4 — `[...inserts]` array spread.** Drizzle's `values()` requires a mutable array; the spread copies the array shell only (row payloads untouched). Explicitly NOT the banned `{ ...input }` object-spread class (grep-verified zero object spreads into Drizzle calls; precedent: `queryDb`'s own `[...params]`).
- No other deviations: method set, names, signatures, ORDER BY, guarded-UPDATE semantics, affected-count return, and filter semantics are byte-faithful to plan §4.2.

## 10. Carry-Forward Knowledge

1. **`(tx ?? db)` union executor COMPILES under tsgo with drizzle-orm 1.0.0-rc.4** — `NodePgDatabase | NodePgTransaction` method calls unify (insert/update/select), so tx-optional writes need no if/else statement duplication.
2. **Awaited Drizzle UPDATE without `.returning()` resolves to pg's `QueryResult`** — `.rowCount: number | null` IS the affected count (`?? 0`). The plan's "Drizzle affected-row count" is exactly this.
3. **oxlint `no-unsafe-enum-comparison` fires on pgEnum column vs TS-enum-member comparisons** (the `$inferSelect` type is the string-literal union, NOT the enum — 1.1 carry-forward #4). Fix: compare against a const typed as `NotificationSelectType["type"]`.
4. **Drizzle `values()` rejects `readonly` arrays** — spread the array shell (`[...rows]`) like `queryDb` does for params; document that it is not an object spread.
5. **Drizzle `count()` is pre-mapped to `number`** — do NOT wrap builder-branch counts in `Number()` (`no-unnecessary-type-conversion` denies it); raw-SQL `count(*)` DOES need `Number()` (pg bigint arrives as a string).
6. **Raw-SQL timestamp columns alias + parse identically to the builder branch** (`created_at AS "createdAt"` → Date objects) — `toEqual` between `queryDb` rows and Drizzle rows works, which is what lets the engine mix branches safely.
7. **For 2.6/2.7:** repo filters params are structural `Pick`s — pass the engine's `NotificationListFilterInput` VARIABLE directly (excess props OK); only fresh literals must be trimmed to `{ type, isRead }`. `markReadOnce`'s `null` is the ONLY not-found signal (translate to `NotFoundError("NOTIFICATION", errorsTranslations.notificationNotFound)`); `markAllReadForUser`'s number is the affected count (return it verbatim); `createManyReturning` gives the batch atomicity REQ-013 needs, with ONE captured `now` per batch supplied BY THE ENGINE via the inserts' `createdAt`.
