## 6. Cleanup Design (REQ-J5)

1. **Commit-or-nothing setup:** the whole cast (3 actors = 3 `users` + 3 role-child rows) is provisioned inside ONE committing `db.transaction` in `beforeAll`; a throwing setup rolls back and leaves nothing.
2. **Side-effect rows tracked as observed:** immediately after `emitForUser` returns, the created row id is registered — `tracked.register(notifications, emittedRow.id)` (2.1's carry-forward rule #2) — so teardown never depends on the `notifications.user_id` cascade alone.
3. **`afterAll` → `tracked.cleanup()`:** reverse-registration-order hard deletes (notifications row FIRST, then each role-child row before its owning user — FK-safe by construction), followed by the mandatory existence re-probe of EVERY registered row; any residue throws and fails the suite.
4. **Never `runInRollback`** (journey-layer rule 1) — the engine owns its transactions; an outer rollback wrapper would deadlock or miss committed rows.
5. **RED-state safety:** while the engine is missing, the suite fails at module load — `beforeAll` never runs, so no fixture is ever created in the RED state (independently probed: `notifications` table count = 0).
