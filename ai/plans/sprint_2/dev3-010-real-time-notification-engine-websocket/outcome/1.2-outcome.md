## 8. Deviations

- **D-1 — TS-mirror-side parity assertion form.** The natural first draft used `expect(Object.values(NotificationType)).toEqual([...CANONICAL_VALUES])`, which fails tsgo with `TS2769`: bun-types declares `toEqual` as `toEqual(expected: T)` / `toEqual<X = T>(expected: NoInfer<X>)`, and with `T = NotificationType[]` the string-literal array is NOT assignable to the enum array (TS string-enum literal types are not bidirectionally assignable). Resolved by using the **precedent's own comparison form** for that assertion — joined-string `toBe` (`Object.values(NotificationType).join("|")` ↔ `CANONICAL_VALUES.join("|")`), exactly how `applicant-status.enum.test.ts` asserts its frozen value set. Nothing was lost: order-sensitive byte identity on the mirror side (joined form) + order-sensitive array-deep equality between pgEnum ↔ TS mirror (`expect([...notificationType.enumValues]).toEqual(Object.values(NotificationType))` — passes because the enum array IS assignable to `string[]`) + the pgEnum-side array-deep assertion. No casts were needed for the fix.
- **D-2 — schema import in an enum-layer test.** The applicant precedent's header says "NO DB, NO schema imports"; this test imports `@/backend/db/schema/enums` because the parity mandate requires reading the pgEnum at runtime. Verified safe (definition-only import; `DATABASE_URL` is even stripped by the runner) and consistent with 4 existing test files importing `@/backend/db/schema`. Documented in the test header so the apparent contradiction with the precedent is explained in-place.
- **D-3 — tier depth exceeds the Tier 1+2 mandate.** The suite implements the precedent's full 4-tier guard structure (Tier 3 chaos/fuzz + Tier 4 security included) rather than stopping at the mandated Tier 1+2, because the applicant file is the layer's only guard-test convention and Tier 4 is the strongest SEC evidence. Test-code-only addition; no production surface added.
- No other deviations. The guard body is byte-faithful to plan §2.3's mandated shape and to the precedent.

2. **bun-types `toEqual` overload quirk:** `expect(<Enum[]>).toEqual(<literal[]>)` fails typecheck (enum array vs literal array are mutually non-assignable) while the reverse (`expect(<literal-or-string[]>).toEqual(<Enum[]>)`) passes (enum members ARE assignable to `string`). For enum parity tests, compare via joined strings (`join("|")` + `toBe`) or anchor `T` on the `string[]` side — never pass an enum-typed array as the `expect()` subject against a literal-array expectation.
3. **Enum runtime tests are co-located and runner-gated:** `backend/enum/**/*.enum.test.ts` (applicant precedent + now notification) run via `bun run test/scripts/run-test.ts <path>`; direct `bun test` is blocked by the `test-runner-guard` preload (bunfig.toml) — always use the canonical runner (also required for log capture).

Future enum-parity tests (e.g., if `NotificationDeliveryStatus` or similar lands in DEV3-011+) can replicate this suite's parity describe directly.
