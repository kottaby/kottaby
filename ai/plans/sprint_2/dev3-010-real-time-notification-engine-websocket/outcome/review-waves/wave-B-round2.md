## Findings

### F1 — MINOR (latent) — `publishReceipts` SILENTLY skips the receipt store when a receipt carries `emitClaimKey` but `options.cache` is absent

- **Location**: `backend/services/notifications/notification-engine.service.ts:616-619` (`publishReceiptsFromIndex`).
- **Evidence**: the store guard is `receipt.emitClaimKey !== undefined && cache !== undefined`. The claim was already CONSUMED at emit time against the emit's injected cache (`claimOrPriorReceipt` → `attemptEmitClaim`, SET-NX-EX). If a caller threads `{ cache }` into `emitForUser(s)` but passes `publishReceipts(receipts, locale, { transport })` (or no options at all), the store is skipped with NO log at skip time — and F1's exact symptom recurs: subsequent same-key replays log "claim held, but no replayable receipt was readable" and fail open into duplicate inserts. Contrast with the emit side, which WARNS symmetrically when a keyed emit runs cache-less (`warnEmitIdempotencyUnavailable`, `emit-idempotency.ts:125-130`). Note the existing `publishReceipts` tests all pass transport-only options (fine today only because those receipts are unkeyed).
- **Rule/impact**: latent — zero production emitters exist (Round-1 F5 re-confirmed: `rg "emitForUser|emitForUsers|publishReceipts|NotificationIdempotencyClaimCache"` non-test hits remain definitions only). The docblock (`:453-455`) documents the requirement, but the failure is silent rather than warned.
- **Suggested disposition**: mirror the emit-side warn — when `receipt.emitClaimKey !== undefined && cache === undefined`, emit one structured `NOTIFICATION_IDEMPOTENCY_DEGRADED` warn ("keyed receipt handed to publishReceipts without a claim cache; receipt not stored").

### F2 — INFO — No direct test for the store-outage fail-open INSIDE `publishReceipts`

- **Evidence**: the `storeThrows = true` outage test (`notification-engine.emit.test.ts:1186-1215`) covers only the OWN-COMMIT path. The new wiring in `publishReceiptsFromIndex` (`:617-619` — the `if` + call) is the fix's only untested seam; the shared helper it calls is fully tested and cannot throw, so risk is low. Suggest one added case: keyed tx-path receipt + `cache.storeThrows = true` → `publishReceipts` resolves, publishes, logs one warn, stores nothing. Folds naturally into the D6 test-hardening pass.

### F3 — INFO — Residual crash-window: commit-then-crash before `publishReceipts` leaves a consumed claim with no receipt

- **Evidence**: pre-existing and documented (`emit-idempotency.ts:79-81`, deviation D5 fail-open). The fix narrows it to a genuine crash/omission window (the happy path now always stores), but the emitter-integration wave should treat "commit succeeded, publishReceipts never ran" as an accepted duplicate-insert source and consider an operational note. No action requested this round.

## New-Defect Hunt on `45a0c9e` (engine + WS server)

**Per-user index (`Map<userId, Set<connId>>`)** — clean. All FIVE registry mutation sites maintain the index in the same synchronous step: open-register (`notification-ws-server.ts:390-391`), close (`:406-409`, guarded by the `registry.delete` result AND a `userId !== null` belt-and-braces — registered sockets always have non-null userId since `open()` returns early on null `:372-377`; rejected handshakes never enter the registry), per-user eviction (`:507-508`), missed-pong termination (`:535-536`), and shutdown (`registry.clear()` + `connectionsByUser.clear()`, `:580-581`). No other `registry` mutations exist (full-file read; grep of `registry.`). Stale entries are impossible: late close events for already-deleted conns no-op on `registry.delete → false`; empty sets are dropped on last unregister (`:300-302`); `randomUUID()` connIds make collisions negligible. The index is a strict derived view bounded by the registry's own global/per-user caps — no new unbounded state. Runtime: the churn, eviction, and over-cap-drain tests (which assert `connectionCountForUser(202) === 0` post-drain) all pass. `deliverFanout` is now O(recipients + their conns) with `sendFrameToConnection` re-checking `registry.get` (stale-id no-op) — the O(recipients × registry) scan is gone.

**Frame cap 4096 (`WS_MAX_INBOUND_FRAME_BYTES`)** — safe for all legitimate traffic. The only legitimate inbound frames in this push-only protocol (REQ-034; `message()` ignores everything, `:394-397`) are CONTROL frames: the client's auto-pongs answering the server's app-owned pings. RFC 6455 §5.5 hard-caps control-frame payloads at 125 bytes, so pongs cannot approach 4096 regardless of whether Bun counts control frames against `maxPayloadLength` (wired at `:352`). Empirical pins from the passing suite: a frame exactly AT 4096 B leaves the socket OPEN; a frame 1 byte OVER closes ONLY the offending socket while a sibling's push loop stays intact (new test, `notification-ws-server.test.ts:873-898`); and the liveness test "a peer that misses 2 consecutive pongs is terminated; a ponging peer survives the same window" passes under the cap — proving pong processing is intact. Oversized-frame handling is per-socket runtime-enforced isolation, never touching the push loop. Outbound frames are not governed by `maxPayloadLength` (inbound-only) — no publish path is affected.

**Engine store/publish wiring** — store-then-publish order on both post-commit paths (own-commit `:364-367`/`:431-437`; `publishReceiptsFromIndex` `:616-622`); `storeEmitReceiptQuietly` cannot throw, so a store outage never suppresses the publish; the in-order index-recursive sweep is preserved (`:624`). `NotificationDeliveryReceipt.emitClaimKey` is an additive optional readonly field — no consumer breakage (non-test consumers: types, engine, emit-idempotency only).
