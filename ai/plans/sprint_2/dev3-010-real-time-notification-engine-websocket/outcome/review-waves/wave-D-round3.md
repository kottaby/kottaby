## Part 2 — Fresh attack angles (this round's mandate)

### (a) GraphQL variable-coercion attacks — **HELD, no bypass**

- **Int overflow in `limit`/`offset`?** `MyNotificationsFilterInput.limit/offset` are Pothos `t.int` → GraphQL `Int` (`notification-filter-input.pothos.ts:37-38`): graphql-js coercion rejects non-integers and anything outside 32-bit signed **before a resolver runs** — no float, no exponent, no >2³¹−1 value can reach the engine. The engine re-validates anyway: `limit ∈ 1..50` (`Number.isSafeInteger` + range, engine `:261-268`), `offset ≥ 0` safe integer (`:269-272`). `offset` has no upper bound, but its GraphQL ceiling (2³¹−1 ≈ 2.1e9) is trivially inside Postgres `bigint` range, binds as a `$N` parameter on BOTH branches (repo `:244-252` raw / `.offset()` builder `:242`), and the scan cost is bounded by the caller's OWN indexed inbox rows — self-harm only, no amplification. `hasMore = offset + items.length < totalCount` cannot overflow at 2⁵³.
- **ID coercion to int?** `markNotificationRead(id: ID!)` accepts string-or-number wire forms; `parseNotificationIdArg` (`notification.mutation.ts:81-90`) guards the number form with `isPositiveSafeInt` and the string form with the canonical regex `/^[1-9]\d*$/` + safe-int re-check. Probed spellings: `"12abc"`, `"1.5"`, `"1e3"`, `" 1 "`, `"012"` (leading zero), non-ASCII digits (`"١٢"` — JS `\d` is ASCII-only), and >16-digit magnitudes all → `NaN` → the engine's pre-DB gate rejects with the localized `ValidationError` before any DB access. An accepted id (e.g. `"9007199254740991"`) addresses at most a nonexistent row → the same guarded zero-row `NotFoundError` as any foreign id (no oracle). Smuggled filter fields (`userId` in the input object) die as GraphQL validation failures — the input type carries exactly `type`/`isRead`/`limit`/`offset` (`notification-filter-input.pothos.ts:30-40`, types `notification.types.ts:104-109`).

### (b) i18n/locale injection + prototype pollution — **HELD, output provably bounded**

- `ctx.locale` originates ONLY from `extractLocale` (`gqlContextFactory.ts:108-120`): the cookie path captures group `(en|ar)` from `/next-locale=(en|ar)/` (any cookie-header position still yields only `en|ar`), the Accept-Language path requires membership in `SUPPORTED_LOCALES = {"en","ar"}` (`:97`), and the fallback is the literal `"en"`. The output set is exactly `{en, ar}` — no attacker-controlled string can reach the translation seam.
- `getServerTranslations(locale)` → `getTranslations` → `resolveLocale` re-guards with `isAppLocale` (`server.ts:11-17`, `AppLocale.ts:5-7`) before the `messagesByLocale[...]` lookup — even a hypothetical `"constructor"`/`"__proto__"` spelling fails the guard and falls to `defaultLocale`. **No namespace is ever derived from user input in the notification path**: the engine performs fixed property access (`.errorsTranslations`) on the resolved bundle; `ctx.t(namespace)` takes compile-time literals in every resolver. No object merge, spread, or dynamic key assignment touches locale-controlled data → **no prototype-pollution path exists**. Localized error copy is constant bundle strings.

### (c) `markAllRead` type-filter as an enumeration oracle — **HELD, self-scoped by construction**

`markAllReadForUser` (`notification.repository.ts:295-310`) ALWAYS conjuncts `eq(notifications.userId, callerUserId)` with `is_read = false` and the optional `type` — the affected-row count (`rowCount`) and the statement's timing profile describe **only the caller's own rows**, read through the caller's own user-keyed index. The `type` values are a public enum; "how many unread rows of type X do I have" is the caller's own data by definition. There is no predicate, count, timing, or error-shape channel that varies with any OTHER user's rows — a cross-user inference requires removing the `user_id` conjunct, which has no code path (single construction site, shared predicate discipline verified R1/R2, unchanged tree). **Not an oracle.**

### (d) Cache-poisoning via the idempotency store (forged receipt with mismatched userId) — **HELD at the trusted boundary; no new exposure**

- The stored value is only ever addressed by `notif:emit:<sha256("sortedIds:type:rawKey")>` (`buildEmitClaimKey`, `emit-idempotency.ts:67-71`); a poisoned entry under a mismatched-userId digest requires **pre-knowledge of the raw emission identity** (recipient ids + type + raw key) **plus Redis write access**. That is exactly the write-compromised-trusted-cache premise Round 2 ruled on (R2 §1c); the extension this round — a revived poisoned receipt flowing through `publishReceipts` into `publishFanout(receipt.recipientUserIds, …)` — is reachable only through the same premise, and an attacker holding Redis write access can already inject well-formed fan-out envelopes directly onto the fixed channel with strictly less effort (`parseFanoutEnvelope` validates shape, not provenance). The idempotency store adds no capability beyond the already-accepted trusted-bus posture. Not re-reported as a finding (documented residual).
- Defense-in-depth verified on the revive path: `parseStoredEmitReceipt` (`:144-185`) enforces exact required keys, non-empty arrays, per-row field-by-field type guards (`parseStoredNotificationRow`, `:188-244` — positive-safe-int ids, enum-guarded type, string/null copy fields, temporal `createdAt`), and **drops `emitClaimKey` on revive** (constructs a fresh `{notifications, recipientUserIds}`), so a replayed prior receipt never re-stores — no store churn, no key reflection. The engine returns a duplicate receipt with NO insert and NO publish; the digest never crosses a client boundary (zero `emitClaimKey` references under `frontend/**` and zero emit-surface references under `backend/graphql/**` — both greps re-run fresh this round).

### (e) WS shutdown race (auth in-flight during graceful shutdown) — **race EXISTS, security impact NONE → F1r3 (INFO)**

Traced at source (`notification-ws-server.ts`): `shutdown()` sets `shuttingDown = true` synchronously (`:563`) but the listener stays up until `bunServer.stop(true)` after the 500 ms drain sleep (`:586-590`); meanwhile `fetch`'s pipeline suspends at `await verifyAccessToken(token)` (`:459`) and — critically — **neither `fetch` after its await nor `open()` re-checks `shuttingDown`** (`open()`, `:359-393`, checks only `reject`/`userId`/global cap). A handshake completing in the drain window therefore upgrades, passes the full auth pipeline, and registers into `registry` + `connectionsByUser` AFTER `registry.clear(); connectionsByUser.clear()` (`:580-581`). Assessed consequences: the late socket never receives the documented `1001` close (the close loop at `:573-579` already ran) and is instead terminated by the forced stop / process exit (`scripts/start-notification-ws.ts:49-57`) within ~0.5–1 s; it receives **zero frames** (`deliverFanout` no-ops on `shuttingDown` BEFORE building the frame, `:330-332`) and zero pings (timer cleared); its close event drains registry/index normally; caps are still enforced in `open()`. **No auth bypass, no post-drain data delivery, no cap evasion, no cross-user path** — an attacker timing a handshake into the window gains a ≤1 s-lived empty socket. Downgraded to INFO (shutdown hygiene), reported as F1r3 below.

## Findings

### F1r3 — INFO — No post-await `shuttingDown` re-check: a handshake completing during graceful shutdown can register after the drain and miss the `1001` close

- **Severity**: INFO (availability/hygiene nuance at process shutdown; zero security impact — assessed above)
- **Location**: `backend/ws/notification-ws-server.ts:459` (`await verifyAccessToken` suspension with no re-check after), `:486` (`server.upgrade` unconditional), `:359-393` (`open()` registers without a `shuttingDown` check), vs. `:563`/`:580-586` (drain + clear + sleep sequence).
- **Evidence**: window = from `shuttingDown = true` to `bunServer.stop(true)` (≥500 ms + unsubscribe duration); an in-flight (or newly arriving) authenticated handshake completing inside it lands in the registry post-`clear()` and is reaped only by the forced stop/process exit — an abrupt close instead of the contract's `1001`. Pinned shutdown tests cover the happy path and idempotency only (`notification-ws-server.test.ts:604-627`); no test races a handshake against shutdown.
- **Suggested fix** (one-line class): re-check `shuttingDown` after the `await verifyAccessToken` (or at the top of `open()`) and policy-close `1001` before registering.

**No BLOCKER, MAJOR, or MINOR findings this round.** All five fresh attack angles (a)–(e) resolved to defense verdicts; the only residual is the INFO-grade shutdown race above.
