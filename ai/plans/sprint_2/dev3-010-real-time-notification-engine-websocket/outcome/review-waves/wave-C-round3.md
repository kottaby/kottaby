## Findings

### F1 — MINOR — focus-visible ring coverage is inconsistent across the new notification surface (WCAG 2.4.7 per the repo's own audit-R4 measurement)
- **Location**: every keyboard-focusable control this feature adds EXCEPT the bell — toast close IconButton (`NotificationRealtimeToastHost.tsx:83-88`), mark-all snackbar close IconButton (`NotificationsFeedContainer.tsx:413-421`), `MarkAllButton` + its dialog buttons (`MarkAllButton.tsx:47-72`), mobile filter toggle Button + read-state pair + 7 type Chips (`NotificationFilterChips.tsx:64-131`), row mark-read Button/IconButton (`NotificationRow.tsx:170-196`), retry Button (`NotificationFeedError.tsx:63-72`), pager Buttons (`NotificationsFeedContainer.tsx:308-328`).
- **Evidence**: the bell IconButton DOES get `...focusVisibleRingSx` (`NotificationUnreadBadge.tsx:77-78`), so the feature applies the repo's ring module to one of its ~12 interactive controls. The repo's own audit-R4 record (`frontend/components/ui/focusRing.ts:4-11`) states: "MUI v9 ButtonBase ships no focus-visible styling — plain IconButtons and Buttons rendered with NO visible keyboard ring (`outline:none`; the default `.Mui-focusVisible` fill measured ≈1.1:1 against the auth panel background), failing WCAG 2.4.7". The shared fix module exists and is applied to `LocaleSwitcher` (`LocaleSwitcher.tsx:58`) — mounted in the SAME AppBar right-actions cluster as the bell — and to `AuthFormShared` (`:116,:144`), so keyboard users see a ring on the locale switcher and the bell, then lose it on every notification action.
- **Rule**: checklist #4 spirit (affordances must actually reach the user — keyboard channel) / repo a11y discipline (audit-R4 module).
- **Fix**: spread `...focusVisibleRingSx` into those controls' `sx` (~10 mechanical sites). Scope note: pre-existing dashboard views (AppBar menu/theme/logout IconButtons) share the gap — a repo-wide backlog; this finding is scoped to the NEW controls this feature introduces, which is where the inconsistency is visible (same feature, same cluster, one control ringed, the rest not).

### F2 — INFO — fresh keyword-pattern sweep: `color: "inherit"` ×2 — ruled sanctioned, recorded for future sweeps
- This round's prescribed NEW pattern `:\s*"(?:transparent|inherit|initial|unset|currentcolor)"` hits exactly two sites: `NotificationsFeedContainer.tsx:418` and `NotificationRealtimeToastHost.tsx:87` — both `sx={{ color: "inherit" }}` on the close IconButton inside a filled `Alert`, i.e. the icon inherits the Alert's contrast-text palette token.
- **Ruling**: `inherit` is a CSS-wide keyword, not a named color — nothing is hardcoded; the rendered color IS the parent surface's theme token, and MUI's `IconButton` itself defaults to `color="inherit"`. Exact repo precedent: `GraphQLErrorSurfaceHost.tsx:130` and `AuthFormShared.tsx:171` (both pre-existing outside this feature, unflagged in rounds 1–2; the toast surface deliberately mirrors the error host's conventions per its docblock). Categorically different from R1-F2's `"transparent"` bgcolor literal (a real named-color value). No action — recorded so future keyword sweeps (which now include CSS-wide keywords per this round's pattern) don't re-flag it.

### F3 — INFO — numeric-literal hunt (the R2-F1 reinterpretation class): one harmless shape-scale oddity; ZERO hazardous literals anywhere in the surface
- **Sweep method**: every sx object in the surface grep-swept for bare numeric `width/height/min*/max*` (sizing transform: `value <= 1 && value !== 0 → ${value*100}%` — `node_modules/@mui/system/sizing/sizing.js:18-20`), `margin/padding/gap` (spacing scale), `top/bottom/left/right` (positions), `zIndex`, `borderRadius` (shape scale) — targets named by this round: NotificationUnreadBadge, ToastHost, FilterChips, List, EmptyState, skeletons, DashboardAppBar badge mount, Row. Transform behavior confirmed empirically on the installed packages via `unstable_styleFunctionSx` (`maxHeight:1→"100%"`, `margin:-1→"-8px"`, `marginTop:0.5→"4px"`, `borderRadius:2→8`, `top:0→0`, `left:12→12`, `zIndex:1200→1200`).
- **Result**: **no sizing prop anywhere in the surface carries a bare numeric ≤ 1 (≠ 0)** — the R2-F1 hazard class is fully eradicated. All numerics found are >1 (raw numbers → emotion px: dot 8/8, type-icon 40/40, avatar 32/32, empty-state 72/72, skeletons 40/40·28·140·120·32·120, minHeight 28/36/44, maxWidth 200/320/420/480, fontSize 14/20, Toolbar minHeight 56/64) or 0 (`minWidth: 0`, list `margin/padding: 0` resets → `0px`). Margin/padding/gap numerics (`gap: 1`, `px: 2`, `py: {xs:6,sm:10}`, `marginTop: 0.5/1`, `my: 0.5`, `p: {xs:1.5,sm:2}`) are the sanctioned spacing-scale idiom (`frontend/AGENTS.md:30`). Toast-stack offsets `bottom: {xs: 96|188, sm: 104|196}` are block-axis positions — passthrough (empirically `top: 0 → 0`, `left: 12 → 12`), so px as intended, RTL-safe. **`NotificationUnreadBadge`'s sx contains no numeric literals at all** (only the documented `[dir=rtl]` CSS-var flip, R1-F4). **z-index**: both toast stacks use the `theme.zIndex.snackbar` token (`NotificationRealtimeToastHost.tsx:57`, `NotificationsFeedContainer.tsx:391`) — no raw z-index numbers anywhere. **Focus-visible**: `focusVisibleRingSx` is palette-token-driven (`var(--mui-palette-secondary-main)` — `focusRing.ts:16-22`); coverage gap → F1.
- **The one oddity**: `NotificationList.tsx:127` — skeleton `borderRadius: 999` goes through the shape scale (`createUnaryUnit(theme,'shape.borderRadius',4)` — `borders.js:41-50`) → `999 × 4 = 3996px`. CSS clamps border-radius to half the box side, so the rendered pill is IDENTICAL to the apparent intent — zero visual/layout impact (unlike R2 F1's viewport-sized box). Optional hygiene: `"999px"` or `"50%"`. The sibling `borderRadius: 2` → 8px sites (Row `:100`, List `:59/:133`, Host `:94`, FeedError `:61`) are the intended MUI idiom (default theme radius) — no action.
