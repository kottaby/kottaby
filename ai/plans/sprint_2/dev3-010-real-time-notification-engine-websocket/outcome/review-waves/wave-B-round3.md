### F1 — INFO (latent) — Stored-receipt cache VALUE is unbounded: cohort size × body length have no caps

- **Location**: `emit-validation.ts:135-147` (`validateEmitBatchInput` — non-empty + no-duplicate recipients, but NO maximum cohort size), `emit-validation.ts:16` + `db/schema/notifications/notifications.ts:36` (`body` is `text`, accepted with no length bound), `emit-idempotency.ts:133-135` (`serializeEmitReceipt` = `JSON.stringify` of the FULL receipt).
- **Evidence**: REQ-016's "duplicate → return the PRIOR receipt" requires the whole receipt in the value, so growth is by design — but nothing bounds it. A 10k-recipient broadcast with a multi-KB body serializes ~10k full rows (each carrying title/body copy) into ONE `cache.store` SET, held 24h per claim key; the same JSON is parsed back on every duplicate replay. Round 1's F6 already noted copy-in-values (data-residency lens); this is the sizing lens the Round-3 hunt asked for. Inert today (no production adapter — R1 F5 re-confirmed — and no production emitters), and the WS egress path is NOT affected (each socket frame carries only the single projected row, not the cohort).
- **Suggested disposition**: for the emitter-integration wave — either cap cohort size in `validateEmitBatchInput` (reject > N with `ValidationError`) or document a chunking rule for large broadcasts, and give emitters a body-length guideline. No action this round.
