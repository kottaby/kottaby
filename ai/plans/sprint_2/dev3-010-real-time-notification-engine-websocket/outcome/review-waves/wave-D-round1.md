# Wave D (pentester) — Round 1

**Reviewer**: independent adversarial agent | **Date**: 2026-08-29 | **Scope**: security

Branch: `feat/dev3-010-real-time-notification-engine-websocket` @ `79f2900`. Static analysis + reasoning only (no live attacks, no code changes, no commits). Every defense below was read at source and actively probed for bypasses.

## Findings

### F1 — MINOR — Sidecar fan-out delivery is an O(recipients × registry) synchronous scan, and envelope sizes are unbounded

- **Severity**: MINOR (latent availability defect on the platform's broadcast path)
- **Location**: `backend/ws/notification-ws-server.ts:267-290` (`deliverFanout`), `backend/services/notifications/realtime/redis-pubsub-transport.ts:166-225` (`parseFanoutEnvelope` — no length bound on `userIds`), `backend/services/notifications/emit-validation.ts:135-147` (`validateEmitBatchInput` — no max cohort size)
- **Attack scenario**: `deliverFanout` iterates `registry.values()` (up to 1000 connections) **for every entry of `userIds`** — O(N×M) synchronous work on the sidecar's single event loop. A `system_broadcast` emit to a 50k-user cohort (exactly the use case the enum member exists for) executes 5×10⁷ iterations plus 50k `Set`-less scans → a multi-second event-loop stall during which ALL handshakes, pings, and pushes for every user are delayed. A stall approaching `idleTimeout` (95s) would additionally reap healthy sockets. The bus side compounds it: `parseFanoutEnvelope` accepts any `userIds` array length and `JSON.parse` handles any message size — a compromised/misbehaving Redis (or a runaway emitter) can publish an envelope with 10⁶+ ids for a minutes-long stall. There is no untrusted ingress to the emit surface today (verified: zero production callers — see Wave B F5), which is why this is MINOR and not MAJOR.
- **Evidence**: `for (const userId of userIds) { for (const state of registry.values()) { … } }` (`notification-ws-server.ts:272-289`); `recipientIds = userIds.filter(isPositiveSafeInteger)` with only a non-empty + all-positive check (`redis-pubsub-transport.ts:180-183`); batch validation checks non-empty/positive/no-dupes but no upper bound (`emit-validation.ts:137-146`).
- **Suggested fix**: build `const targets = new Set(userIds)` and scan the registry once (O(N+M), one line), or maintain a `Map<userId, ConnState[]>` index; optionally bound `userIds.length` in `parseFanoutEnvelope` (drop-and-warn, consistent with the guard's posture).

### F2 — INFO — `verifyAccessToken` `sub` coercion uses `Number.parseInt`, so non-canonical numeric strings pass the "positive-int coerce" (checklist item 10's own question)

- **Severity**: INFO (not exploitable without the HS256 signing secret — and with the secret, `sub: "1"` is available directly)
- **Location**: `backend/lib/auth/jwt.ts:157-160`
- **Evidence**: `Number.parseInt(userIdRaw, 10)` — checklist probe results: `"0"` → FAILS (`userId <= 0`), but **`"1.5"`, `"1e3"`, `" 1 "`, `"1.0"` all coerce to userId 1** (parseInt truncates at the first non-digit and tolerates surrounding whitespace). The sidecar's docblock promises a fail-closed "positive-int coerce" (`notification-ws-server.ts:414-417` re-asserts `Number.isSafeInteger` on the *derived* number, which does not catch the truncation). The signer only ever emits canonical `String(userId)` (`jwt.ts:131`), so no server-issued token carries a non-canonical `sub`; exploitation requires token-forging ability, at which point the attacker picks any `sub` anyway.
- **Suggested fix** (defense in depth): mirror the canonical-form regex already used by the mutation resolver (`notification.mutation.ts:62` `/^[1-9]\d*$/`) when coercing `sub`, so the identity channel fails closed on non-canonical spellings.

### F3 — INFO — Handshake throttle keys on the immediate peer address: behind a reverse proxy or CGNAT, one client can starve the handshake budget for everyone behind the same egress

- **Severity**: INFO (deployment-posture caveat; the anti-spoofing choice itself is correct)
- **Location**: `backend/ws/notification-ws-server.ts:377-379` (`server.requestIP(request)` → `ipKey`; `X-Forwarded-For` deliberately never read — no spoofing surface)
- **Evidence**: bucket = 5-token burst + 1 token / 2s sustained per address. If the sidecar is deployed behind an LB/reverse proxy or carrier-grade NAT, ALL clients share ONE bucket → a single script (valid origin + no cookie needed — throttled requests consume tokens regardless of auth outcome, `:379` runs before the cookie read at `:387`) can hold the shared bucket at zero and force `4429` for every legitimate user behind that egress. Also, IPv6 keying uses the full address (not a /64), so one /64 yields per-address buckets — the standard per-IP-throttle limitation.
- **Suggested disposition**: pin the deployment contract in the ops docs (sidecar directly exposed, or one real client per bucket / trusted-proxy strategy to be designed before prod). No code change requested in this wave.

### F4 — INFO — Global-cap exhaustion DoS assessment (checklist item 7's explicit ask): accepted residual risk

- **Severity**: INFO (documented residual; no change requested)
- **Location**: `backend/ws/notification-ws-server.ts:325-334` (cap 1000 → `1013`), `:437-457` (per-user cap 5 → oldest evicted `4009`), `:469-488` (missed-pong reaping)
- **Assessment**: filling the 1000-slot registry requires ≥200 **authenticated** accounts (per-user cap 5 evicts beyond that, regardless of source IP), each keeping sockets alive through the app-owned ping/pong cadence — i.e., a mass-credential-compromise attack, at which point notification DoS is not the interesting impact. Acquisition is rate-limited per source IP (0.5/s sustained); silent sockets are reaped within ~2 ping intervals (60s+); legitimate users rejected with `1013` retry with backoff (`use-notification-realtime.ts:509-535`) and recover as slots free. Unauthenticated sockets never enter the registry (rejected in `open()` before `registry.set`), so no unauth cap-exhaustion path exists. Fail-closed, bounded, acceptable.

### F5 — INFO — 16MB inbound frame budget for a push-only protocol

- **Severity**: INFO (cheap hardening; authenticated + origin-checked clients only)
- **Location**: `backend/ws/notification-ws-server.ts:76` (`WS_MAX_INBOUND_FRAME_BYTES = 16 * 1024 * 1024`), `:299` (`maxPayloadLength`), `:340-343` (`message()` ignores every application frame per REQ-034)
- **Evidence**: the protocol needs ZERO client→server application bytes (pong is a *control* frame, not counted against `maxPayloadLength`); Bun's documented default of 16MB is carried over verbatim. Authenticated clients can still buffer junk up to that cap per socket before the runtime closes 1009. Shrinking to a few KB is free hardening.

### Cross-reference — Wave B F1 (MAJOR, latent) confirmed still open, security angle

- **Location**: `backend/services/notifications/notification-engine.service.ts:341-344` / `:400-403` (tx branches return the receipt with no `storeEmitReceiptQuietly`; only own-commit branches `:351-355` / `:412-417` store).
- **Verified this round**: unchanged at HEAD. Security relevance: the pre-insert claim is consumed but no receipt is ever stored for tx-owning emitters, so a replayed domain event inserts **duplicate user-visible notifications** (duplicate-content amplification) while the claim TTL holds — a correctness/availability issue on the tx path, inert today (no production emitters, no production claim-cache adapter). Not counted as a new Wave D finding; disposition belongs to Wave B F1.

## Verdict

**5 new findings: 0 BLOCKER / 0 MAJOR / 1 MINOR (F1) / 4 INFO (F2, F3, F4, F5)** — plus one cross-reference confirming Wave B F1 (tx-path idempotency receipt store) still open at HEAD.

All 12 checklist defenses VERIFIED HOLDING with direct source evidence; no BOLA, oracle, BOPLA, BFLA, CSWSH, query-token, SQL-injection, XSS, or log-disclosure bypass was found despite active hunting. The core identity architecture is genuinely sound: identity is unreachable from any client-controlled input on every path (GraphQL input types carry no identity field; the WS handshake reads only Origin + cookie; the JWT `sub` is the sole identity source and is re-asserted server-side).

**Recommended next actions**:
1. F1 — apply the O(N+M) delivery fix (Set-based recipient matching or a per-user registry index) BEFORE any broadcast-scale emitter ships; consider bounding envelope `userIds` length in `parseFanoutEnvelope`.
2. F2 — switch `sub` coercion to the canonical positive-int regex (mirrors `notification.mutation.ts:62`).
3. F3 — pin the sidecar deployment posture (direct exposure / proxy strategy) in the ops runbook before production.
4. F5 — shrink `WS_MAX_INBOUND_FRAME_BYTES` to a few KB (push-only protocol).
5. Re-check Wave B F1 disposition before the first tx-owning emitter adopts `idempotencyKey`.
