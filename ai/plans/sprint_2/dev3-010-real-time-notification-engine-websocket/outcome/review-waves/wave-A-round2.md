### INFO-R2-1 — `emitClaimKey` digest-form invariant is construction-enforced, not type-enforced (compliant with repo convention, documented)

- **Severity**: INFO (no rule violation — recorded because the Round-2 brief explicitly asks "hashed-digest invariant: enforced by types or only convention?")
- **Location**: `backend/types/notifications/notification.types.ts:94` (`readonly emitClaimKey?: string`), `backend/services/notifications/emit-idempotency.ts:67` (`buildEmitClaimKey(…): string`), `emit-idempotency.ts:47-51` (`NotificationIdempotencyClaimCache.claim/store/get(key: string, …)`)
- **Evidence**: The digest-form invariant is carried by **JSDoc + single-producer construction + a runtime pin**, not by the type system: the field, the builder's return, and the cache port's key parameter are all plain `string`, so a raw `idempotencyKey` is *type-assignable* to `emitClaimKey`. It is nevertheless safe by construction: the ONLY producer is `buildEmitClaimKey` (`emit-idempotency.ts:67-71`, returns `notif:emit:<sha256-hex>`, raw key never leaves it), the engine attaches only that producer's output (`notification-engine.service.ts:356` and `:421`, both fed from `claimOrPriorReceipt`'s `claimKey`), and no other site in the tree assigns the field (`rg -n emitClaimKey` → 8 hits: 1 type field, 2 engine attachments, 2 engine reads, 3 comments/tests). The invariant is additionally runtime-pinned: `notification-engine.emit.test.ts:1112+1124` asserts `receipt.emitClaimKey === buildEmitClaimKey([...], type, idempotencyKey)`.
- **Why it is NOT a violation**: the repo has **zero branded/nominal string types anywhere in `backend/`** (`rg "type \w+ = string & |Brand|branded" backend/` → no type hits), so demanding a branded `EmitClaimKey` here would invent a convention the codebase does not use. Plain `string` is the established pattern (cf. `DBTransaction`, `NotificationType` consumers all use structural types).

### INFO-R2-2 — tx-path stored receipt JSON redundantly embeds the claim digest; the revive path deliberately drops it (harmless, digest-only)

- **Severity**: INFO (runtime/storage observation arising from the reviewed type addition — no type-discipline defect)
- **Location**: `backend/services/notifications/notification-engine.service.ts:617-618` → `emit-idempotency.ts:112-122` (`storeEmitReceiptQuietly`) → `:133-135` (`serializeEmitReceipt` = `JSON.stringify(receipt)`)
- **Evidence**: On the caller-`tx` path the receipt carries `emitClaimKey`, so the cache VALUE stored under that key embeds the digest a second time (as key AND as a field inside the JSON). `parseStoredEmitReceipt` (`:144-185`) rebuilds the revived receipt field-by-field **without** `emitClaimKey`, so replayed prior receipts never carry the field — semantically correct: a replayed (already-claimed) receipt must not re-store even if a caller wrongly re-publishes it, and `publishReceiptsFromIndex`'s store step is gated on `receipt.emitClaimKey !== undefined` (`service.ts:617`). No raw key rides either form (digest only, both layers).
- **Why it is NOT a violation**: pure redundancy of a non-sensitive digest; no shape duplication (the stored JSON is a serialization of the canonical type, not a second type), and the drop-on-revive behavior is fail-safe in the conservative direction.
