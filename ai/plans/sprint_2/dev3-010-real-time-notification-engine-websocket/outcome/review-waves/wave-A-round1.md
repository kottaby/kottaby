### INFO-1 — Frontend wire-frame structural view of the realtime envelope (compliant, documented)

- **Severity**: INFO (no rule violation — recorded because checklist #7 asks about payload copies)
- **Location**: `frontend/hooks/use-notification-realtime.ts:124-138`
- **Evidence**: `rg -n "RealtimeNotificationPayload"` across the tree → the only **definition** is `backend/types/notifications/notification.types.ts:124` (`export interface RealtimeNotificationPayload`). Every other occurrence is either a `import type … from "@/backend/types"` consumer or a test object literal. Separately, `rg -n 'kind: "notification"' --type ts` surfaces a second *type declaration* of the envelope shape: `RealtimeNotificationFrame`/`RealtimeNotificationFrameData` at `use-notification-realtime.ts:124-138`.
- **Why it is NOT a violation**: the frontend layer is forbidden from importing `@/backend/types` (the file's own header at :117-123 documents this: "the canonical type lives in `backend/types`, which the frontend layer never imports"). The frame type is deliberately **not** a copy of the canonical type: it models the JSON wire form (`id: number | string`, `createdAt: string` vs canonical `Date`, `type: string` pre-guard), carries a distinct name, and is guarded at runtime by `isRealtimeNotificationFrame` (:148-167) which fails closed on any envelope revision drift (`v !== 1` / `kind !== "notification"` → drop). This is the same sanctioned cross-boundary pattern as the spied-transport's `FanoutTransportLike` (`test/workflows/helpers/spied-transport.ts:24`), which imports the canonical payload rather than re-declaring it. No third copy exists anywhere (verified: `kind: "notification"` type-declaration sites are exactly these two + canonical; all other hits are object literals in tests or the runtime guard reconstruction in `redis-pubsub-transport.ts:213`).
