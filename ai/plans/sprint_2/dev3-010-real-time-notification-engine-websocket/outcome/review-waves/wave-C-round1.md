## Findings

### F1 — MINOR — `aria-label` on a generic `Box` never reaches assistive tech
- **Location**: `frontend/views/notifications/NotificationRow.tsx:95-104`
- **Evidence**: the unread dot is rendered as
  ```tsx
  <Box aria-label={labels.filterUnread} sx={theme => ({ ... bgcolor: theme.palette.primary.main })} />
  ```
  `Box` renders a bare `div` (ARIA `generic` role). Per ARIA in HTML, `generic` is a name-prohibited role — screen readers ignore `aria-label` there, and axe-core flags it as `aria-allowed-attr` ("aria-label attribute cannot be used on a div with no valid role"). The component docblock (`NotificationRow.tsx:38-39`) claims "a dot chip (accessible name = `filterUnread`) flags the unread state" — the translated label is therefore dead weight: the unread state is conveyed by tint + bold only (WCAG 1.4.1 borderline for the dot itself; the row action button presence is the real differentiator). The only in-repo `Box`+`aria-label` precedent is `frontend/views/dashboard/DashboardSidebar.tsx:62`, which uses `component="nav"` (landmark — naming IS allowed). Fix: `role="img"` + `aria-label`, or visually-hidden text next to the dot, or reuse the `Chip` used elsewhere in the row.
- **Rule violated**: checklist #4 (translated string must actually reach the user) / repo a11y discipline.

### F2 — MINOR — bare CSS color keyword `"transparent"` in `sx`
- **Location**: `frontend/views/notifications/NotificationRow.tsx:73`
- **Evidence**:
  ```tsx
  bgcolor: unread ? theme.palette.action.selected : "transparent",
  ```
  `frontend/AGENTS.md:4` states "NEVER use hex colors, rgb/rgba values, **or color names**". `"transparent"` is a CSS color keyword literal in `sx`. The Wave-C grep spec (`#[0-9a-fA-F]{3,8}`, `rgb(`, `hsl(`) does not catch keywords — this is the one keyword literal in the surface. Repo precedent uses `transparent` only as a `color-mix()` endpoint alongside palette tokens (`GraphQLErrorSurfaceHost.tsx:143,166,235`, `ApiStatusIndicator.tsx:188-214`, `SiteFooter.tsx:33,131,146`) — no other bare `bgcolor: "transparent"` exists under `frontend/views/**` or `frontend/components/**`. Impact is nil (the value is semantically "no background" and the row `Box` has no default bgcolor — the key could simply be omitted in the read branch), but it is the sole literal that contradicts the letter of the color-name rule.
- **Rule violated**: checklist #2 (palette-token colors) — keyword edge case not covered by the prescribed greps.

### F3 — INFO — vertical physical margin properties (not RTL-breaking; repo-sanctioned shorthand family)
- **Location**: `NotificationRow.tsx:124` (`marginTop: 0.5`), `NotificationFeedError.tsx:76` (`marginTop: 1`), `NotificationFilterChips.tsx:112` (`my: 0.5`)
- **Evidence**: RTL-sensitive (inline-axis) physical properties are ZERO across the surface — `rg 'marginLeft|marginRight|paddingLeft|paddingRight|left:|right:|text-align'` over the surface exits 1 (no matches); the toast stacks use `insetInlineStart/End` (`NotificationRealtimeToastHost.tsx:42-43`, `NotificationsFeedContainer.tsx:380-381`). Vertical physical margins do not mirror under `dir=rtl`, and `frontend/AGENTS.md:30` explicitly sanctions `mt`/`mb` sx shorthands ("<Typography sx={{ fontWeight: 700, mb: 1 }}>"). No action required; noting for the record since the strict logical form would be `marginBlockStart`.

### F4 — INFO — badge RTL override is a deliberate physical-CSS-vars workaround
- **Location**: `frontend/components/ui/NotificationUnreadBadge.tsx:86-98`
- **Evidence**: `[dir=rtl] & .MuiBadge-badge` flips `--Badge-inset/--Badge-origin/--Badge-translate` with `!important` because MUI's badge anchor slot is physical. The inline comment (lines 87-93) documents why. This is the code that MAKES the badge RTL-correct — no violation; recorded so a future reviewer does not mistake it for physical-property drift.
