### INFO-R3-1 — `RealtimeNotificationCacheRow` hand-declares the 8 `Notification` fields instead of deriving from the codegen row type (drift window exists but is bounded and loud elsewhere)

- **Severity**: INFO (no rule violation — surfaced by the Round-3 "type duplication that could drift" hunt; pre-existing since task 4.2, file untouched since `765fbdb`, i.e. before Round 1)
- **Location**: `frontend/hooks/use-notification-realtime.ts:217-228` (declaration), `:458-468` (construction), `:321` (sole consumption: `details.toReference(row, true)` inside `cache.modify`)
- **Evidence**: The type re-lists all eight public `Notification` fields (`id: string`, `type: NotificationType`, `title`, `body: string | null`, `isRead: false`, `relatedEntityType/Id`, `createdAt: string`) as `StoreObject & { … }`. Its only sink is Apollo's `toReference`/`cache.modify` — a deliberately untyped escape hatch — so a future GraphQL `Notification` field change would **not** fail to compile at this site (it WOULD fail loudly in `NotificationRow.tsx:6` / `NotificationList.tsx:6`, which type their props by the codegen `MyNotificationsQuery_myNotifications_items`).
- **Why it is NOT a violation**: it is a *specialized cache-write view*, not an operation-result type — `isRead` is literal-narrowed to `false` (fresh-arrival invariant), `__typename` is added, and the `StoreObject` intersection is required for `toReference(row, true)`. Checklist #8's codegen-only rule concerns operation result/variable types, which are all imported from codegen everywhere. The drift window is also runtime-bounded: the frame guard `isRealtimeNotificationFrame` fails closed on envelope revision drift and `isNotificationType` drops unknown types. **Hardening suggestion** (one line, non-blocking): `type RealtimeNotificationCacheRow = StoreObject & MyNotificationsQuery_myNotifications_items & { readonly __typename: "Notification"; readonly isRead: false }` — the construction literal would then get compile-time excess/missing checks against the codegen shape.
