### CA-3 — Idempotency claim port (J2-defined concrete structure for 2.2 §3c's advisory `cache?: object` placeholder; no J1 precedent — 0.2-outcome A1 ruled Task 2.6 defines its own injected SET-NX-EX port)

```typescript
interface NotificationIdempotencyClaimCache {
  claim(key: string, ttlSeconds: number): Promise<boolean>; // atomic SET NX EX — true = claim WON (proceed with write); false = already claimed (duplicate)
  store(key: string, value: string, ttlSeconds: number): Promise<void>; // plain SET-with-TTL overwrite — attach the completed receipt AFTER insert
  get(key: string): Promise<string | null>; // GET — the prior receipt's serialized value for an already-claimed key
}
```

**Why value storage is required (not just a boolean claim):** the `notifications` table has NO idempotency-key column (schema zero-drift, REQ-048) — REQ-016's "duplicate claim → return the PRIOR receipt" is satisfiable ONLY by a value-carrying claim cache (claim before insert, `store` the serialized receipt after commit, `get` on duplicate). The journey's `InMemoryClaimCache` test double mirrors the three ops with wall-clock TTL expiry; Redis adapters (Task 2.6) map 1:1 (`SET NX EX` / `SET EX` / `GET`). Fail-open-on-outage semantics are 2.6's service-tier concern (D5) — the journey's double never throws.

### CA-4 — Batch emit behavior (REQ-013/021/047)
