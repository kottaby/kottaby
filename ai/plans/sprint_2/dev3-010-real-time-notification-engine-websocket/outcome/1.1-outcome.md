## 8. Deviations

- **D-1 — `NotificationReturnType` RHS form.** Plan §2.2 writes `export type NotificationReturnType = NotificationSelectType;`. That exact form is flagged by `sonarjs/redundant-type-aliases` (S6564, error in the type-aware lint service: *"Remove this redundant type alias and replace its occurrences with 'NotificationSelectType'"*), and the QL gate must exit 0. Resolved as:
  ```typescript
  export type NotificationReturnType = typeof notifications.$inferSelect;
  ```
  **Type identity is preserved exactly** — both sides derive the row shape from the same table's `$inferSelect`, and the conformance suite pins bidirectional assignability (`selectAsReturn` / `returnAsSelect`). No suppression comments and no shared-config changes were introduced. The plan's stated intent (a service/API type name Pothos binds, instead of a schema type name) is fully preserved. Every §2.2 consumer (`NotificationDeliveryReceipt`, `NotificationListPageReturnType`, `RealtimeNotificationPayload.data`) references `NotificationReturnType` unchanged.
- **D-2 — `NotificationType` import form in the types file.** Imported as `import type` (with a NOTE mirroring `applicant.types.ts`) instead of the literal value-import phrasing, because the enum is used only at type positions here and Biome `useImportType` provably normalizes value imports in that situation (empirical probe recorded in §6). The value-import mandate remains honored at every runtime-consumption site (guard, Pothos registration, service validation — and the test-d suite's 8 member accesses).
- No other deviations. Shapes, field optionality/nullability, readonly modifiers, the `v: 1` / `kind: "notification"` literals, and the `Pick` key list are byte-faithful to plan §2.2.
