## 1. What Was Built

**NEW `backend/services/notifications/realtime/`** — the realtime fan-out substrate, five modules + namespace barrels:

- **`fanout-transport.ts`** — the PORT module: `NotificationFanoutTransport` (publish-only, exactly the plan §4.3 shape) + the symmetric subscriber-side contracts (`FanoutListener`, `FanoutSubscription`, `NotificationFanoutSubscriptionSource`). The publish port is deliberately publish-only so the journey layer's `SpiedFanoutTransport` satisfies it structurally without modification (pinned green by a dedicated conformance test importing the spy from `@/test/workflows/helpers/spied-transport`).
- **`in-process-transport.ts`** — `InProcessTransport`: direct in-memory tap with subscription registration (copy-on-write listener registry, instance-scoped — zero module-level mutable state); the ONLY transport legal in tests/harnesses and usable in single-process dev.
- **`redis-pubsub-transport.ts`** — `RedisPubSubTransport` over an injected minimal client port (`RedisFanoutClient`: publish/subscribe/unsubscribe/close): fixed channel `kottaby:notifications:fanout`, JSON envelope `{ userIds, payload }` emitted through an allowlisted field projection; symmetric `subscribeFanout` side whose every message passes the exported runtime shape guard `parseFanoutEnvelope` (malformed → drop + ONE structured `logger.logDomainError` warn `{ code: "NOTIFICATION_FANOUT_ENVELOPE_INVALID", entity: "notifications" }` — never a crash); a throwing listener is logged (`NOTIFICATION_FANOUT_LISTENER_ERROR`, `errorName` only) and the loop survives.
- **`ioredis-fanout-client.ts`** — `IoredisFanoutClient(url, options?)`: the default Redis client over ioredis (the README's local/self-hosted client). `lazyConnect` (construction never dials), `maxRetriesPerRequest: 1` (publishes fail fast on outage — empirically ~250 ms to a clean typed rejection against a refused loopback port), an `error`-event listener attached at construction (outages never become unhandled crashes), `close()` = QUIT with a force-disconnect fallback (never keeps the host process alive). **Deliberately NOT re-exported through the barrel** — see D-4.
- **`fanout-transport.factory.ts`** — `resolveFanoutTransport(options?)`: reads ONLY `getNotificationFanoutTransport()` + `getRedisUrl()` from the registered env seam; `in-process` → `InProcessTransport`, `redis` → `RedisPubSubTransport` over the injected client or the default ioredis client (built via a LAZY `await import` — ioredis never loads in in-process/test import graphs). Stateless by design; `redis` selected with no `REDIS_URL` throws a fail-fast configuration `Error` (mirrors `env.ts`'s `requireEnv` plain-error precedent for bootstrap misconfiguration — not a domain error).
- **Barrels** — `realtime/index.ts` (4 modules; `./` paths, `export *`, one `/` per path) + `notifications/index.ts` (`export * from "./realtime"`). `backend/services/index.ts` deliberately NOT extended (D-5).

**Degenerate-input contract (both adapters, symmetric):** `publishFanout([], payload)` resolves WITHOUT touching the bus (no bus traffic, no listener delivery) — the transport-level mirror of 2.4's `createManyReturning([])` → `[]`.

**Outage contract:** both adapters' `publishFanout` reject cleanly on failure (the error propagates untouched); degradation (log + persisted-inbox-only) remains the ENGINE's concern per REQ-011 — task 2.6 consumes this by catching publish failures.

**Engine (2.6/2.7) consumption notes:**
- The options seam `{ transport?: NotificationFanoutTransport, cache? }` (2.2 §3c / 2.3 CA-2) plugs straight in: `SpiedFanoutTransport` is a structural `NotificationFanoutTransport` (pinned by `fanout-transport.test.ts` — the spy records publishes driven through a port-typed reference, unmodified).
- The factory is **async and stateless**. When `options.transport` is absent, resolve the default ONCE per process at the engine's own seam and memoize it there — calling `resolveFanoutTransport()` per emit would construct a fresh ioredis client (and TCP connection) every time. (The module-level bounded-memo decision belongs to 2.6 under its own state-discipline rules.)
- Publish failures reject — wrap engine publishes in try/catch → `logger.logDomainError({ code: "NOTIFICATION_DELIVERY_DEGRADED", entity: "notifications" })` → resolve (REQ-011/043). The transports already NEVER swallow publish errors.
- `publishFanout([], …)` is a no-op — the engine still validates non-empty recipients pre-DB (2.4 D-3 note); zero-publish assertions in journeys remain valid because the engine simply will not call the transport for empty batches.

**Sidecar (2.8) consumption notes:**
- Subscribe via the SAME transport interface: `await transport.subscribeFanout(listener)` — the listener receives ONLY guard-validated envelopes (`userIds` positive-safe-int array, payload type-true with `createdAt` revived to a `Date`), so the sidecar needs no re-validation of shape; it routes `envelope.userIds` → socket-set intersection and forwards `envelope.payload` (REQ-021 frame).
- The sidecar's shutdown path calls `subscription.unsubscribe()` and (when it owns the client) `client.close()`.
- The in-process publish path propagates a throwing listener's error to the PUBLISHER (async rejection) while the redis path logs-and-drops it — a deliberate medium-correct asymmetry (documented in both adapters' JSDoc); the sidecar runs on the redis/in-process subscribe side where its own bugs are logged, never crash the loop.

## 6. SEC — Security & Tenancy Audit (2.5.SEC)

- **Envelope carries ONLY allowlisted payload fields — by construction AND by test:** the publish side builds the wire envelope through `projectFanoutPayload` (an explicit field-by-field projection of `v`/`kind` + the 7-field `data` projection), so extra runtime properties cannot cross the bus even if smuggled past the compile-time type — pinned by the "extra properties smuggled past the compile-time type never reach the bus" test (an intersection-typed payload carrying `smuggled: "secret"`; the wire JSON contains neither `smuggled` nor `secret`). The wire key-sets test pins EXACTLY `["payload","userIds"]` / `["data","kind","v"]` / the 7 data fields.
- **Channel name constant:** `NOTIFICATIONS_FANOUT_CHANNEL = "kottaby:notifications:fanout"` is the single production definition; grep evidence: the literal appears in production code ONLY in that const declaration + its JSDoc (test files reference it via the imported constant after the final cleanup pass — zero hardcoded channel literals outside the declaration).
- **No user PII on the bus:** the envelope carries recipient ids + the 7-field notification projection; the payload contains NO `userId` (pinned: `Object.hasOwn(data, "userId") === false`). All transport logging carries codes/entities only — `{ code, entity, errorName }` — never titles, bodies, recipient lists, or connection strings (grep evidence in §4 of the SR section: the three `logDomainError` sites use exactly `code`/`entity`/`errorName`).
- **Runtime shape guard before touching connections (REQ-045):** `parseFanoutEnvelope` validates JSON → exact key sets (extra AND missing keys both reject) → positive-safe-integer recipient ids and `id`/`relatedEntityId` → enum-validated `type` (via the 1.2 `isNotificationType` fail-closed guard) → primitive types for the remaining fields → parseable ISO timestamp (revived to `Date`). Malformed → dropped + ONE structured warn per message, zero deliveries, zero crashes (32-case matrix).
- **Fail-fast misconfiguration:** `redis` selected without `REDIS_URL` throws a descriptive configuration error at resolution time (a static deployment error must not masquerade as a runtime degradation).

## 9. Deviations

- **D-1 — Subscriber side is a SEPARATE port interface (`NotificationFanoutSubscriptionSource`).** The task requires the port be "structurally satisfied by the existing `SpiedFanoutTransport`" (publish-only). Folding `subscribeFanout` into `NotificationFanoutTransport` would break that assignability, so the symmetric subscribe contract lives beside the publish port in the same module. The sidecar (2.8) types against the separate interface; publish-only doubles keep satisfying the publish port untouched.
- **D-2 — The selection factory is ASYNC with a lazy ioredis import.** Plan §4.3 does not specify sync/async. Async was chosen to honor the backend's documented lazy-adapter-import exception (cron queue-adapter precedent): ioredis loads only when the Redis bus is actually selected, keeping the SDK out of in-process/test import graphs (serverless cold-start posture). Consumers are all async (engine methods, sidecar startup).
- **D-3 — `publishFanout([], …)` is a documented no-op on BOTH adapters.** An envelope addressed to nobody is bus traffic with zero observable routing effect; dropping it is the transport-level mirror of 2.4's `createManyReturning([])` degenerate-input contract. The engine still owns non-empty-recipient validation pre-DB.
- **D-4 — `ioredis-fanout-client` is NOT re-exported through the realtime barrel.** A static barrel re-export would load ioredis into every barrel consumer, undoing D-2's laziness. The barrel documents the exclusion; consumers deep-import the concrete client only where genuinely needed (the factory does so lazily; the integration smoke statically).
- **D-5 — `backend/services/index.ts` was NOT extended with `./notifications`.** Precedent: the top services barrel already omits the heavy/leaf namespaces (`fx`, `gateway`, `redis`). The notifications namespace (which transitively carries ioredis via its factory default) stays importable at `@/backend/services/notifications`; task 2.6 decides the top-barrel question when the engine lands.
- **D-6 — The subscribe side revives `createdAt` to a `Date`.** The wire format stays pure JSON (ISO-8601 string), but `parseFanoutEnvelope` constructs a real `Date` so the listener observes the exact `RealtimeNotificationPayload` type (type-true round-trip — the sidecar and any `toEqual` assertions see Dates, matching the in-process path).
- **D-7 — Publish-side allowlist projection (`projectFanoutPayload`).** Not strictly required by the compile-time type, but it makes "the envelope carries ONLY allowlisted fields" true BY CONSTRUCTION (SEC) rather than by convention — extra runtime properties cannot cross the bus even past an `as` cast.
- **D-8 — Default client posture: `lazyConnect: true` + `maxRetriesPerRequest: 1` + always-attached `error` listener.** Empirically verified in-sandbox: construction never dials; a publish against a refused loopback port rejects in ~250 ms with a typed error; the background connection keeps retrying with ioredis' default capped backoff so subscriptions resume automatically once Redis returns (REQ-045 reconnect posture). Callers may override any option via the `options?: RedisOptions` passthrough (used by the unit tests' no-retry posture).
- **D-9 — Asymmetric listener-failure semantics between the two adapters (documented in both JSDocs).** In-process: a throwing tap rejects `publishFanout` (the publisher learns immediately — the in-process analogue of a publish outage). Redis: a throwing listener is logged and dropped so the socket/subscription loop never crashes (REQ-045's "never crash"). Both are the correct semantics for their medium.

## 10. Carry-Forward Knowledge

1. **ESLint bans relative imports outside `**/index.ts`** — even between sibling modules of a new namespace (`./fanout-transport` fails `no-restricted-syntax`). Barrels are the ONLY exemption. Dynamic `import()` escapes the ESLint selector but should still use the `@/` alias.
2. **`sonarjs/assertions-in-tests` requires an `expect()` in every test** — "completes without hanging/throwing" tests need an honest assertion; time-bound assertions (`Date.now() - startedAt < bound`) assert exactly that property.
3. **ioredis under Bun is fully runnable for negative-path tests**: `new Redis("redis://127.0.0.1:1", { lazyConnect: true, retryStrategy: () => null })` + publish rejects in ~10 ms; with the default retry strategy + `maxRetriesPerRequest: 1` it rejects in ~250 ms (`MaxRetriesPerRequestError`); `close()` (QUIT → force-disconnect fallback) always releases the process. `disconnect()` after any state prevents the retry loop from keeping the event loop alive.
4. **Bun test supports top-level `await` + `describe.skipIf`** — the combination is the cleanest env/reachability gating for integration suites (probe at module load, skip the describe when unreachable). The canonical runner and the runner-guard both tolerate it.
5. **Index-signature fixture types** (`{ [key: string]: unknown; … }` nested per level) let tests mutate parsed-JSON-shaped fixtures with zero `any` and zero type assertions — the oxlint-safe replacement for `as MutableThing` test doubles.
6. **For 2.6:** the engine's default transport = `(await resolveFanoutTransport())` resolved ONCE and memoized at the engine's own seam (the factory is stateless by the bounded-state mandate); injected `transport` in the options seam bypasses the factory entirely. Publish failures: catch → `logger.logDomainError({ code: "NOTIFICATION_DELIVERY_DEGRADED", entity: "notifications" })` → resolve (the transports never swallow). `publishFanout` with an empty batch never reaches the bus.
