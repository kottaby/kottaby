## 1. What Was Built

**NEW `NotificationEngine` emit surface** — `export namespace NotificationEngine` in `backend/services/notifications/notification-engine.service.ts`, plus two focused helper modules (the service file hosts zero type definitions per `backend/services/AGENTS.md`; all shapes come from `@/backend/types`):

- **`emit-validation.ts`** — the pre-DB fail-closed gate. `validateEmitInput` / `validateEmitBatchInput` run BEFORE any database AND before any cache access; every failure throws the localized generic `ValidationError` (`errorsTranslations.validation` — the errors namespace deliberately ships no emit-specific keys). Rules: `title` non-empty-after-trim ≤255 (schema `varchar(255)`; stored VERBATIM — the emptiness check is validation, never transformation), `body` nullable string, `type` via the 1.2 fail-closed `isNotificationType` VALUE import, `relatedEntityType`/`relatedEntityId` strict co-presence (type non-empty ≤100 = schema `varchar(100)`; id positive safe int), recipient ids positive safe ints via the shared `isPositiveSafeInt` guard (exported — 2.7's inbox id guard reuses it), batch list non-empty with NO duplicate recipient ids (a duplicated cohort member is a caller bug, rejected pre-DB), optional `idempotencyKey` non-empty ≤128.
- **`emit-idempotency.ts`** — the claim machinery behind deviation D5. `NotificationIdempotencyClaimCache` INJECTED port (`claim(key, ttlSeconds)` = SET-NX-EX · `store(key, value, ttlSeconds)` = SET-EX · `get(key)` — value semantics REQUIRED because `notifications` has no idempotency-key column, zero schema drift); `buildEmitClaimKey` (`notif:emit:<sha256("<sorted recipient ids joined by ,>:<type>:<key>")>` — raw key NEVER stored or logged, only its SHA-256 hex digest); `attemptEmitClaim` (claim won → proceed; held + replayable receipt → `duplicate` with the revived prior receipt; held + unreadable/nothing stored or ANY cache error → `unavailable` = fail-open + ONE structured warn); `storeEmitReceiptQuietly` (receipt attached ONLY after the insert's transaction has committed — a receipt stored pre-commit could outlive a rolled-back emission and ghost future replays); `serializeEmitReceipt`/`parseStoredEmitReceipt` (field-by-field revive of every row; ANY structural deviation → `null` → fail-open, never a crash). TTL constant `NOTIFICATION_EMIT_CLAIM_TTL_SECONDS = 86_400` (24h, `docs/IDEMPOTENCY.md` window). NO default cache adapter and ZERO module-level cache state — keyed emits without an injected cache run fail-open with a warn.
- **`notification-engine.service.ts`** — the engine. `emitForUser(input, locale, tx?, options?)` / `emitForUsers(input, locale, tx?, options?)` / `publishReceipts(receipts, locale, options?)`; per-call injection seam `NotificationEngineCallOptions { transport?, cache? }` (the 4th-arg trailing options seam pinned by 2.2 §3c / 2.3 CA-2 — planned §4.1 two- and three-arg call shapes stay valid for production callers). Transaction composition is the DEV1-002 `withTransaction(outerTx)` SAVEPOINT pattern, byte-faithful to the `registration.service.ts` precedent: `outerTx` provided → `outerTx.transaction(fn)` (SAVEPOINT; the caller's unit stays usable); `undefined` → `db.transaction(fn)` (the engine's OWN commit — the function resolves only once committed, which makes the publish-after-commit ordering provable from code structure: no publish line is reachable before the `withTransaction` await resolves). Caller-tx path returns a `NotificationDeliveryReceipt` WITHOUT publishing (the caller's post-commit step is `publishReceipts`); own-commit path stores the receipt (when a cache is injected), then publishes exactly ONE `publishFanout` carrying the FULL recipient list (batch = one publish, REQ-013), payload projected field-by-field from the representative first row with `userId` excluded by construction (REQ-021). ONE `new Date()` captured per batch before the insert unit (REQ-047). `publishReceipts` sweeps receipts strictly IN ORDER via an index-recursive helper (no await-in-loop), one publish per receipt; every publish failure — own-commit, `publishReceipts`, AND default-transport resolution — degrades to exactly one `logger.logDomainError` with `{ code: "NOTIFICATION_DELIVERY_DEGRADED", entity: "notifications" }` and RESOLVES (REQ-011/043). The DEFAULT transport resolves ONCE per process through the 2.5 factory (single-slot bounded promise memo — the module's only state, per 2.5's BINDING "resolve ONCE at the engine's own seam"); the claim cache has NO default. i18n via `getServerTranslations(locale).errorsTranslations` (property access); `title`/`body` cross the engine VERBATIM — zero translation, zero templating, zero mutation (REQ-015/028).
- **`notification-engine.emit.test.ts`** — 33 tests / 288 expects / 9 describes (§5).
- **`index.ts` (namespace barrel)** — `export * from "./notification-engine.service"` added ahead of `./realtime` (alphabetical). `backend/services/index.ts` still deliberately NOT extended (2.5 D-5 — heavy/leaf-namespace precedent; the engine transitively carries the ioredis-carrying factory).

## 9. Deviations

- **D-1 — The journey-RED-window tsgo profile MUTATED (expected, documented):** baseline was 2×TS2307 ("Cannot find module '@/backend/services/notifications/notification-engine.service'") confined to `test/workflows/notifications/**`. - **D-2 — Claim-key recipe generalizes `userId` to the normalized recipient SET:** plan §4.1/REQ-016 write `notif:emit:<sha256(userId:type:key)>` (the single-recipient case). For `emitForUsers` the emission identity is the cohort, so the digest input is `<sorted ids joined by ,>:<type>:<key>` — for one recipient this reduces to the spec's exact recipe. Sorting makes replay order-insensitive; a different cohort under the same key claims separately (J2 step-7/8 semantics + the recipe-pin tests).
- **D-3 — `getServerTranslations(locale)` is called with ONE argument:** the task text's `getServerTranslations(locale, "errors")` does not match the shipped signature (`shared/locale/server-graphql.ts` accepts only `locale`); the errors namespace is reached by property access `.errorsTranslations` per the 1.3/1.4 flat-errors ruling (codebase ground truth over doc text — the same stale-notation lesson as 1.3).
- **D-4 — `emitForUser` returns the ROW on the own-commit path and a RECEIPT on the caller-tx path:** plan §4.1's declared union `Promise<NotificationReturnType | NotificationDeliveryReceipt>`; 2.2 §3 explicitly allows either shape per path (the journey narrows structurally). The asymmetry is intentional: keyless own-commit emitters want the created row; tx-owning emitters need the receipt handle.
- **D-5 — One bounded module-state memo (the default-transport promise):** the task's "cache adapter INJECTED (no module state)" is honored literally for the CACHE (no default, no module state). The DEFAULT TRANSPORT is memoized in a single-slot promise because 2.5's BINDING mandates resolving it ONCE per process at the engine's seam (per-emit resolution would construct a fresh ioredis client + TCP connection per emission). Tests always inject their own transport; the memo is exercised only by the hermetic factory-default test.
- **D-6 — Batch validation also rejects DUPLICATE recipient ids:** not in the plan's explicit rule list, but a duplicated cohort member would receive byte-identical sibling rows from the one multi-row insert — a caller bug, rejected pre-DB (documented in `emit-validation.ts`).
- **D-7 — Receipts are stored post-commit ONLY on the own-commit path:** the caller-tx path takes the CLAIM pre-insert but never STORES the receipt (the caller owns the commit decision; a stored pre-commit receipt could outlive a rolled-back emission and ghost future replays into returning nonexistent rows). Store failures degrade warn-only.
- **D-8 — `relatedEntityType` ≤100 bound added:** schema-faithful (`varchar(100)`) — the plan lists only "non-empty"; the bound prevents a post-validation DB truncation error.
- **D-9 — Validation reuses the GENERIC errors-namespace `validation` key:** the errors namespace ships no emit-specific keys (adding one would touch every locale + parity suites — out of 2.6 scope); the generic copy is the established pattern for service-side input guards.
