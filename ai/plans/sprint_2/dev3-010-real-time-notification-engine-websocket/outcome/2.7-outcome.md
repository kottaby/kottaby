## 1. What Was Built

**The `NotificationEngine` INBOX surface** — four methods appended inside the existing `export namespace NotificationEngine` block (2.6's emit code byte-untouched apart from two import lines + the file header sentence):

- **`listMyNotifications(userId, filter, locale, tx?)`** — the ONLY list surface for notification rows. Input hardening (REQ-054) runs BEFORE any DB access: `limit` must be a safe integer in `[1, 50]` (defaults to **20** when absent or null at runtime — the GraphQL nullable-Int shape), `offset` a non-negative safe integer (defaults to **0**), `type` through the fail-closed `isNotificationType` enum guard, `isRead` a boolean when present. Delegates to `NotificationRepository.listForUser` + `countForUser` (the 2.4 shared predicate builder — REQ-026 coherence by construction) and wraps `{ items, totalCount, hasMore }` with `hasMore = offset + items.length < totalCount`.
- **`getMyUnreadCount(userId, locale, tx?)`** — the badge read; `NotificationRepository.countUnread` (the `(user_id, is_read)` composite-index read, REQ-018).
- **`markRead(callerUserId, notificationId, locale, tx?)`** — the one-directional read latch (REQ-019/029). `notificationId` passes the shared `isPositiveSafeInt` guard (reused from `emit-validation.ts` — 2.6 BINDING honored) BEFORE any DB access; `markReadOnce → null` maps to `NotFoundError("NOTIFICATION", t.notificationNotFound)` after exactly ONE structured `logger.logDomainError({ code: "NOTIFICATION_NOT_FOUND", entity: "notifications", entityId, locale })`; an already-read row returns unchanged (idempotent).
- **`markAllRead(callerUserId, type, locale, tx?)`** — single set-based sweep via `markAllReadForUser`; returns the affected-row count verbatim; `0` on an empty matching set; the optional `type` filter runs through the enum guard (defense-in-depth).

**Identity = the `callerUserId`/`userId` parameter ONLY** (resolvers will pass the verified `ctx.user.id`); no inbox method accepts identity from any input object — the filter carries `type`/`isRead`/`limit`/`offset` exclusively (REQ-030).

Module-scope additions (all runtime, zero type definitions per `backend/services/AGENTS.md`): `NOTIFICATION_ENTITY` (the NotFoundError entity name — entity only, never the full code), exported page-window constants `NOTIFICATION_INBOX_DEFAULT_PAGE_LIMIT = 20` / `NOTIFICATION_INBOX_MAX_PAGE_LIMIT = 50` (single source of truth for 3.2's resolver JSDoc/input docs), the `InboxWindowView` runtime-widened read of the filter's window fields, and three fail-closed validation helpers (`validateInboxUserId`, `validateOptionalNotificationType`, `resolveInboxListRequest`).

Validating the caller id on ALL four methods is the consistent ID-channel discipline (resolvers pass a verified id, so a non-positive id can only be a caller bug — fail-closed beats a confusing empty page / 0). Journeys pass real ids, so nothing shifts.
- **D-2 — The page-window defaults are applied at RUNTIME through a widened view (`InboxWindowView`), not by widening the canonical type:** `NotificationListFilterInput` (1.1, binding) marks `limit`/`offset` required, but plan §3.2 mandates "default 20 when `null`" for the GraphQL nullable-Int input. The engine therefore reads the two fields through an `unknown`-typed runtime view and applies `?? 20` / `?? 0` — the static type stays untouched, the runtime contract is served, and whatever value IS present still passes the bounds validation. `undefined` and "absent" behave identically (only `??` is used).
- **D-3 — `isRead` gets a boolean guard (not in the plan's enumerated hardening list):** a hostile non-boolean `isRead` would otherwise flow into the shared predicate's `eq()` bind and surface as an opaque driver error; fail-closed `ValidationError` is cheaper and consistent with REQ-054's spirit.
- **D-4 — Inbox methods accept `tx?: DBTransaction` LAST (no options parameter):** plan §4.1's general "every method takes `tx?` last" rule, applied to the 3-arg binding signatures from 2.3-outcome CA-1 (optional trailing parameter — every journey call shape stays valid). No `options` seam: the inbox surface never touches a transport or the claim cache, so an options parameter would be dead surface area.
- **D-5 — `markRead`'s not-found denial logs ONE structured domain error before throwing:** follows the `applicant-lifecycle.service.ts` precedent (log `{ code, entity, entityId, locale }` → throw the translated `NotFoundError`); the task's SR item explicitly requires the `logger.logDomainError` shape. Validation failures do NOT log (mirroring `emit-validation.ts` — expected rejections that the caller is about to receive as a `DomainError` need no separate warn; only the enumerated domain denial logs).
- **D-6 — The interleave test's determinism rests on documented client-FIFO serialization:** `Promise.allSettled([markAll, emit])` on ONE transaction serializes as UPDATE-then-INSERT (the sweep's statement is submitted synchronously; the emit's insert is deferred behind its claim-await microtask) — the pinned "new row stays unread" outcome is therefore deterministic, and the sequential companion case pins the opposite ordering. This is the same single-client queuing the 2.4 repo storm tests rely on.
- **D-7 — `listMyNotifications` issues list and count as two independent reads when no `tx` is supplied** (each takes the repo's Neon-HTTP fast path): plan §4.4 classifies these as statistical reads (no follow-on write, no window), and REQ-026's coherence is guaranteed by the shared predicate, not by a snapshot. Callers needing a snapshot pass `tx`.
