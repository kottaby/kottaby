# Task 5.5 — Ngrok callback channel + intention URL wiring — Outcome

## Summary

Landed the development tunnel delivery path and closed the intention-URL seam. The ngrok callback
channel (`NgrokCallbackChannel`) spawns the ngrok agent (`ngrok http --url="https://<domain>"
<port>` — the documented flag; `--domain` is deprecated), verifies readiness by probing the PUBLIC
domain's health surface (`https://<domain>/api/health`, 2xx/3xx accepted) — never the local agent
API, whose loopback port may belong to another agent — and retries the probe until the readiness
budget (the paymob HTTP timeout) elapses before surfacing a typed unreachable error. The authtoken
reaches the agent through the child process environment, never the command line and never a log
line or error message (agent output is discarded outright), and the channel registers a
process-exit cleanup that kills the spawned agent. Delivery reuses the simulation channel's
synthesis builder (`buildSimulatedProcessedCallback` — the production signer path), so test
deliveries carry the exact wire shape a real provider delivery takes, POSTed through the tunnel
with `?hmac=<digest>` to the public webhook surface. A fail-closed runtime guard in both public
methods throws if the channel is ever invoked in a production runtime.

The factory's acquisition seam now constructs the channel and verifies its FULL readiness sequence
(eligibility keys + probe), translating a failed sequence into the simulation fallback with the
named reason `ngrok-unreachable` and one structured info log whose `detail` carries the tunnel's
own error message (never the authtoken). A dev-only `configureCallbackChannelTestDelivery()` seam
captures injectable spawn/transport/cleanup stand-ins (consumed once at channel construction,
dropped by `resetCallbackChannel()`, production-guarded with the same
`PAYMENT_CALLBACK_TEST_DELIVERY_UNSUPPORTED` code as the real channel's test-delivery rejection) —
the seam that lets the suites drive the tunnel channel offline. The adapter's `resolveCallbackUrls`
now consumes the resolved channel's `publicBaseUrl` through `getCallbackChannel()` — the ONE
channel resolver (REQ-090; no per-file tunnel check anywhere) — composing `notification_url` and
`redirection_url` from the tunnel base when the `ngrok` channel is selected and omitting the
members when the resolved channel carries no public base (`real`/`simulation`; the vendor then
falls back to the operator-configured dashboard URL).

## Semantic review checklist (5.5.SR)

- **No dead branches**: both fallback reasons are produced and asserted by distinct env states
  (`ngrok-not-configured`: keys absent/partial; `ngrok-unreachable`: probe failure); the ngrok
  selection, idempotent readiness, and every channel error path (spawn failure, probe timeout,
  non-2xx probe, delivery rejection, production guard) are test-driven.
- **Zero module-level mutable state beyond the plan-specified singletons**: the channel's `agent`/
  `ready` fields are instance state (one instance per factory resolution, dropped by reset); the
  factory's `channel` + `testDeliverySeams` are the lazy-singleton/dev-seam cache, both dropped by
  `resetCallbackChannel()`. No clocks/randomness in production paths (the readiness deadline uses
  `Date.now()` — a timeout budget, not synthesized data).
- **Enums as value imports**: `PaymentGateway` stays a VALUE import (string-widened comparison
  idiom unchanged); `CallbackChannelKind` is the plan-specified string union (type-only import).
- **Env getters**: no new getters needed — the three keys already resolve through the typed
  `getEnvironmentConfig().ngrok` snapshot with `resetEnvironmentCache()` parity (pinned by
  `env.test.ts`); no consumer reads `NGROK_*` env directly (static source pin green).
- **No cross-layer imports**: channel → `paymob`-domain synthesis builder + `lib/errors` (same
  domain); factory → `lib/env`/`lib/logger`/`lib/errors` + the two channels; adapter → the factory
  (both backend services). No `@/shared` additions (no user-facing strings added — all channel
  errors are operator/dev-facing diagnostic messages on the established 5.4 pattern).
- **NO per-file ngrok checks**: `process.env.NGROK` appears nowhere outside `backend/lib/env.ts`;
  the factory is the only consumer of the ngrok config (the adapter consults the channel's
  `publicBaseUrl`, never the env keys).
- **NO plan-meta in code**: grep-pinned zero REQ/task/plan references in comments or JSDoc.
- **No hardcoded fake data**: probe URLs compose from the configured domain; spawn commands compose
  from config; test fixtures use obviously-fake values (`.ngrok.app`, `adapter-test-*`).

## Security audit (5.5.SEC)

- **Authtoken never logged**: the token reaches the agent through the child process environment
  (never the command line — process listings cannot leak it; never a log line or error message —
  agent stdout/stderr are discarded; the fallback log's `detail` carries only the channel's own
  error message, and the suite pins the token appears nowhere in the log call). It is also not
  added to `NEXT_PUBLIC_*` or any client-reachable surface.
- **Ngrok channel unreachable in production**: the factory never resolves it there
  (`isProductionRuntime() ⇒ real`, pinned), the channel's `assertDevelopmentRuntime()` guard throws
  `PAYMENT_CALLBACK_NGROK_DISABLED` from BOTH public methods before any transport call, and the
  new dev-only `configureCallbackChannelTestDelivery()` seam is production-guarded with
  `PAYMENT_CALLBACK_TEST_DELIVERY_UNSUPPORTED` — a production process cannot even arm the tunnel
  seams, let alone resolve the channel.
- **Probe hits the public URL only**: pinned to exactly `https://<domain>/api/health`; the local
  agent API (loopback 4040/4041) is never contacted.
- **No network in tests**: every suite runs offline — the spawn/transport/cleanup seams are
  injected stand-ins; no real ngrok binary, domain, or API call is involved.
- **BOLA/BOPLA/BFLA**: no data access in this tier (no DB, no user context); the channel surface is
  dev-only tooling with no tenancy identity, so IDOR/BFLA classes do not apply; the production
  guards above are the abuse boundary.
