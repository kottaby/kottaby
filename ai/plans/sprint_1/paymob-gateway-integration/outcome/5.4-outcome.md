# Task 5.4 — Callback channel factory + simulation channel — Outcome

## Summary

Landed the single source of truth for how a provider callback reaches the webhook receiver outside production (D14): `CallbackChannelPort` + `CallbackChannelKind` in the typed billing layer, a lazy `getCallbackChannel()` factory mirroring the payment-gateway factory's singleton/reset shape, and the FULLY implemented simulation channel — the offline development default. The factory resolves `real` for a production runtime or any non-paymob deployment (null public base, no-op readiness, fail-closed test delivery); in development with paymob active it consults the tunnel acquisition seam — the ONE place tunnel configuration is read (through the typed env snapshot, never raw `process.env`) — and otherwise resolves `simulation` with exactly ONE structured info log naming the fallback reason (`ngrok-not-configured` / `ngrok-channel-unavailable`). The ngrok channel CLASS is the next task's file: the seam is structured so it drops in without touching any other resolution rule (see the seam ruling below).

The simulation channel synthesizes Paymob-shaped processed callbacks (nested `obj`, every one of the twenty documented signed members, `order.merchant_order_id` echoing the delivery reference) and signs them with the PRODUCTION `buildTransactionHmacMessage` builder under the configured `PAYMOB_HMAC_SECRET` — no parallel signer — then POSTs `?hmac=<digest>` to the local webhook surface: the exact wire shape a real delivery takes. Synthesis is deterministic (no clock, no randomness): identical arguments produce byte-identical bodies and signatures, so replay scenarios reproduce true duplicate deliveries, while distinct references derive distinct transaction ids. Confirm/fail map onto the transaction flags; cross-user scenarios deliver each payment's own reference. A fail-closed runtime guard inside BOTH public methods throws in a production runtime before any transport call, and an unconfigured HMAC secret fails delivery closed with a typed `SERVICE_UNAVAILABLE` instead of signing under an empty key. The channel's outbound transport is injectable (the provider HTTP client's established seam), which is what lets the end-to-end suite dispatch the channel's actual wire request straight into the REAL route handler.

## Security audit (5.4.SEC)

- **Simulation unreachable in production:** factory resolution rule (production ⇒ real) + in-channel fail-closed guard, both test-pinned; the real channel's `deliverTestCallback` throws `PAYMENT_CALLBACK_TEST_DELIVERY_UNSUPPORTED`, so no production caller can synthesize settlements through ANY channel.
- **Signer reuse (no drift):** exactly one HMAC message implementation is involved — the production `buildTransactionHmacMessage`; pinned by independent-oracle agreement AND by the real-route gate accepting the produced deliveries.
- **Secret hygiene:** the HMAC secret flows constructor-injected from the typed env snapshot (the channel never reads the environment); an absent secret fails closed (`SERVICE_UNAVAILABLE`) instead of signing under an empty key; no secret material ever appears in a log line or error message (fallback log carries only the reason string; delivery errors carry only the URL/status).
- **No network in tests:** all three suites run offline — the channel's injectable transport records/dispatches locally; the end-to-end suite's transport invokes the route handler in-process.
