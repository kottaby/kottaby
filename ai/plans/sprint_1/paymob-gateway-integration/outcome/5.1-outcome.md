# Task 5.1 — Reconcile service — Outcome

## Summary

Landed the reconciliation backstop: `reconcilePendingPaymobPayments({ now, batchLimit })` in `backend/services/billing/payment-gateway/paymob/paymob.reconcile.ts`. The sweep gates on the active provider + the server-to-server API key (anything else answers a zero-count result with exactly one informational skip line — never an error), pulls the stale-pending batch through the 2.2 repo finder `findStalePendingByGateway(PaymentGateway.Paymob, olderThan, limit)` with `olderThan = now − getPaymobConfig().reconcilePendingMinutes` (default 30 min), and resolves each row independently: `PaymobHttpClient.transactionInquiryByMerchantRef(row.paymentReference)` (a fresh auth token minted per inquiry inside the client — never cached), then the terminal inquiry is mapped to the SAME verified-event shape the webhook parser produces and handed to `SubscriptionActivationService.processWebhookEvent(event, "en")` — no bespoke update anywhere, so the guarded decision, lane crediting, provider-reference recording (NULL→value inside the guarded statement), keyed notification dedupe, and replay semantics are byte-identical to the callback path. The batch is bounded (default ceiling 50, explicit smaller limits honored, oversized/non-positive clamped), the walk is head-first sequential (the codebase's recursive sweep-helper shape — one row settles completely before the next is touched), and every row's outcome lands in one log line carrying correlation ids only. Rows whose inquiry is still in flight, whose last transaction is a reversal/child variant (the same verified-then-ignored variants the webhook dispatch never settles), whose reference is missing, or whose inquiry is provider-unavailable stay pending for a later sweep — the backstop never terminates an in-flight purchase. A provider-unavailability rejection skips only its own row; a non-upstream error (infrastructure breach inside the transport or the activation surface) propagates and aborts the run for the cron caller to report.

Result counters: `{ checked, confirmed, failed, skipped }` with the invariant `checked = confirmed + failed + skipped` — `confirmed`/`failed` count only handoffs the activation surface APPLIED (`processed: true`, replays included — the earlier delivery settled them); refused handoffs (unknown reference, settlement quarantine — the service mutated nothing and logged its own reason) count as `skipped`.

One design decision worth flagging for review: the inquiry path consumes exactly three config members (API key, API base host, per-attempt timeout) and its gate is the API key ALONE, but `PaymobHttpClient`'s constructor demands the full `PaymobResolvedConfig`. Rather than widening the landed 3.3 type (which would force fail-closed guards on members the checkout path type-guarantees — dead branches), the sweep's private `resolveInquiryConfig` fills the checkout-only members with resolved-or-inert values (`""`/`0`) the inquiry path provably never reads; the suite pins that no checkout credential ever reaches the wire on this path (mint body = `{api_key}` only, inquiry body = `{auth_token, merchant_order_id}` only, headers = `Content-Type` only — no `Authorization` header).

## Semantic review checklist (5.1.SR)

- **No read-then-write without atomicity:** the sweep holds ZERO write paths — its single read (`findStalePendingByGateway`, a non-transactional `queryDb` bare read per the repo AGENTS rule) selects the batch, and every state decision flows through the activation surface's guarded single-statement writers. The only "writes" in the module are the in-memory per-run tally, threaded immutably through the recursive walk.
- **No module-level mutable state:** the module's top level holds four `const` primitives and functions only; the client is constructed per sweep invocation and holds nothing between calls; auth tokens are minted per inquiry inside the client and never retained (the 1-hour vendor TTL makes retention stale shared state). The test file's `originalEnv` snapshot and `trackedRestores` registry are the suite-side restore fixtures (the adapter suite's established env-fixture pattern, bounded and drained per test).
- **No dead branches:** every branch in the implementation is exercised by the suite — gating's two legs (provider, API key absent/blank), the batch-limit default/honor/clamp/floor arms, the missing-reference skip, the upstream-error skip vs the non-upstream rethrow, the reversal/child skip, the in-flight skip, terminal success vs decline, the refused vs replayed handoff, and the resolved-or-inert config fallbacks (the API-key-alone gating test runs the sweep with every checkout credential absent — the fallback arms of `resolveInquiryConfig` are live, and the wire assertions prove the inert values never reach the network).
- **No cross-layer imports:** the module imports `@/backend/db/repo` (service→repo read — the standard flow; the repo's single-writer discipline governs writes, which the sweep never performs), `@/backend/enum`, `@/backend/lib/{env,logger}`, the sibling paymob HTTP module, the billing activation service (the plan-mandated handoff — both live under the billing domain), and `@/backend/types`. No `app/`, GraphQL, or frontend imports; no fetch of anything beyond the vendor's auth/inquiry endpoints (inside the reused client).
- **Enum value imports:** `PaymentGateway` is a VALUE import in both files (the finder's first argument is the runtime enum member; `PAYMOB_PROVIDER_VALUE` widens it to string for the env comparison — the webhook route's landed pattern); `PaymentStatus` is a value import in the suite's row fixtures. Type-only members (`StalePendingPaymentWithReferenceRow`, `PaymentWebhookEvent`, `PaymobTransactionInquiryResult`, `PaymobResolvedConfig`, `PaymobFetch`) use `type` imports.
- **Scope = only the 2 new files** (+ zero modifications — `git status` clean apart from the two additions before the stage-1 commit).
- **Clean comments:** plan-meta grep zero matches (above); every docblock describes the contract (gating semantics, walk discipline, event-shape identity, inert-member rationale), not the task that produced it.
- **Inquiry token never logged (5.1.SEC, test-pinned):** the sweep's only log sites are the gating skip line (`provider` + `apiKeyConfigured` boolean — never the key itself), the per-row outcome line (paymentId/reference/outcome/detail), and the completion tally; the transport's own failure lines are the landed sanitized endpoint+status pairs. The suite spies ALL five logger levels over a mixed batch (settled, in-flight, reference-less, inquiry-unavailable — every log site fires, including the client's `logDomainError` upstream line) and asserts the minted-token and API-key sentinels never appear in any serialized call. The API key also never enters the wire except the mint body where the vendor requires it.
- **No token caching (D7):** `transactionInquiryByMerchantRef` mints per call (the 3.3 client's own design); the sweep adds no retention layer. Test-pinned: 2 rows ⇒ exactly 2 token mints, each inquiry body carrying the freshly minted token.
- **Race conditions / env getters:** configuration is re-resolved per sweep invocation through the registered typed getters (a provider or key flip is observable on the next run without a restart); per-row decisions are serialized head-first, and concurrent sweeps converge through the activation surface's guarded transitions exactly like concurrent callbacks (the 4.2 arbitration) — a replayed handoff is counted applied and mutates nothing.
