## Summary

- The payment-result page landed: a server-component shell at `app/(dashboard)/student/checkout/result/page.tsx` (`withPageAuth({ roles: [UserRole.Student] })`, `generateMetadata` from the locale cookie, `await searchParams` per the Next.js 16 promise contract) wrapping a `"use client"` orchestrator that re-queries `mySubscriptions` through the task-7.1 generated document — **zero trust in query params**, per the REQ-027 display-only ruling.
- **The trust boundary** (the task's core contract): the success arm is gated EXCLUSIVELY on the authoritative re-query returning an ACTIVE `StudentSubscription` row. A forged `?success=true` with no server truth renders the pending arm — never success (test-pinned across BOTH locales, branches 8/9). The hint record's ONLY consumption is `hintsIndicateDecline`: inside the pending row's negative zone, a decline redirect (`success=false`) downgrades the display to the failed arm's guidance copy. The hints can DOWNGRADE inside the negative zone — never elevate anything to positive.
- **The failed-arm refinement** (a design decision worth flagging): the generated `SubscriptionStatus` has NO `Failed` member — a failed purchase leaves the subscription row `Pending` with the payment unverified — and `paymentVerifiedAt === null` is true for BOTH pending and failed purchases, so a payment-level-truth arm decision cannot distinguish them from the query payload alone. The failed arm therefore rides the display-only decline hint (`success=false`), exactly the REQ-027 "hints" role: server truth (the pending row) still gates that the student sees NO positive state, and the hint only refines WHICH non-positive guidance copy renders.
- View decomposition (all `< 150` lines, the max-lines lint limit): `PaymentResultContainer.tsx` (orchestrator + checking arm), `ResultArmBody.tsx` (the per-arm summary panel + CTAs), `ResultSummaryRows.tsx` (label/value rows), `resultPresentation.ts` (pure type→presentation maps + the arm resolver), `resultRoutes.ts` (route constants), `resultViewIds.ts` (testids).

## Semantic review checklist (7.3.SR)

- **No dead branches:** every arm (checking / permission-fallback / generic-error / success / pending / failed) and every hint branch (decline, pending-override, forged-true, forged-over-zero-rows) is test-exercised in BOTH locales; the zero-rows and pending-row arms are separately pinned.
- **No module-level mutable state:** all view modules hold `const` primitives/functions and immutable lookup tables (`Record` maps, never mutated); the container holds no refs, no module state.
- **Enums as values:** `SubscriptionStatus` is imported as a VALUE from the codegen output in `resultPresentation.ts` (the arm decision + the exhaustive chip table); no string literals for enum values anywhere.
- **No cross-layer imports:** view imports are `@/frontend/**` (graphql documents, generated types, sibling views, shared UI, providers), `@/shared/locale/**`, `next/*`, `@mui/*` — the established client set; the server page imports `@/backend/enum/users/user-role.enum` (the page-level `UserRole` precedent) + `@/frontend/**` + `@/shared/locale/**`. `shared/` was never imported INTO.
- **No plan-meta in code:** grep-pinned zero (above).
- **No hardcoded fake data:** all copy resolves through `useAppTranslation(Checkout)` property access; all wire values render straight from the `mySubscriptions` payload; fixtures (test/story files only) are declared test DATA, never consumed by production code.
- **MUI v9 / theme:** `sx`-only styling; colors exclusively through `theme.palette.*` callbacks (`successContainer`/`onSuccessContainer`/`warningContainer`/`onWarningContainer`/`errorContainer`/`onErrorContainer`/`divider`/`text.*`); `*Outlined` icon discipline (no icons needed — the checking arm uses `CircularProgress`); reduced motion honored (no transitions mounted); Money rendering stays out of this surface (the row's `amount` is not in the selection set; the localized-EGP rule is owned by the subscriptions list).
- **Zero trust re-verified:** `hintsIndicateDecline` can only return `true`/`false` for the negative-zone refinement; `resolveResultArm` returns `"success"` ONLY on `SubscriptionStatus.Active` — the forged-hint tests prove no positive render is reachable from query params alone.

- **Student-scoped (BOLA/BOPLA/BFLA):** the server guard is the only authz boundary (`withPageAuth({ roles: [UserRole.Student] })`; anonymous → `/login?redirect=/student/checkout/result`; role mismatch → own role dashboard). - **Zero trust in query params (the task's .SEC bullet):** the forged `?success=true` probes are test-pinned to render NOTHING positive without server truth (branches 8/9, both locales).
