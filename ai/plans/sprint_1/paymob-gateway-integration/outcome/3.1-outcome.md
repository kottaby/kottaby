# Task 3.1 — Paymob HMAC verification module — Outcome

## Summary

Landed the Paymob callback HMAC trust boundary as three new pure-function files: the vendor's documented HMAC key lists (`paymob.constants.ts`), the message builders + `verifyPaymobHmac` (`paymob.hmac.ts`), and a colocated golden/tamper vector suite (`__tests__/paymob.hmac.test.ts`). The builders reproduce the provider's signed message exactly for all three callback shapes (processed POST transaction, flat GET response redirect, card-token POST), and verification compares the SHA-512 hex HMAC through the fixed-length SHA-256 digest idiom (cron `bearerSecretMatches` / `webhook-signature.helpers` precedent) — length-agnostic, timing-safe, never throwing on attacker-controlled input. Key lists were transcribed from the offline vendor mirror (not from plan approximations), and the transaction list was reconciled against the mirror's own worked example: **20 signed slots** (with the `pending` slot empty in the vendor sample, proving the missing→empty-string rule).

## Files created

- `backend/services/billing/payment-gateway/paymob/paymob.constants.ts` — `PAYMOB_TXN_HMAC_KEYS_POST` (20 getter paths, nested shape), `PAYMOB_TXN_HMAC_KEYS_GET` (20 flat parameter names; differs from POST only at the order-id slot: `order.id` → `order_id`), `PAYMOB_TOKEN_HMAC_KEYS` (8). Each entry is a getter path relative to the object being signed; the transaction's own identity member appears as `id` (the vendor writes it `obj.id` because its list is framed on the whole callback body).
- `backend/services/billing/payment-gateway/paymob/paymob.hmac.ts` — pure functions, no I/O, no env reads, no logging, no module state; secret always passed in: `buildTransactionHmacMessage(source: PaymobProcessedCallbackBody["obj"])`, `buildTransactionHmacMessageFromQuery(query: Record<string, string | undefined>)` (order-id slot prefers `order`, falls back to `order_id` — the vendor's pages use both flat names), `buildTokenHmacMessage(obj: PaymobTokenCallbackBody["obj"])`, `verifyPaymobHmac(message, providedHmac: string | undefined, hmacSecret)`. Serialization: booleans lowercase `true`/`false`, numbers/strings plain, absent values → empty string (an absent member still consumes its slot — the message is position-sensitive). Vendor types imported type-only from `@/backend/types` (the A-set DTOs from 2.3).
- `backend/services/billing/payment-gateway/paymob/__tests__/paymob.hmac.test.ts` — 23 tests / 50 `expect()`: constants pinned verbatim; golden vectors with the expected message written out slot-by-slot in the test (POST success, POST declined/pending, GET via `order`, GET via `order_id` fallback, `order`-wins precedence, token); tamper vectors (flipped `success`, altered `amount_cents`, missing documented key, wrong secret both directions, missing/empty `hmac`, empty secret, whitespace in message and in the presented digest, uppercase hex re-encoding) each denied while the honestly-signed twin of the same payload verifies; unsigned-member proofs (`is_refund`/`is_void`/`refunded_amount_cents`/`captured_amount`/`order.merchant_order_id`/token extras never influence the message); digest-comparison shape (wrong-length and same-length-wrong-value presented HMACs denied without throwing, deterministic).

Files NOT modified: `backend/types/billing/paymob.types.ts` and the 2.3 static-assertions suite (key lists in code now carry the runtime truth the static suite anticipated; no pin changes needed), webhook route (task 4.1 owns the branch), everything else. Scope boundary: exactly the three new files.

## Security (3.1.SEC)

- Constant-time comparison: `verifyPaymobHmac` hashes both the presented and the expected hex string to fixed-length SHA-256 digests and compares with `timingSafeEqual` — no length-dependent early exit (wrong-length and same-length-wrong-value probes both denied, test-pinned), following `bearerSecretMatches` (`app/api/cron/sweep-sessions/route.ts:66-73`) and `webhook-signature.helpers.ts`.
- Fail-closed: missing/empty presented HMAC → `false`; empty secret → `false`; no exception path on attacker-controlled input.
- No secrets logged: zero `console.*`/`logger` references in all three files; the secret exists only as a function parameter.

## Carry-forward knowledge (for later tasks)

- 3.2 (`mapCallbackToEvent`) consumes the POST builder shape but NOT the HMAC module itself; 3.3 (`parseWebhookEvent`) is the caller: build message via `buildTransactionHmacMessage(body.obj)` (or token builder for token-shaped payloads), then `verifyPaymobHmac(message, input.query["hmac"], config.hmacSecret)` — the `hmac` value always arrives in the QUERY for both POST and GET deliveries.
- 4.1 route: on verify failure → 401, zero state; TOKEN/refund/void shapes are verified then ignored (null → 200 no-op envelope already landed in 2.3).
- 5.4 simulation channel signs synthetic payloads with `buildTransactionHmacMessage` + `createHmac("sha512", PAYMOB_HMAC_SECRET)` — no parallel signer.
- Digest compare is case-sensitive lowercase hex; the vendor's sample digests are lowercase — no normalization added (uppercase hex is denied by design, test-pinned).
- Serialization rules for any future signer: booleans lowercase, numbers plain decimal, missing → empty string; `pending` may legitimately be absent on completed transactions (the vendor's own sample concatenation shows an empty slot there).
