# Task 3.3 — Paymob HTTP client + gateway adapter — Outcome

## Summary

Landed the outbound transport boundary and the `paymob` provider behind the `PaymentGatewayPort`. `paymob.http.ts` is a stateless `PaymobHttpClient` over two injected dependencies (the resolved provider config and a fetch-like `PaymobFetch` seam — production rides the platform fetch, tests inject a recorder): every attempt runs under a per-attempt `AbortSignal.timeout` sized from the configured budget; retries are bounded (3 attempts total, 100 ms pause) and granted only to failures that provably produced no provider side effect (no-response transport rejection, 5xx); a timed-out request is NEVER retried (it was delivered — its state is unknown and belongs to the reconciliation sweep) and neither is a 4xx or an unusable 2xx body; failures surface as typed sanitized errors carrying the upstream status (or `null`) with fixed generic messages — upstream body content never enters an error message — and each failed attempt logs exactly one sanitized line (endpoint + status). Responses are presence/type-checked before the typed DTO is built so a missing contract member fails closed instead of flowing `undefined` into money paths. `paymob.adapter.ts` is `PaymobPaymentGateway`: it holds NOTHING between calls, re-resolving the provider config fail-closed on every operation (`requirePaymobConfig` → `DomainError("SERVICE_UNAVAILABLE", "Payment gateway is not configured.")`), `createCheckout` builds the intention from the server-derived input and returns the checkout descriptor whose reference is the correlation key (never the intention id), and `parseWebhookEvent` is the webhook trust boundary: JSON-parse + presented-`hmac` gate → dispatch by PAYLOAD SHAPE through five module helpers (transaction → verify with the 20-key list, then settle or verify-then-ignore refund/void/parent; card-token / `TOKEN`-typed → verify with the 8-key list then ignore; unknown nested shape → malformed, never guessed; no nested object → flat redirect verified over the flat query then ALWAYS ignored — display-only by ruling). The factory registers the adapter lazily exactly like mock (`[PaymentGateway.Paymob]: () => new PaymobPaymentGateway()`).

## Semantic review checklist

- Module state: the client and the adapter hold NOTHING between calls — a fresh client is built per provider call; auth tokens are minted per use and never cached (vendor expires hourly); config is re-resolved per operation, so a config change or per-request mode flip is observable without a restart; no secret or derived value is ever retained. The only module-level values in both files are constants.
- Dead branches: none — the QL loop caught the one real instance (helpers shadowed by an inlined dispatch) and it is now wired through; every remaining branch (all three delivery shapes, each rejection path, each retry-policy cell) is exercised by the suites.
- Cross-layer imports: backend `lib/env`, `lib/errors`, `lib/logger` + `@/backend/types` + `@/shared/locale/server-graphql` + sibling paymob modules only; no `app/`, DB, or GraphQL-layer imports; no fetch of anything outside the three vendor endpoints.
- Enum value imports: `PaymentGateway` is imported as a VALUE in the adapter (its `provider` member must equal the enum value the factory keys on — the same pattern as `MockPaymentGatewayAdapter`) and in the factory's lazy-registration map; no other enum imports.
- Secrets not logged: the only logging is `logUpstreamFailure(path, status, retrying)` — endpoint path + HTTP status + retry flag; the secret/API key/HMAC secret/token never appear in any log line or error; HMAC secret exists only as a `verifyPaymobHmac` parameter.
- Upstream body not leaked: all failure messages are fixed module constants ("Payment provider could not be reached." / "rejected the request." / "returned an unusable response." / "did not respond in time."); `PaymobUpstreamError` carries only the numeric status (or `null`); response bodies are validated then discarded — test-pinned that body text never reaches an error message.
- Scope: exactly the four new files + four modified files listed above; no route, schema, cron, or type-pin changes (4.1 owns the route branch).

## Carry-forward knowledge (for later tasks)

- Endpoints used (vendor mirror): intention `POST v1/intention/` (secret key via `Authorization: Token`); auth mint `POST api/auth/tokens` (API key in body); inquiry `POST api/ecommerce/orders/transaction_inquiry` (minted token in the request BODY).
- Retry rules: 3 attempts total, 100 ms pause, retries ONLY for no-response transport failures and 5xx; timed-out delivered requests are NEVER retried (unknown provider state → recovery is the 5.1 reconciliation sweep, not a second POST); 4xx and unusable 2xx bodies are terminal; budget exhaustion surfaces `PaymobUpstreamError` with `status: null` when no response ever arrived.
- `parseWebhookEvent` error-type mapping for 4.1 route dispatch: `UnauthorizedError` ("Invalid payment webhook signature.") → mask to 401; `ValidationError` code `PAYMENT_WEBHOOK_MALFORMED` with the localized validation message → 400-family; `DomainError` `SERVICE_UNAVAILABLE` → service-unavailable; `null` return → verified-but-ignored delivery, ack with the 2.3 no-op envelope; a returned `PaymentWebhookEvent` moves money state. The `hmac` always arrives in the QUERY for POST and GET deliveries alike.
- `itemName` sourcing: the adapter sends the locale-free module constant `CHECKOUT_ITEM_NAME = "Subscription"` (parser rejections use the deployment-default `GATEWAY_LOCALE = "en"`) — if per-plan display names are ever wanted, that constant is the single edit point.
- Callback URLs are optional by contract: with `NEXT_PUBLIC_BASE_URL` unset the intention omits `notification_url`/`redirection_url` and the vendor uses the merchant-dashboard callback URL; `resolveCallbackUrls` also trims trailing slashes from the origin.

## Cross-file dependencies

- 4.1 (webhook route): branch on the `paymob` provider, call `adapter.parseWebhookEvent({ rawBody, query })`, map per the error-type table above; the route must not re-verify HMAC or inspect the raw body itself.
- 5.1 (reconciliation sweep): reuses `PaymobHttpClient.transactionInquiryByMerchantRef(specialReference)` (fresh token per inquiry) to resolve unknown-state delivered intentions; the client's no-retry-on-timeout rule is what makes the sweep the single owner of unknown-state recovery.
