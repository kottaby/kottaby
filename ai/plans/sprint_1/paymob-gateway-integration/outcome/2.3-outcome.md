## Carry-forward knowledge (for later tasks)

- Vendor DTO field lists (3.2/3.3 mappers consume): intention request = `amount` (integer cents) / `currency` / `payment_methods: number[]` / `items[]{name,amount,description?,quantity?}` / `billing_data{11 members}` / `special_reference` / `notification_url?` / `redirection_url?`; response sanity subset = `id` (string) + `client_secret` + `special_reference` + `intention_order_id`; processed callback = `{ type?, obj: PaymobTransactionCallbackObj }` with `type` NOT guaranteed (dispatch on shape); response callback = flat optional string query params incl. `hmac`, `"source_data.*"`, `txn_response_code`; token callback = the 8 signed keys; inquiry result = reconciliation subset incl. `order.merchant_order_id`.
- `WebhookParseInput` contract + null semantics: adapters receive the exact received bytes (`rawBody`) + query record; return the verified event to settle, or null for verified-but-ignored variants (TOKEN/refund/void/unknown types); route acks null with `{ processed: false }` 200 (no `replayed` flag) so provider retries stop with zero state change. Mock never returns null.
- `specialReference` sourcing: it IS the purchase-claim idempotency key (≤128 chars, `isCarryableIdempotencyKey`-narrowed `string`), echoed back by Paymob as `order.merchant_order_id` — fulfillment (4.2) and reconciliation (5.1 `transactionInquiryByMerchantRef`) must resolve by it. The vendor docs state no length cap for `special_reference`; 128 fits the legacy `merchant_order_id` column tolerance, sandbox proof is already covered by the deferred QA row.
- Billing sourcing: `buildCheckoutBillingInput(studentUserId, t, tx?)` is the single server-side projection (real `fullName`/`email`/`phone`, phone nullable); the `"NA"` placeholder fill for Paymob's required `phone_number`/address members belongs to the 3.2 mapper (`buildIntentionRequest`), NOT to the domain port.
- `PaymobResolvedConfig` is the fail-closed narrowing target for 2.1's env config (nullable env members → concrete; wallet integration stays nullable by design — wallet deployments are an operator choice).
