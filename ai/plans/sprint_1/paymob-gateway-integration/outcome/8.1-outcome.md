## Summary

The journey landed as a single sequential, actor-attributed workflow file (8 tests / 114 expect calls) that drives the REAL purchase service through the REAL paymob provider branch and settles through the REAL webhook receiver, the REAL activation service, and the REAL notification persist path on the REAL test database.

**Harness architecture (the two seams):**

- **Purchase leg — one mocked hop.** `SubscriptionPurchaseService.purchase` resolves the gateway through `getPaymentGateway()`; the factory constructs `PaymobPaymentGateway()` with no transport override, so the adapter's default production delegate is the platform fetch. The journey spies `globalThis.fetch` with a recording fetch that (a) intercepts ONLY `https://accept.paymob.com/v1/intention/` (records url/headers/body, serves a validated intention response) and (b) passes EVERY other URL through to the real fetch. This is the fetch boundary the adapter's transport resolves to in production — the injected-boundary discipline at its landed default. The full `typeof fetch` (including the `preconnect` member) is satisfied so the spy stays a real, total dependency.
- **Callback leg — zero mocked hops.** The journey boots an in-process `Bun.serve` receiver on an ephemeral port (port 0), sets `NGROK_PORT` to its assigned port, resets both factories, and resolves the delivery channel through `getCallbackChannel()` — which resolves `simulation` (the development default; tunnel keys deliberately absent, no per-test tunnel logic anywhere). `channel.ensureReady()` probes the receiver's health surface; every settlement is delivered via `deliverTestCallback(...)`, which POSTs the production-signed `?hmac=` callback over a real loopback socket into the REAL `POST /api/payments/webhook` handler — the route's own HMAC gate IS the oracle, so the verification → parse → guarded-transition → credit → notification-persist chain is entirely production code.

**Journey arms (all green):**

1. **Happy-path purchase:** student A buys with `PAYMENT_GATEWAY_PROVIDER=paymob` — intention request pinned field-by-field (`Authorization: Token <secret>`, `amount` cents 20000, `special_reference` = the verbatim idempotency key, server-derived billing email, NO `notification_url`/`redirection_url` members on the simulation-channel path); pending pair + junction + verbatim claim commit; descriptor `{ paymob, key, checkoutUrl }` with the configured public key + client secret.
2. **Delivery + activation:** signed callback through the resolved channel → payment `paid` with `providerTransactionId` recorded (the guarded one-time NULL→value write), subscription `active` with `endDate − startDate = intervalDays` exactly and `paymentVerifiedAt` stamped, hifz lane credited the full sessionCount (tajweed byte-identical), ONE persisted `payment_confirmation` notification (copy composed in the recipient's persisted locale, pinned against the EN bundle), receipt published strictly post-commit addressed to Student A ONLY.
3. **Replay:** the SAME settlement args re-delivered (byte-identical callback by the channel's determinism) → no double credit, no second notification, no second publish, decided rows' statuses + `updatedAt` timestamps byte-identical.
4. **Bad HMAC:** a wrong-secret signature over the same args → masked 401 `UNAUTHORIZED`, zero state change (statuses, timestamps, balances, inbox, publishes all pinned).
5. **Flipped success flag:** the valid signed callback body with `success` flipped AFTER signing (stale signature) → masked 401, zero state change.
6. **Failure outcome:** fresh purchase + `{outcome: failed}` delivery → `pending→failed` with the provider reference recorded, subscription stays pending (no window, unverified), zero credit, the FAILURE notification persisted (failed copy pair) + published to Student A.
7. **Cross-user settlement:** student B purchases (own key, own plan) and its OWN reference settles B's pair (paid + provider reference + active + tajweed credit + notification + publish) while Student A's decided rows stay byte-identical and A's inbox count does not grow — the reference is the only lookup key, so a callback can never resolve onto another student's rows.
8. **Cross-user money quarantine:** a cleanly-verified callback for Student A's pending pair carrying the OTHER plan's price → settlement quarantine, `{processed:false}` ack (delivery resolves, never throws), Student A stays pending with the reference still NULL, zero credit, zero notification, zero publish, exactly ONE bounded quarantine log.

**Env discipline:** the journey saves/restores 10 env keys (`PAYMENT_WEBHOOK_ENABLED`, `PAYMENT_GATEWAY_PROVIDER`, 5 `PAYMOB_*`, `NGROK_PORT`, `NGROK_AUTHTOKEN`, `NGROK_DOMAIN`) and resets both factories (`resetPaymentGateway()` + `resetCallbackChannel()`) before resolution and after restore. Tunnel keys are deleted (not set) so the factory resolves the development default — no per-test ngrok branching anywhere (REQ-094 honored through the factory exactly as landed).
