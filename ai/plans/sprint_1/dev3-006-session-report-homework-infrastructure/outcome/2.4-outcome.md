## 3. 2.4.SEC — Security & Tenancy Audit

- **Wave-context reveal set = {student, teacher, linked parent of that student} — nothing broader:** the SELECT lists exactly `sessionId` + per-participant `id`/`full_name`/`locale` (10 columns). No governance flags, no emails, no balances, no handshake codes, no session notes. The parent leg is reachable ONLY through `students.parent_id` of the session's OWN student — a foreign/other parent can never appear (LEFT JOIN keyed on `st.parent_id`, and `st` is pinned to `s.student_id`).
- **Id-addressed only:** the single predicate is `s.id = $1` (bound). No caller-supplied participant data can widen the row set; `null` uniformly means session-not-found.
- **Locale columns are the ONLY per-recipient preference data** — present by design (REQ-018 copy composition happens in 2.6 from these values; `recipient.locale ?? defaultLocale` per 0.2 item 8).
- **Lock is read-for-gate — no write:** `lockForReportGate` performs a SELECT … FOR UPDATE; it writes nothing to `session` (grep: no `.set(` in the method). It serializes the caller's subsequent report/homework writes against other gate-locked writers (D2); escrow/lane columns are untouched by this surface (REQ-044 posture — plan §4.3 row 7).
- **No `*` select, bound parameters, no `--`, no `inArray`/`sql.raw`** — pinned by the suite's static tests and grep-verified.
- **Cross-tenant:** participant scoping is NOT this read's job (raw id-keyed read returning the gate quadruple/wave trio to the service); 2.7 gates the caller BEFORE the wave read (owner-only submit; participant-oracle reads) per plan §4.2's pipeline — the repo exposes no route that turns arbitrary ids into another student's parent beyond the one structural leg.
