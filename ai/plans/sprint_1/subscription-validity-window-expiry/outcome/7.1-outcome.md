## Lock-In Assertions Pinned (exactly what was pinned)

1. **Window delta (REQ-010)** — on a real activation (`intervalDays: 37`, a non-default value so the delta provably comes from the plan row): `end − start === plan.intervalDays * 86_400_000` **exactly** (both endpoints derive from the single in-transaction `now` — no sub-second noise, so the exact form is the honest strongest pin; the `86_400_000` literal mirrors the service's module-private `MS_PER_DAY` at `subscription-activation.service.ts:96`, deliberately not re-exported), **plus** the `secondPrecisionMs` form `secondPrecisionMs(end) − secondPrecisionMs(start) === intervalDays * 86_400_000` — a whole-day interval is a whole-second multiple, so the pin survives the second-resolution floor the journey fixtures rely on. Also pinned: `start ∈ [before, after]` (window anchored at the real activation instant) and `paymentVerifiedAt === startDate` (one captured `now`).
2. **Minimum interval (Tier 2)** — `intervalDays: 1` (the CHECK's `> 0` floor) passes the ceiling guard, activates, and yields a window of **exactly one day** (both delta forms).
3. **Leap-day-adjacent activation (Tier 2)** — honest wall-clock note: the flow reads `new Date()` internally (`subscription-activation.service.ts:360`); pinning `now` to a Feb-29 instant would require mocking the GLOBAL `Date` constructor shared by the whole engine stack (PGlite driver, Drizzle, entity helpers) — an intervention of the same grade as re-implementing the flow, so it was **not** done. Instead, per the task's primary instruction, the arithmetic is pinned via the **observed row timestamps of a real activation**: the delta assertion, plus a **cross-check against UTC calendar-field normalization** (`Date.UTC(y, m, day + intervalDays, h, ms…)` — the computation that actually knows about Feb 29, normalizing day-of-month overflow through month lengths and leap years). The service's epoch-ms arithmetic must equal the calendar landing for the observed instant; whenever a run's observed window spans a Feb 29 this IS the leap-day case, and since the two computation paths agree for every instant, the pin holds on every run regardless of host clock.
4. **`interval_days = 0` impossible by CHECK (REQ-012)** — DB-level probe inside `runInRollback`: control insert with the floor value `1` commits first, then `createTestPlan(tx, { intervalDays: 0 })` is caught via the `expectRepoError` try/catch helper (NEVER `.rejects.toThrow`) and asserted to be the **specific** constraint via `constraintNameOf(err) === "plans_interval_days_check"` (the violation probe is the last statement of its transaction — the 25P02 aborted-tx pattern of the sibling `plan-catalog-schema` suite, which pins the same CHECK from the catalog side). NULL is pinned by the **schema-definition introspection** (`getTableConfig(plans)` → `interval_days` column `.notNull === true`; a type-safe null insert is unreachable, so a DB null probe would be dishonest). Additional structural pin: `getTableConfig(subscriptions).columns` contains **no** interval column at all — `interval_days` is a PLANS-only column, so the window can only ever be computed from the activating plan row.
5. The `plans_interval_days_check` existence is double-pinned: live DB behavior (23514 probe) + drizzle table-config `checks` name list.
