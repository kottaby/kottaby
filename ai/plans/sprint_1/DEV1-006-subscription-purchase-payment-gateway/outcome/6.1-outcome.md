## Ordering decision (checkout vs plan read)

The plan row is read (active-only) BEFORE the gateway checkout so the provider receives the verbatim `amount`/`currency` from the authoritative plan row; the checkout call stays OUTSIDE any transaction. The checkout-time read is NOT authoritative — the purchase transaction re-validates active state + lane (a plan deactivated mid-checkout fails the purchase; the provider session is discarded with the rollback). This matches plan §1.2 (sequence diagram) and REQ-011/REQ-031.

## 4-tier map

- Tier 1: happy path (pending pair + junction + claim backfill + checkout descriptor, verbatim "200.00"/"EGP"); inactive + unknown plan → PLAN_NOT_FOUND zero-writes; NULL lane → PLAN_LANE_UNCONFIGURED zero-writes; missing key → VALIDATION zero-writes; suspended caller → FORBIDDEN zero-writes; same-caller replay → DUPLICATE_REQUEST, one pair survives; renewal (fresh key) → second pair
- Tier 2: empty-string key = missing; 128-char key accepted verbatim; 129 rejected; plan row is the source of truth (padded title, "199.99" verbatim)
- Tier 3: serialized same-key double-submit (one success + one DUPLICATE_REQUEST + ONE pair); real-PG `Promise.allSettled` double-submit on the production path (one success + one conflict + one pair + claim backfilled); mid-flow FK failure releases the claim (same key reusable on retry)
- Tier 4: foreign caller replaying A's key → oracle-safe PAYMENT_NOT_FOUND (no existence leak, zero writes); forged payload fields (amount/currency/userId/studentId) cannot influence the persisted row (server-derived only)
