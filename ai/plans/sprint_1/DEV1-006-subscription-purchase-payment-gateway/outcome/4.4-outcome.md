## Summary

Both Phase-4 repo extensions landed as single-statement primitives that follow the precedents just established by 4.1–4.3:

1. `PlanRepository.findActiveById(id, tx?)` — the purchase-time re-validation read. Active-only predicate `WHERE id = ? AND is_active = true` on BOTH executor branches (Drizzle select on a supplied tx; raw parameterized SQL via `queryDb` standalone), reusing the existing `PLAN_READ_COLUMNS` alias projection (which already carries `balance_lane AS "balanceLane"` — the shared-tree seed dependency — left byte-identical). Unknown plan and deactivated plan collapse into the same `null`, so a purchase can never bind to a withdrawn catalog row; callers re-validate INSIDE their transaction so a concurrent deactivation serializes behind the row lock.
2. `StudentRepository.creditLaneBalance(studentId, lane, amount, tx?)` — the activation crediting write. ONE unguarded raw-SQL UPDATE (`SET balance_x = balance_x + amount, updated_at = now() WHERE id = ?` with an aliased full-row `RETURNING` → `StudentSelectType | null`), resolving the target column exclusively through the NEW frozen map `CREDIT_LANE_BALANCE_COLUMNS` (`Record<SubscriptionCreditLane, AnyPgColumn>`, `Object.freeze`, enum-member keys — Hifz→`balance_hifz`, Tajweed→`balance_tajweed`, Reviews→`balance_reviews`). The existing `LANE_BALANCE_COLUMNS` held-fee map was NOT touched (verified via diff: zero removed lines; the new map's JSDoc only references it).

**NULL-lane decision (documented per task instructions):** the existing debit/refund primitives (`decrementLaneIfAvailable` / `incrementLane`) do NOT coalesce — `incrementLane` issues `SET balance_x = balance_x + 1` verbatim, so PostgreSQL NULL arithmetic propagates and a NULL lane column stays NULL. `creditLaneBalance` mirrors that convention EXACTLY (no `COALESCE`): crediting a NULL lane is a no-op on that lane, and the `balance_* >= 0` CHECK evaluates unknown on NULL rather than firing. Registration (`createForRegistration`) zeroes all lanes, so NULL lanes only exist on legacy/degenerate rows. The behavior is proven live in the test suite (see below).

## Cross-File Dependencies (for 6.1 / 7.1)

1. **6.1 purchase tx order:** `findActiveById(planId, tx)` FIRST (null ⇒ `NotFoundError("PLAN", …)` / PLAN_NOT_PURCHASABLE, whole tx rolls back) → claim insert → subscription/payment inserts. The read must receive the purchase `tx` — the active-state re-validation is only race-safe against a concurrent `setActiveStatusOnce(false)` inside the same transaction.
2. **7.1 activation:** on the zero-row-free path (`activatePendingOnce` returned a row), call `creditLaneBalance(studentId, plan.balanceLane, plan.sessionCount, tx)` in the SAME transaction; a null return means the student row vanished (cascade) — the caller decides (the repo raises nothing). `plan.balanceLane` is non-null for all seeded plans (2.3), but 6.1's fail-closed guard still owns the NULL-lane case.
3. **NULL-lane credit semantics inherited, not invented:** crediting a NULL lane column keeps it NULL (no COALESCE — same as `incrementLane`). If 7.1 ever needs NULL→0 seeding semantics, that is a NEW decision to be made there, not a silent change here.
4. The `students_balance_*_check` constraint names are pinned by the new CHECK-floor test — renaming them breaks the suite.
5. `findActiveById`'s no-tx branch returns the same `PLAN_READ_COLUMNS` shape as `findById`/`listActive` (incl. `balanceLane`) — keep that projection intact if refactoring.
