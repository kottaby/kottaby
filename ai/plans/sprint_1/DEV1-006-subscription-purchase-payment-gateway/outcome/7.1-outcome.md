# Task 7.1 Outcome — SubscriptionActivationService

**Plan:** `ai/plans/sprint_1/DEV1-006-subscription-purchase-payment-gateway/`

## Summary

`backend/services/billing/subscription-activation.service.ts` — namespace `SubscriptionActivationService`, one public entry point:

```ts
processWebhookEvent(event: PaymentWebhookEvent, locale: string, outerTx?: DBTransaction):
  Promise<{ processed: boolean; replayed?: boolean }>
```

with private `confirmPayment` / `failPayment` paths. The service receives an ALREADY-VERIFIED event (signature/size/parse belong to the route, task 8.1) and owns the settlement decision in fail-closed stages:

1. **Reference correlation** — `SubscriptionRepository.findByPaymentReference(event.reference, outerTx)`. Unknown ⇒ `{ processed: false }` + one bounded `logger.logDomainError` (`PAYMENT_REFERENCE_UNKNOWN`, ctx carries reference + outcome only) — no error storm, zero mutation.
2. **Settlement quarantine** — `StudentPaymentRepository.findBySubscriptionId(...)` then amount/currency comparison. Missing ledger row OR any disagreement ⇒ `{ processed: false }` + one `logger.error` carrying correlation ids only (`reference`, `outcome`, `subscriptionId`, `paymentId` — never raw payloads, never financial values). Zero mutation.
3. **`confirmed`** — ONE `withTransaction` unit, fixed order: path-selection read of the payment status (selection ONLY — the guarded updates are the arbiter and re-verify every predicate server-side) → `PlanRepository.findById` in-tx + NULL-lane fail-closed guard (`ValidationError("PLAN_LANE_UNCONFIGURED")` — the whole unit rolls back) → `activatePendingOnce` (zero-row ⇒ `{ processed: true, replayed: true }`, no credit, no second notification) → `markPaidOnce` → `StudentRepository.creditLaneBalance(userId, lane, plan.sessionCount, tx)` → `NotificationEngine.emitForUser(NotificationType.PaymentConfirmation, ..., tx)` persist-in-tx → `publishReceipts` strictly AFTER the unit resolves (engine degrades any publish failure to one structured log — never rolls back).
4. **`failed`** — one guarded decision write (`markFailedOnce`); subscription untouched (stays pending per the state machine), no credit, no notification. Zero-row ⇒ `{ processed: true, replayed: true }`.

Notification copy composed from the notifications namespace in the caller-supplied locale (server-to-server — no per-recipient locale resolution, per the engine's deferred-item D2 ruling). The emit is deliberately KEYLESS: the dedupe obligation is owned by the activation itself — the `activatePendingOnce` zero-row arbiter guarantees the emit and the credit run exactly once per subscription (a keyed emit would fire the engine's documented fail-open warn on every delivery with no cache injected).

## Decision log

1. **`outerTx?` third parameter (test path — plan-signature deviation, documented).** Plan §4.1 pins `processWebhookEvent(event, locale)`. The implementation adds an optional `outerTx?: DBTransaction` — the exact seam 6.1's `purchase` uses, and the documented purpose of the canonical `withTransaction` helper ("typically the test path under `runInRollback`"). Without it, Tier 1/2/4 tests could not run hermetically: the alternative (committed fixtures per test) is PROHIBITED by the schema itself — probe-proven this session: a `student_payments` row can never be deleted (BEFORE DELETE trigger), and even the linked subscription cannot be deleted (its `ON DELETE SET NULL` fires an UPDATE that the amended `prevent_student_payments_update()` guard rejects — not a permitted transition). Committed pairs + owners would be permanent residue. `outerTx` also carries the two pre-transaction reads and the failed-path write so the whole delivery participates in the caller's transaction (portable to real PG, unlike bare pool reads inside a rollback wrapper). Production callers (8.1) omit it — the 2-arg plan call shape still type-checks.
2. **Payment pre-read is path selection ONLY.** The in-tx status read decides which guarded path MAY run; `activatePendingOnce` / `markPaidOnce` / `markFailedOnce` re-verify the pending predicate server-side — a stale read can never override a concurrent decision writer. Documented in code; the `activatePendingOnce` zero-row → replay branch is exercised by the real-PG-gated concurrent test (sequential pre-reads always see the winner's committed state, so that branch is race-only).
3. **Late `confirmed` after `failed` = `{ processed: false }` (return contract).** REQ-053 demands reject-and-log, no silent upgrade. Rejecting WITHOUT throwing keeps the gateway ack at 200 `{processed:false}` (a thrown conflict would 4xx and trigger endless gateway retries against a terminal state — the same liveness-vs-integrity reasoning as REQ-025/026). Logged `PAYMENT_REPLAY_INCOMPATIBLE` via `logDomainError`. Full return contract documented in the JSDoc: `{processed:true}` applied · `{processed:true, replayed:true}` already applied · `{processed:false}` not applied (unknown ref / quarantine / late-confirmed).
4. **NULL lane at activation → fail-closed before ANY write.** `ValidationError("PLAN_LANE_UNCONFIGURED", t.subscriptionPurchase.planLaneUnconfigured)` (key reuse — no new error keys) rolls the whole unit back: the subscription stays pending and the gateway retry re-classifies once ops configures the lane (REQ-032 discipline; the lane is never guessed).
5. **Plan read at activation uses `findById`, not `findActiveById`.** The dispatch requires the plan read in-tx for `intervalDays`/`sessionCount`/`balanceLane` but does not require the active-only predicate: the payment is already settled, and the FK restrict guarantees the row exists — a catalog deactivation between purchase and webhook must not void a paid activation (REQ-011's active-only rule is purchase-time). `plan === null` (unreachable) fails closed as a `ConflictError` invariant.
6. **Defensive invariants are `ConflictError` (midpoint FIX-1 class).** The four unreachable-through-contract branches (ledger row vanished in-tx, plan vanished despite FK restrict, pending decision vanished after the activation won, student vanished despite FK restrict) throw `ConflictError` — same class as the billing repos' insert invariants. All roll the unit back; none swallow state.
7. **`failed` path is one guarded statement wrapped in `withTransaction(outerTx, …)`** — REQ-031's one-scope rule holds trivially (a single atomic UPDATE), and the wrapper keeps the test path inside the caller's savepoint instead of escaping to the pool.
8. **Keyless notification emit** — see Summary; no `NOTIFICATION_IDEMPOTENCY_DEGRADED` warn noise, no behavioral gap (activation guard = dedupe).
9. **Unknown-reference log level:** `logger.logDomainError` (warn in production, debug under TEST_SERVER) — REQ-025's "warning, never an error storm" via the house discipline of REQ-044 ("`logger.logDomainError` for expected rejections, `logger.error` for quarantine/mismatch").
