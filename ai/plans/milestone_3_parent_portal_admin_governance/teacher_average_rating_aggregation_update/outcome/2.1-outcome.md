## Deviation Report (fix-or-report → REPORTED, cross-file)

**Tier-4 premise drift — `Number.MAX_SAFE_INTEGER + 1` is NOT an empty-family result; it is a raw `22003`.**
`tasks.md` 2.1.TE (and the task instruction) say the absurd id is "bound-parameter safe ⇒ empty family result". Empirically verified against the live cluster: `evaluations.evaluated_id` is `int4`, PostgreSQL infers the unknown-typed bind parameter as `integer` from the `=` context, and the value `9007199254740992` fails the cast with SQLSTATE **22003** (`numeric_value_out_of_range`) — Drizzle surfaces the raw driver error. The value can never silently match rows, so the security property Tier 4 probes (no injection, no silent widening) holds — but the *expected outcome* in the plan wording is unachievable without deviating from the §4.2 verbatim implementation shape (no cast on the bind). The test asserts the honest behavior: 0 / −7 ⇒ empty aggregate; `MAX_SAFE_INTEGER + 1` ⇒ untranslated 22003 via `expectRepoError` + the file's `hasPostgresErrorCode` helper. **Action for the orchestrator:** amend the `tasks.md` 2.1.TE wording (and any plan §4.2 echo) at review time or in a plan fix-up commit — no code or spec-behavior change is needed. The same int4-domain fact is why the pre-existing evaluator-id probe in this file already used `2_147_483_647`.
