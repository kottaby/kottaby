## RULING 1 (DI-0.3-1, HIGH) — Journey teardown vs `student_payments`/`teacher_transaction` immutability triggers

### INVESTIGATION

**(a) Exactly what the triggers block.**
The immutability family is three tables — `audit_logs`, `student_payments`, `teacher_transaction` (header comment `backend/db/migration/3-immutability-triggers.sql:1-23`). For EACH of the three, the migration creates a pair of BEFORE-row-level triggers that RAISE EXCEPTION (canonical SQL file: `audit_logs` :43/:48, `student_payments` :73-83, `teacher_transaction` :103-113; identical drizzle mirror `backend/drizzle/20260904084152_custom_3-immutability-triggers/migration.sql` — `prevent_student_payments_update_trigger` :68, `prevent_student_payments_delete_trigger` :73, `prevent_teacher_transaction_update_trigger` :93, `prevent_teacher_transaction_delete_trigger` :98):

- ANY `UPDATE` of any row → `RAISE EXCEPTION '<table> is immutable — UPDATE is not permitted'` (:59-64/:66-71 for functions, :73-77/:79-83 triggers).
- ANY `DELETE` of any row → same shape (:89-101/:103-113).
- `INSERT` is never blocked.

Critical second-order consequence (verified in schema FKs): the immutability triggers also fire for **FK-action-driven implicit UPDATEs** on these tables:
- `student_payments.subscription_id → subscriptions.id ON DELETE SET NULL` (`backend/db/schema/billing/student-payments.ts:30-32`) — deleting a `subscriptions` row BEFORE its `student_payments` row would fire `prevent_student_payments_update_trigger` and fail.
- `teacher_transaction.session_id → session.id ON DELETE SET NULL` (`backend/db/schema/billing/teacher-transaction.ts:33`) — same hazard from deleting `session` first.
- RESTRICT FKs also pin the delete order: `student_payments.student_id → students.id ON DELETE RESTRICT` (`student-payments.ts:27-29`); `teacher_transaction.wallet_id → wallet.id ON DELETE RESTRICT` (`teacher-transaction.ts:30-32`).

**(b) Existing test-side suspension mechanism.**
YES — one, and it is the repo's sanctioned pattern:
- `withAuditDeleteTriggersSuspended(fn)` — `test/helpers/db-cleanup.ts:83-109`. Discovers every USER (non-internal) trigger on `audit_logs` via `SELECT tgname, tgenabled FROM pg_trigger WHERE tgrelid = 'audit_logs'::regclass AND NOT tgisinternal` (:85), DISABLEs all discovered triggers (:97-99), runs `fn`, and restores each trigger's EXACT prior `tgenabled` (O/D/R/A) in a `finally` (:59-70, :102-108); a no-trigger (push-provisioned) environment runs `fn` directly (:91-93). Runs on the global `db` (no tx param). Production code never imports it (scoping note :40-42).
- It is already consumed cross-layer by journey teardown: `test/workflows/helpers/journey-cleanup.ts:77-89` wraps its `audit_logs` deletes.
- Same `pg_trigger` probe shape reused in the trigger-tier DB test `backend/db/test/logic/audit/audit-immutability.test.ts:336-343`.
- **No `session_replication_role` usage exists anywhere in code or tests** (repo-wide grep: only `docs/admin/audit-trail.md:60`, which classifies `session_replication_role = replica`, `DISABLE TRIGGER`, and `DROP TRIGGER` as raw-credential environment-tier bypasses, not application/test mechanisms). No trigger drop/disable helper other than db-cleanup.ts exists in `test/` or `scripts/`.

**Connection facts (is `SET LOCAL session_replication_role = replica` viable?).**
`backend/db/index.ts:147-160` builds a `pg.Pool` from `DATABASE_URL` (max 10; lazy). `.env.test:3-4`: `DB_PROVIDER=postgres`, `DATABASE_URL=postgresql://postgres@127.0.0.1:5432/app_db` — local cluster, user `postgres` (superuser, trust auth on local installs), so `SET LOCAL session_replication_role` would technically execute. It is **nevertheless ruled out**: (1) it suspends ALL triggers including referential-integrity triggers, so a mistyped teardown DELETE could silently orphan rows (the `pg_trigger` approach touches only the named tables' non-internal triggers); (2) it is privilege-environment-dependent (CI materializes `.env.test` from `.env.test.ci` + step env — the role there is not contractually superuser), while the `pg_trigger` dance is privilege-free and provider-agnostic (also works under `DB_PROVIDER=pglite`, `backend/db/index.ts:38-40`); (3) zero repo precedent; (4) docs list it as a bypass posture, not a mechanism.

### RULING (binding for tasks 1.3, 2.2, 2.4)

1. **Add ONE new test-only helper to `test/helpers/db-cleanup.ts`** (same file as the audit precedent, no edit to existing exports):
   ```ts
   export async function withImmutabilityTriggersSuspended<T>(
     tables: readonly string[],
     fn: () => Promise<T>
   ): Promise<T>
   ```
   Behavior — EXACTLY the `withAuditDeleteTriggersSuspended` pattern generalized by table: for each table in `tables`, discover non-internal triggers via `pg_trigger` (`tgrelid = '<table>'::regclass AND NOT tgisinternal`), capture `tgenabled`; DISABLE every discovered trigger (across all listed tables) before invoking `fn`; restore EVERY trigger's exact prior firing state in `finally` (a trigger already disabled stays disabled); if NO listed table carries user triggers (push-provisioned DBs), run `fn()` directly with zero DDL round-trips. Executes on the global `db` (NO tx parameter — journey teardown runs outside any rollback wrapper per `test/workflows/AGENTS.md` rule 1, exactly like the audit helper). Header must repeat the test-env-scoping note: production runtime code never imports it. `withAuditDeleteTriggersSuspended` itself is NOT modified (audit cleanup keeps using it).
2. **Teardown order (task 2.4 `afterAll`, and the same shape wherever journeys B/C/D hard-delete these tables):** the journey-tracked `student_payments` ids and `teacher_transaction` ids (returned by the Task-1.3 factories) are hard-deleted FIRST, inside
   `await withImmutabilityTriggersSuspended(["student_payments", "teacher_transaction"], async () => { … })`,
   BEFORE any parent-side delete. Rationale: (a) RESTRICT FKs (`student_payments.student_id`, `teacher_transaction.wallet_id`) block `students`/`wallet` deletion while the rows exist; (b) ON DELETE SET NULL parents (`subscriptions`, `session`) would fire the immutability UPDATE triggers if deleted first. Then the existing FK-safe teardown proceeds (subscriptions → session → reports/evaluations → wallet → role children → `deleteUsersByIds`, whose audit deletes keep riding `withAuditDeleteTriggersSuspended`). Post-teardown zero-residue proof: count-by-tracked-id on both tables == 0 (harness rule 2 / REQ-042).
3. **Do NOT extend `JOURNEY_TRACKED_TABLE_DELETE_ORDER`** (`test/workflows/helpers/journey-fixture-registry.ts:67-76`) and do NOT modify the registry or `journeyCleanup`: their "immutable rows are assert-ZERO, never cleaned" contract (:29-35, :202-224) stays correct for the DEV3-016 journeys. The platform-analytics journeys track the two immutable tables' ids locally in the journey file (arrays filled from factory return values in `beforeAll`) and delete them explicitly under the new wrapper. This keeps the shared harness untouched.
4. **No migration, trigger, or production-code change.** This is a test-harness capability plus plan wording only.

## RULING 3 (DI-0.3-3, MEDIUM) — Repo non-tx executor convention

### INVESTIGATION

**The CRITICAL rule, verbatim** (`backend/db/repo/AGENTS.md:38`):
> "**Neon HTTP Client for Bare Reads (CRITICAL)**: All non-transactional read methods in database repositories MUST use `queryDb(tx)` from `@/backend/db`. When Neon HTTP mode is eligible, reads execute statelessly over HTTP POST; when `tx` is passed or HTTP mode is disabled, it falls back seamlessly to transaction/TCP handles. See `docs/drizzle/neon-http-client.md` for complete architecture, rules, and examples."

**What `queryDb(tx)` actually means in this tree.** `docs/drizzle/neon-http-client.md:30-44` documents an executor-selector `queryDb(tx?: DBTransaction)` ("tx wins FIRST … stateless HTTP fallback") — but that selector is **not implemented in this tree** (no `getStatelessHttpDb`/`isNeonHttpEligible`/`getActiveHttpProvider` symbols exist outside the doc). The only shipped export is the raw parameterized-SQL runner `queryDb<T>(text, params?)` (`backend/db/index.ts:218-257`). The tree's compliant interpretation — how repos actually satisfy the rule — is the **dual-branch method**: `tx` supplied → Drizzle builder on `tx`; absent → raw parameterized SQL via `queryDb(text, params)`:

- `backend/db/repo/users/user.repository.ts:43-63` (`findByEmail`) and :75-95 (`findById`) — file header :5 names the rule ("Reads use `queryDb` … per the Neon-HTTP-client rule"); branch = `if (tx && isDBTransaction(tx)) { tx.select()… } else { queryDb(text, params) }`.
- `backend/db/repo/notifications/broadcast-audience.repository.ts` — the READ-ONLY exemplar: header :34-38 ("Reads use `queryDb` … on the non-transactional branch — the Neon HTTP fast path — and the Drizzle query builder on a supplied transaction, mirroring `NotificationRepository` / `UserRepository`"); non-tx branch `resolveViaQueryDb` :203-249 (raw `$n`-parameterized text); tx branch via the builder; the two representations are kept semantically identical on purpose (:75-94, `GOVERNANCE_PREDICATE_SQL` vs `governanceConditions()`).
- Same split: `notification.repository.ts` (reads :180/:209/:245 via `queryDb`; writes `tx ?? db` :131/:157/:274 — writes are out of the rule's scope), `plan.repository.ts:115-164`, `student.repository.ts:120-121/:193-194/:256`.

**The mixed siblings (deviation side).** `backend/db/repo/audit/audit-trail.repository.ts:148,177` and `backend/db/repo/admin/admin-user.repository.ts:127` (plus its `getStats` :178-213, which this plan REUSES untouched) execute reads on `tx ?? db`, documented in their own headers (:5-9). That is the precedent the plan §4.1 copied — but it contradicts the layer's CRITICAL rule for non-tx reads; `session.repository.ts`/`wallet.repository.ts` mix both styles (writes `tx ?? db`, standalone reads `queryDb`). `AdminUserRepository.getStats` is untouchable here (2.M/5.2 git-diff gate) and is NOT this ruling's subject.

### RULING (binding for task 2.5)

Every `PlatformAnalyticsRepository` method implements the **dual-branch executor** — the plan's literal `tx ?? db` is RESCINDED for this repo:

- Signature stays exactly as planned: trailing `tx?: DBTransaction` (typed via `@/backend/types`; with `DBTransaction` the `isDBTransaction` guard used by `DBQueryExecutor`-typed siblings is unnecessary — branch simply on `if (tx)`).
- **`tx` supplied** → the query executes on `tx` (Drizzle builder — `tx.select({ … sql<number>\`count(*)::int\`… }` with `sql` fragments, bound params, enum members as VALUE-imported binds) so the read joins the caller's transaction / `runInRollback`.
- **`tx` absent** → the same statement executes via `queryDb<RowType>(text, params)` from `@/backend/db` (raw parameterized SQL, numbered `$n` binds — the Neon HTTP fast path when eligible).
- **`db` MUST NOT be imported by the new repo file at all** (import `queryDb` only) — there is no `db`-fallback branch to write.
- The two branches MUST stay semantically identical (broadcast-audience mirror discipline): same predicate text, same parameterization, same ordering. Aggregation helpers (`utcDayStart`/`isoWeekStart`/`utcMonthStart`) compute `Date` bounds ONCE per call and bind into BOTH branches as parameters.
- Test note for 2.5.TE (already mandated "BOTH `tx` and non-`tx` executor branches"): inside `runInRollback` the non-`tx` branch hits the pool OUTSIDE the rollback tx, so non-`tx`-branch assertions must not depend on uncommitted fixtures — assert branch execution/shape against committed state (or baseline-delta math), and keep fixture-delta assertions on the `tx` branch.

### AMENDMENTS

- **Plan §4.1 (`plan.md:374`):** "every method takes an explicit `now` where windowed plus trailing `tx?: DBTransaction` (executor `tx ?? db`)" → "(executor: dual-branch — `tx` when supplied, else raw parameterized SQL via `queryDb`; per `backend/db/repo/AGENTS.md` CRITICAL Neon-HTTP rule; no `db` fallback)".
