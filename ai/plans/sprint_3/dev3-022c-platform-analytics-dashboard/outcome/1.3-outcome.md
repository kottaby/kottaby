Design points (all verified against the live schema files before writing — `backend/db/test/AGENTS.md` rule 18):

- **FK-aware ids:** every parent id is an explicit positional arg in the established ids-order convention; nullable FKs (`student_payments.subscription_id`, `evaluations.session_id`, `teacher_transaction.session_id`) are explicit `number | null` params so journeys can model unlinked rows without reaching into overrides.
- **Explicit timestamps / relative-to-now fixtures:** every factory sets `createdAt: new Date()` at CALL time (not module load) and every factory's `overrides` (typed `Partial<XSelectType>`) accepts ANY timestamp column for relative offsets — REQ-026 posture. `createTestSubscription` additionally defaults `startDate: new Date()` + `endDate: null` so the default row satisfies the ACTIVE-window predicate (`status='active'`, start due, end not due); an expired fixture needs an `endDate` in the past, which the JSDoc example shows.
- **CHECK constraints honored by the defaults themselves:** `student_payments_amount_check` ≥ 0 (`"100.00"`), `teacher_transaction_amount_check` ≥ 0 (`"50.00"`), `reports_student_rating_by_teacher_check` 0–5 (default `5`, nullable override documented), `evaluations_score_check` 0–100 (default `85`, nullable), `wallet_balance_check`/`wallet_total_earning_check` ≥ 0 (`"0.00"`), `teacher_average_rating_check` 0–5 (`null` default).
- **Money = decimal STRINGS, currency = 3-char code strings** (`"EGP"` — `currency` is `char(3)`, not an enum; per-currency revenue grouping keys on it verbatim).
- **Enum values via VALUE imports only:** `SubscriptionStatus`, `PaymentStatus`, `PaymentGateway`, `TransactionType`, `TransactionStatus`, `SessionStatus`, `SessionType` — all imported as runtime values from the TS mirrors of the `backend/db/schema/enums.ts` pgEnums (`@/backend/enum/billing/*.enum`, `@/backend/enum/scheduling/*.enum` — the exact deep-import convention used by `session.repository.ts`, `wallet.repository.ts`, and DB-test siblings). ZERO raw enum strings in any new factory (the raw strings visible in the file belong to pre-existing factories, untouched).
- **Immutability (RULING 1 compliance, domain language only):** the `student_payments` and `teacher_transaction` factories carry a short append-only note ("this factory therefore only ever inserts" / "a payout settles via a NEW compensating row, never an in-place flip") — INSERT is unaffected by the immutability triggers, so factories insert normally; comments name no artifact, no trigger SQL, no task/REQ references.
- **No side channels:** no factory writes audit rows or notifications (single-table inserts only); `createTestTeacherRow` does NOT create or infer a user/role — the caller creates the `users` row with role `teacher` (no implicit role synthesis, documented in the JSDoc).
- **Ledger ≠ cached columns:** `createTestTeacherTransaction` explicitly does NOT touch `wallet.balance`/`total_earning` (no DB trigger moves them — verified: the only custom triggers are the three immutability pairs in `backend/db/migration/3-immutability-triggers.sql`; the wallet repo updates cached columns at the app layer). Funded-wallet fixtures use the wallet factory's overrides, per the JSDoc.
