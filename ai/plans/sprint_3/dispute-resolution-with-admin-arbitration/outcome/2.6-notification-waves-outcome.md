## Journey-test diff adjudication (mandated explicit ruling)

`git diff test/workflows/sessions/post-confirmation-dispute.journey.test.ts` contains exactly two
logical hunks, both inside the notification-spy plumbing, ZERO assertion-content changes:

1. A new `publishedIdCount()` helper (the flat recipient-id list's current length) with a
   docblock explaining the series mismatch.
2. Two call sites (`J1 step 5` open wave, `J1 step 7` resolve wave; the J2/J3/race legs already
   used a per-leg counter variable the same way) switch their slice marker from
   `publishedUserIds().slice(publishBefore)` to
   `publishedUserIds().slice(publishedIdsBefore)`.

**Ruling: KEEP — a genuine bug fix that STRENGTHENS the assertions.** The journey's spy records
one entry per `publishReceipts` CALL (`publicationCallCount()` counts dispatches), while
`publishedUserIds()` flattens the `recipientUserIds` of every receipt across all dispatches —
two different series. Shipped waves legitimately publish MULTIPLE receipts in ONE call (e.g.
`session-report.service.ts:390` publishes the report-ready student + parent receipt pair in a
single `publishReceipts(receipts, …)` dispatch), so by the time a dispute wave fires, the
dispatch count is strictly smaller than the id count. Slicing the ID list by the DISPATCH count
therefore misaligned the window: it retained stale recipient ids from earlier waves, which could
spuriously FAIL `not.toContain` pins (e.g. the teacher, who legitimately received earlier
session-request/completion waves) — or, had a pinned user appeared in an earlier wave inside the
misaligned window, spuriously PASS a `toContain` pin even if the new wave dropped them. The
fixed marker slices exactly the new wave's recipients; the `publicationCallCount()` delta pins
(+1 dispatch per wave) are unchanged, every `toContain`/`not.toContain` membership pin is
unchanged, and no expected failure was silenced. Corroborating evidence: in the 2.4 red state
these publish assertions sat BEHIND the (then-failing) inbox-row counts and never executed; they
executed for the first time once 2.6 landed and passed only with the corrected marker.

## Carry-Forward for Task 3.1 (exact publish-after-commit contract at the resolver)

- **The resolver shell makes NO publish call on the production path.** Bind
  `openPostConfirmationDispute` / `arbitrateDispute` WITHOUT an outer transaction; the flow
  itself executes the publish-after-commit — internally it calls
  `NotificationEngine.publishReceipts(receipts, locale)` (signature:
  `(receipts: readonly NotificationDeliveryReceipt[], locale: string, options?)`) strictly after
  its own transaction commits, one publish per receipt (per-locale cohort). This is the shipped
  service-side wave convention; the journey pins it (+1 dispatch per wave at the spied engine
  boundary, with the resolver-equivalent journey caller making no publish call).
- **Receipt type:** `readonly NotificationDeliveryReceipt[]` — `{ notifications: rows,
  recipientUserIds, emitClaimKey }`, one receipt per locale cohort, in first-seen cohort order.
  The flows do NOT surface receipts on their return (they return the session row only, per the
  Component-1 signatures 2.4/2.5 pinned); on the outer-tx (test) path the flow skips the publish
  and the transaction-owning caller owns it.
- **Claim keys** (for any retry/replay reasoning at the GraphQL layer):
  `session:<sessionId>:dispute-opened` and `session:<sessionId>:dispute-resolved` — deterministic,
  session id + wave kind only; the engine folds the recipient cohort into the hashed claim and
  fails open without a cache.
- **Failure semantics at the boundary:** emission failures roll back the whole arbitration
  transaction (fail closed — receipts share the tx fate); publish failures degrade at the engine
  (fail open) and never fail the committed mutation — the resolver needs no try/catch around the
  service call for push outages.
- Unchanged 2.5/2.1 carry-forwards: dispatch `Cancel|Complete` → shipped
  `resolveSessionDispute`, `Refund|PartialRefund|Uphold` → `arbitrateDispute`; the schema regen
  MUST ship together with the dispatch.
