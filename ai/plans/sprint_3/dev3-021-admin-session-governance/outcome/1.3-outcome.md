## 1. Registry located — what "the centralized error-code registry" actually is

`docs/graphql/error-handling-contract.md` was read in full FIRST (per task requirement), together with the producer-side doc it references (`docs/graphql/domain-error-extensions-code.md`). The registry is NOT one file — it is a four-surface architecture with a deliberate two-tier code policy:

| Surface | Path | Content |
|---|---|---|
| Code type (category union) | `backend/types/errors/api-error.types.ts:38-47` | `ErrorCode` = EXACTLY nine category codes: `BAD_REQUEST, UNAUTHORIZED, FORBIDDEN, CONFLICT, DUPLICATE_REQUEST, VALIDATION, RATE_LIMITED, SERVICE_UNAVAILABLE, INTERNAL_SERVER_ERROR` |
| Code→HTTP taxonomy | `backend/lib/errors/error-code-taxonomy.ts:41-51` (`ERROR_CODE_HTTP_STATUS`) · `:59-61` (`LEGACY_ERROR_CODE_ALIASES`) · `:68-78` (`CANONICAL_SELF_MAP`, `satisfies Record<ErrorCode, ErrorCode>`) · `:101-115` (`isErrorCode`/`normalizeErrorCode`) | Sole status source; frozen data |
| Producer classes | `backend/lib/errors.ts` | `DomainError` :19-29; `ValidationError` overloaded ctor :78-86 (free-form `(code, message)`); `ConflictError` overloaded ctor :172-182 (JSDoc **names `SESSION_INVALID_TRANSITION` verbatim** at :162 and :169 as a legal custom conflict code) |
| Client row table | `frontend/providers/apollo/error-link.map.ts:360-369` | Branches on normalized code; rows for the nine categories + `*_NOT_FOUND` family (:72-74); **"anything else → `null`"** — custom codes fall through and per-surface arms own their UX |

**The decisive registry convention** (contract §1, "Custom domain codes"): codes like `${ENTITY}_NOT_FOUND`, quota codes, `RECURRING_CLASS_DAYS_REQUIRED` are **legal transport values OUTSIDE the nine categories** — they never resolve through the taxonomy (`normalizeErrorCode` → `null`), producers own their fallback, and they must **never be force-fit into categories**. The "Extending the taxonomy" procedure (union + `ERROR_CODE_HTTP_STATUS` + `CANONICAL_SELF_MAP` + i18n triple + paired suites) exists for new **categories** only. The registry's own SEC suite pins this: `backend/lib/errors/test/error-code-taxonomy.test.ts:126-131` ("custom domain codes fall through — never masquerade as categories") asserts `USER_NOT_FOUND` / `RECURRING_CLASS_DAYS_REQUIRED` / `QUOTA_NOT_FOUND` are non-members, and its grep-prove test confirms no other code→status map exists. Contract "What NOT to Do" additionally forbids Pothos/DB enum registration of codes.

**Therefore the correct registration test for a custom domain code is: does an in-tree producer already use it (or does the class hierarchy make it constructible without registry edits)?** — not "is it in the union?" (it must NOT be).
