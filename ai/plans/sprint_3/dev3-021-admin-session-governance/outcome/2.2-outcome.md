## 1. DECISION (headline): **REUSE — create NOTHING**

No new helper was created at the repo surface or the service layer, because both halves of the needed semantics already exist and compose exactly as the reassign flow requires:

1. **The data-access half exists at the repo layer**: `TeacherRepository.lockForCertificationCheck` — `backend/db/repo/teachers/teacher.repository.ts:111-121` — a REQUIRED-`tx` `SELECT id, is_approved FROM teacher WHERE id = $1 FOR UPDATE` locking read returning the minimal projection or `null`. This is the certification surface the task hunts for; it is NOT missing.
2. **The classification half (localized throws) is service-layer BY DESIGN**: `backend/db/repo/AGENTS.md` (Separation of Concerns: "Repositories are strictly for data access. Business logic, permission checking, and complex orchestration must reside in the `backend/services/` layer") + `.agents/instructions/backend.instructions.md` ("Repo: data-access ONLY — no business logic, no permission checks, no hardcoded error strings") + the repo file's own docblock (`teacher.repository.ts:36-37`: "No business logic, no permission checks, no i18n or logging imports — the caller decides what `isApproved = false` or a `null` row means"). An `assertCertifiedTeacher` that throws localized `ConflictError`s **cannot live in the TeacherRepository surface** without violating all three.
3. **The exact candidate-assertion composition already exists as shipped precedent**: `backend/services/classes/session-lifecycle.booking.ts:202-218` — `null` ⇒ `NotFoundError("TEACHER", t.teacherNotFound)`; `isApproved !== true` ⇒ `ConflictError("TEACHER_NOT_CERTIFIED", t.teacherNotCertified)` (with `logger.logDomainError`). Task 3.1 mirrors this verbatim for the reassign candidate.
4. **Single consumer**: the reassign flow in 3.1 is the only call site (plan §4). A new service-layer `assertCertifiedTeacher` would be indirection over ONE call site (dead-code/semantic-review failure); deduplicating booking's inline block would refactor a shipped, fully-tested DEV3-004 flow — outside this ticket's blast radius and forbidden by D-01 reuse-first discipline.

This satisfies the task's own conditional ("IF missing … else reuse") and plan D-01 (reuse-first): the ticket-scoped helper IS the existing machinery.

### Why the alternatives were rejected

- **Create `assertCertifiedTeacher` in `TeacherRepository`**: direct violation of the repo-layer contracts cited above; the file's own Tier-4 source-pin test (`teacher.repository.test.ts` — "no i18n, no logger, no console, no business logic") would fail by construction. The repo method's `null`/`isApproved:false` return contract IS the designed extension point; the caller owns meaning.
- **Create a NEW service-layer shared helper** (e.g. in the governance module or transitions.ts): exactly one consumer (3.1's reassign), so it adds a second code path where the booking precedent already documents the canonical 3-line classification; exporting from `transitions.ts` would touch a shipped DEV3-004 module ("Nothing in this module is part of the public API", `transitions.ts:45-46`) and change its blast radius for zero behavioral gain.
- **Refactor booking.ts to call a new shared helper**: out of scope for this ticket; risks a 370-test green battery for pure stylistic dedupe (semantic-review: no value, real risk).

## 3. Exact surface for Task 3.1 to consume

**Signature (verbatim from source, `teacher.repository.ts:111-114`):**

```ts
export async function lockForCertificationCheck(
  teacherId: number,
  tx: DBTransaction
): Promise<{ id: number; isApproved: boolean | null } | null>
```

- `tx` is REQUIRED (no optional/non-tx branch) — a locking read outside a transaction protects nothing; always call inside the caller's `withTransaction`.
- `null` ⇒ no `teacher` row exists for the id (teacher rows share PK with `users.id`; a teacher-applicant's `users.id` resolves to `null` — an applicant never mints certification).
- `isApproved: boolean | null` mirrors DB nullability; `null` counts as NOT certified (`!== true`).
- The FOR UPDATE lock is held until the caller's tx commits/rolls back, so the certification value the check sees is the value the subsequent `guardReassignTeacher` write commits against — no flip window.

**Composition 3.1 implements (mirrors `booking.ts:202-218` exactly; classes/logger/errors per 1.3 outcome carry-forward):**

```ts
// inside withTransaction(outerTx, async tx => { ... }), BEFORE guardReassignTeacher
const lockedTeacher = await TeacherRepository.lockForCertificationCheck(input.newTeacherUserId, tx);
if (lockedTeacher === null) {
  logger.logDomainError("Admin teacher reassignment rejected: teacher target not found", {
    code: "TEACHER_NOT_FOUND",
    entity: "session",
    entityId: input.newTeacherUserId,
  });
  throw new NotFoundError("TEACHER", t.teacherNotFound);
}
if (lockedTeacher.isApproved !== true) {
  logger.logDomainError("Admin teacher reassignment rejected: teacher not certified", {
    code: "TEACHER_NOT_CERTIFIED",
    entity: "session",
    entityId: input.newTeacherUserId,
  });
  throw new ConflictError("TEACHER_NOT_CERTIFIED", t.teacherNotCertified);
}
```

Imports: `TeacherRepository` from `@/backend/db/repo`; `ConflictError, NotFoundError` from `@/backend/lib/errors`; `logger` from `@/backend/lib/logger`; `t` from `getServerTranslations(locale).errorsTranslations`. Denial paths write ZERO audit rows (nothing has been written at this point in the tx — the assert precedes every write).

## 6. Carry-forward knowledge for Task 3.1

1. **Do NOT re-implement an `assertCertifiedTeacher`** — compose `lockForCertificationCheck` + the §3 classification inside the reassign `withTransaction`, before `guardReassignTeacher`. This is the shipped booking precedent (`booking.ts:202-218`) and the exact pattern pinned by 1.3 (carry-forward pattern 2) and 1.2 (key table).
2. **Denial semantics for the reassign candidate:** missing teacher row ⇒ `NotFoundError("TEACHER", t.teacherNotFound)` (an applicant's / non-teacher's id dies here); row present but `isApproved !== true` (incl. DB-level NULL) ⇒ `ConflictError("TEACHER_NOT_CERTIFIED", t.teacherNotCertified)`. Never collapse the two arms — they are distinct in the established contract and in the frontend's code-specific arms (`teacherSessionCacheArms.ts:92-99`).
3. **Read-then-write nuance (recorded as a ⚠️ deferred-ledger watch row):** a plain FK on `session.teacher_id` asserts row EXISTENCE only — it cannot enforce `is_approved`. The write-time certification guarantee actually comes from the FOR UPDATE row lock held across check→write within the SAME transaction (the booking pattern). Composing the §3 assert inside the reassign `withTransaction` (which the plan already mandates) delivers the invariant; nothing extra is owed.
4. **Eligibility order in the reassign tx:** state eligibility is owned by the 2.1 guard-update's `WHERE status = 'scheduled'` clause (D-03 matrix); the certification assert and the guard-update are independent predicates — keep the certification assert BEFORE the guard-update (mirrors booking: certification lock → writes) so a denial leaves the row byte-identical with zero audit rows.
5. **No test duplication:** 3.1's service suite should assert the classification arms via its own fixtures (unapproved teacher / applicant id / DB-null flag) against the SERVICE, exactly as `session-lifecycle.service.test.ts:726-752` does for booking — do not re-test the repo method's internals.
