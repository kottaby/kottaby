## 3. Idempotency-key mechanism (RESOLVES the deferred-ledger watch item)

> Resolves deferred-items.md watch item: *"No idempotency-claim decorator position verified for mutations at plan time — reuse the same mechanism the participant mutations use (chained inside `withTransaction` or outer claim wrapper; record finding in 4.3 outcome)."*

**Finding: there is NO decorator and NO outer claim wrapper — the key is a propagation-only function argument threaded resolver -> service, with the claim itself chained INSIDE the service's `withTransaction` body.** Exact flow for `adminCancelSession` (the only one of the four that consumes a key):

1. **Gateway capture (exactly once):** `createGraphQLContext` reads `request.headers.get("x-idempotency-key")` (`backend/graphql/gqlContextFactory.ts:191`) into `ctx.idempotencyKey?: string | null` — PROPAGATION-ONLY per `docs/IDEMPOTENCY.md` + gateway Rule 3: never re-derived, never trimmed, never consultable by any authorization decision.
2. **Resolver passes it VERBATIM:** `SessionAdminGovernanceService.cancel(ctx.user.id, input, ctx.locale, ctx.idempotencyKey ?? null)`. An absent header arrives as `null` and STAYS `null` — null key means claim-DISABLED for that call, so an unkeyed admin cancel is a legitimate fire-and-forget operation (unlike booking, keying is optional here, never required).
3. **Service owns the key-shape guard:** non-null keys that are empty or exceed `MAX_IDEMPOTENCY_KEY_LENGTH` throw `ValidationError(t.idempotencyKeyRequired)` before any database work (`backend/services/classes/session-admin-governance.ts:321-323`).
4. **Claim rides the SAME transaction:** the key is threaded into `cancelSessionInTx(actorId, parsed.data, cancelReason, idempotencyKey ?? null, locale, tx, t, options)` INSIDE the `withTransaction` body — the claim-table insert, the cancel write, the same-lane hold release, and the audit row commit atomically together. This is the plan's "chained inside `withTransaction`" candidate position; no outer claim wrapper exists on the mutation surface.

**Proof:** suite Tier 3 — same `X-Idempotency-Key` replay returns the same response shape, appends NO duplicate audit row, and performs NO second refund (see §5).
