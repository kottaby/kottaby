## Summary

Created the parent-portal monitoring service and its sibling helpers file
backing the five read-only GraphQL queries defined in plan §4.2. The
service is the INV-P1 authorization spine for the portal: every
per-student read funnels through ONE gate (`requireLinkedChild`) run
inside the SAME `withTransaction` as the data reads, so the link grant
and the row scan share one READ COMMITTED snapshot — there is no
time-of-check to time-of-use window between gate and read.

- `ParentMonitoringService.listLinkedChildren` — zero-arg list of the
  caller's confirmed-linked children (soft-deleted excluded). The only
  identity in the predicate is the verified `parentActorId`; no
  per-student gate (the list IS the parent's own scope).
- `ParentMonitoringService.getChildProgress` — the gated child header
  echo + honest progress row count + latest Jadid/Madi positions, in
  ONE payload (the detail header and the progress tab are served
  together — fewer authorization seams).
- `ParentMonitoringService.listChildSessions` — derived attendance
  entries (session rows), paged newest-first.
- `ParentMonitoringService.listChildReports` — per-session report rows
  joined to their session for status/timestamp context, paged
  newest-session-first.
- `ParentMonitoringService.listChildHomework` — homework rows with the
  two parallel Jadid/Madi track blocks, paged newest-session-first.

The gate produces a CONSTANT denial shape across all five causes
(malformed id, missing row, foreign id, never-linked id, severed child)
— the caller cannot distinguish the denial cause (oracle posture).
Every denial emits exactly ONE bounded `logDomainError` whose context
bag is exactly `{ code: "FORBIDDEN", entity: "students", entityId:
<studentId>, locale }` — never the row's stored fields, never the
parent's identity beyond the bound parameter.

## The `requireLinkedChild` Gate Contract (verbatim)

```typescript
export async function requireLinkedChild(
  parentActorId: number,
  studentId: number,
  locale: string,
  tx: DBQueryExecutor | undefined
): Promise<StudentSelectType> {
  const t = getServerTranslations(locale).errorsTranslations;

  const deny = (): never => {
    logger.logDomainError("Parent portal read denied: link not in force", {
      code: "FORBIDDEN",
      entity: "students",
      entityId: studentId,
      locale,
    });
    throw new ForbiddenError(t.forbidden);
  };

  if (!Number.isSafeInteger(studentId) || studentId <= 0) {
    return deny();                                      // malformed id ≡ denial
  }

  const student = await StudentRepository.findById(studentId, tx);
  if (student?.parentId !== parentActorId) {
    return deny();                                      // missing OR foreign OR never-linked
  }

  const childUser = await UserRepository.findById(studentId, tx);
  if (childUser === null || childUser.isDeleted) {
    return deny();                                      // severed (soft-deleted) child
  }

  return student;
}
```

### Denial-Oracle Verification (all five causes → same shape)

The gate enforces a CONSTANT denial shape across every cause the spec
enumerates. Every denial path returns the SAME `ForbiddenError` carrying
the SAME localized message (`errorsTranslations.forbidden`) and emits
exactly ONE `logDomainError` with the SAME bounded context bag. The
caller cannot distinguish the cause from the response bytes.

| # | Cause | Gate arm | ForbiddenError message | logDomainError context |
|---|---|---|---|---|
| 1 | Malformed id (non-integer, ≤0) | `!Number.isSafeInteger(studentId) \|\| studentId <= 0` → `deny()` | `t.forbidden` | `{ code: "FORBIDDEN", entity: "students", entityId: <studentId>, locale }` |
| 2 | Missing id (no student row) | `student === null` → `student?.parentId !== parentActorId` is `undefined !== <number>` → `true` → `deny()` | `t.forbidden` | same |
| 3 | Foreign id (student exists, different parent) | `student.parentId !== parentActorId` → `deny()` | `t.forbidden` | same |
| 4 | Never-linked id (student exists, `parentId IS NULL`) | `student.parentId === null` → `null !== <number>` → `true` → `deny()` | `t.forbidden` | same |
| 5 | Severed child (student + link valid, `users.isDeleted = true`) | `childUser.isDeleted` → `deny()` | `t.forbidden` | same |
| (5b) | Child user row missing (`childUser === null`) | `childUser === null` → `deny()` | `t.forbidden` | same |

Every arm produces:
- **ZERO** rows in the denial response (the throw aborts before any
  data read on the per-student path; on the per-list path, the
  predicate `users.isDeleted = false` excludes the row upstream).
- **ZERO** child fields in the log context bag — only `entityId:
  <studentId>` (the caller-supplied input, not the row's stored
  columns).
- **EXACTLY ONE** `logDomainError` (the `deny()` closure is the
  single log site; no other log call runs on the denial path).
- **IDENTICAL** response bytes (one `ForbiddenError` with one
  localized message string from `errorsTranslations.forbidden`).

The `deny()` closure is the ONLY log site on the denial path — there
is no path that emits zero logs (the closure always logs before
throwing) and no path that emits more than one (the closure throws
immediately after logging, so no second log can run).

```typescript
    parentActorId: number,
    studentId: number,

    outerTx?: DBTransaction
  ): Promise<ParentReportPageReturnType>;

  async function listChildHomework(
    parentActorId: number,
    studentId: number,
    page: ParentPageInput | undefined,
    locale: string,
    outerTx?: DBTransaction
  ): Promise<ParentHomeworkPageReturnType>;

```

Every method:
1. Starts with `await requireActor(parentActorId, UserRole.Parent,
   locale, outerTx, false)` — the relaxed READ path (identity + role
   only; governance arm disabled so a governed-but-not-deleted
   parent's self-scoped reads stay visible). The actor re-check runs
   BEFORE the per-student transaction opens (per plan §4.2: "EVERY
   denial: ... the check runs before any transaction opens on the
   mutation paths" — the relaxed read path inherits the same
   ordering).
2. Per-student methods (`getChildProgress`, `listChildSessions`,
   `listChildReports`, `listChildHomework`) then open ONE
   `withTransaction(outerTx, async tx => { ... })` and run the
   `requireLinkedChild` gate FIRST, before any data read, all inside
   the same transaction snapshot. The `outerTx` parameter lets a
   caller-owned transaction (e.g., a test under `runInRollback`) join
   the unit as a SAVEPOINT — the caller owns the commit boundary.
3. `listLinkedChildren` (zero-arg, no per-student gate) calls the
   repo directly with the caller's `outerTx` (or `undefined` for the
   global `db` handle) — no `withTransaction` needed (the list IS the
   parent's own scope; the predicate `users.isDeleted = false`
   enforces severance at the repo layer).

## Notes on convention adherence

- **Sibling-helper co-location** mirrors the
  `parent-link-request.{helpers,service}.ts` split: the helpers file
  holds the gate + projection mappers + pagination clamp + fail-closed
  enum narrowing helpers (module-private except for the gate and the
  mappers the service consumes); the service file holds the
  five-method namespace. The split honors the repo's `max-lines` /
  `max-lines-per-function` budgets without extracting to a third file.
- **`requireActor` import** — the helper is imported DIRECTLY from
  `./parent-link-request.helpers` by the service file (same-domain
  sibling import precedent: `session.repository.ts` ↔
  `session.repository.helpers.ts`). It is NOT duplicated in the
  monitoring helpers. This matches the plan §4.2 mandate verbatim.
- **`toSessionStatus` replication** — the private helper at
  `backend/graphql/pothos/classes/session.pothos.ts:62` is NOT
  exported (and cross-layer service→graphql imports would violate
  layering). The fail-closed guard is replicated locally as
  `isSessionStatus` (type-guard) + `toSessionStatus` (narrowing
  function with `logDomainError` + throw on corrupt values), mirroring
  the `toCanonicalLinkStatus` discipline in
  `parent-link-request.helpers.ts`. The 2.3 outcome explicitly
  sanctioned this replication.
- **Pagination clamp** — `clampPageInput` uses a local
  `isPositiveSafeInteger` type-guard (avoids `as number` unsafe
  assertions, satisfies oxlint `no-unsafe-type-assertion`). The clamp
  matches the `MAX_PAGE_SIZE = 50` / `DEFAULT_PAGE_SIZE = 25`
  precedent in `session.repository.helpers.ts:163-164`.
- **Optional chain for null-narrowing** — `student?.parentId !==
  parentActorId` (in the gate) replaces `student === null ||
  student.parentId !== parentActorId` (satisfies
  `@typescript-eslint/prefer-optional-chain`). The semantics are
  preserved: `undefined !== <number>` is `true`, so a null student
  still denies.
- **`Promise.all` for parallel list+count** — the per-student list
  methods (`listChildSessions`, `listChildReports`, `listChildHomework`)
  issue the list and count reads in parallel via `Promise.all` inside
  the same transaction. Both reads share the same `tx` snapshot, so
  the count cannot drift from the list (the shared predicate builder
  guarantees this at the repo layer — see 2.3 outcome).
- **`getChildProgress` redundant user lookup** — the gate already
  fetches `childUser` (for the `isDeleted` check) but returns only
  `student` (per the plan's pseudo-signature `Promise<StudentSelectType>`).
  The service re-reads the user via `UserRepository.findById` inside
  the same tx for the `fullName` field. This is a fast PK lookup
  inside the same snapshot — negligible cost. The alternative
  (changing the gate's return type to `{ student, childUser }`)
  would deviate from the plan's pseudo-signature; the faithful
  approach was chosen.
