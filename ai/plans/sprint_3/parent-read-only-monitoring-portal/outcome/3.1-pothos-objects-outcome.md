## Summary

Created the single declarative Pothos module that registers all ten
parent-portal GraphQL object types as `objectRef<...ReturnType>("GraphQLName")`
implementations, each backed EXCLUSIVELY by the closed read-projection
types authored in task 2.1 (`@/backend/types/parents`). The module is
pure declarative — every field is a structural `t.expose*` /
`t.field({ resolve: parent => parent.X })` passthrough; there is zero
inline business logic, zero local type definitions, and zero enum
re-registration. The two shared enums (`SessionStatusPothosEnum`,
`SurahJuzRefPothosEnum`) are imported as VALUES from the ONCE-registered
`backend/graphql/pothos/shared/enum.pothos.ts` and referenced on enum
fields by `t.expose(..., { type })` — no per-field mapping helper is
needed because the task-2.1 ReturnType shapes already carry the canonical
TS enum members (not raw pgEnum strings, unlike the participant
`session` / `home_work` objects which need exhaustive mappers).

Field nullability matches the TS types EXACTLY — every nullable TS field
becomes a nullable GraphQL field, every non-null TS field becomes a
non-null GraphQL field. The four entity-shaped objects expose `id` first
(`t.exposeID("id")` → `ID!`) for Apollo cache normalization. The three
page-wrapper objects and the two composite value objects
(`ParentHomeworkTrack`, `ParentHomeworkPosition`, `ParentChildProgress`)
carry no row id and expose their structural fields directly.

The existing participant objects (`SessionPothosObject`,
`SessionReportPothosObject`, `SessionHomeWorkPothosObject`) are NOT
touched — `git diff --name-only` confirms none of
`backend/graphql/pothos/classes/session.pothos.ts`,
`report.pothos.ts`, or `home-work.pothos.ts` appear in the task's
footprint (D4 / REQ-031 honored).

## Notes on convention adherence

- **Sibling-pattern fidelity** — the file mirrors the
  `parent-link-request.pothos.ts` conventions: module-level JSDoc
  header documenting the single-canonical-object-type pattern +
  BOPLA + Apollo `id`-first + ONCE-registered enum discipline; one
  `objectRef<...ReturnType>("GraphQLName").implement({ fields: t => ({ ... }) })`
  per type; per-object JSDoc block describing the projection's
  domain behavior; NO barrel in the parents directory (transitive
  registration via the query layer, matching the sibling precedent).
- **No per-field enum mapper** — unlike the participant
  `session.pothos.ts` and `home-work.pothos.ts` (which need
  exhaustive `toSessionStatus` / `toSurahJuzRef` switch helpers
  because their `*ReturnType` types carry raw pgEnum string unions),
  this file uses pure `t.expose("status", { type: SessionStatusPothosEnum })`
  passthroughs. The task-2.1 ReturnType shapes already carry the
  canonical TS enum members (the service's fail-closed narrowing
  helpers `toSessionStatus` / `toSurahJuzRef` in
  `parent-monitoring.helpers.ts` produce them before the row reaches
  the GraphQL layer). This is the simpler, more type-safe pattern —
  zero inline business logic in the Pothos file.
- **Nested object refs via `t.field`** — single-nested object refs
  (`ParentHomeworkEntry.jadid`/`.madi`, `ParentChildProgress.child`/
  `.latestJadidPosition`/`.latestMadiPosition`) use
  `t.field({ type: <Ref>, nullable?: true, resolve: parent => parent.X })`.
  Array-of-object-refs (`Parent*Page.items`) use
  `t.field({ type: [<Ref>], resolve: parent => parent.items })` —
  Pothos accepts the `readonly` array directly (the `SessionPagePothosObject`
  precedent at `backend/graphql/pothos/classes/session.pothos.ts:230-240`
  confirms this).
- **`readonly` array passthrough** — the `*PageReturnType.items`
  members are `readonly ...EntryReturnType[]` (task 2.1 closed-shape
  discipline). Pothos's `t.field({ type: [<Ref>], resolve: parent =>
  parent.items })` accepts the readonly array without a spread —
  verified by tsgo (zero errors). No `[...parent.items]` spread is
  needed (the `SessionPagePothosObject` precedent confirms).
