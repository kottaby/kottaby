## Implementation Note — `home-work.repository.ts` standalone SQL column qualification

The prior subagent's commit (`44300d1`, "test(parents): service tests pass
(126); repo/wire/UI test files authored") shipped a fix to the standalone
`HomeWorkRepository.listForStudent` SQL: every column in the SELECT list
is qualified with the `hw.` alias (`hw.id`, `hw.session_id`,
`hw.current_from_ayah`, …). Without the qualification, PostgreSQL (and
pglite) raise `42702` (ambiguous column) when a bare column name exists
in both sides of a JOIN — and `session_id` exists on both `home_work`
and `session`. The pglite executor would surface the ambiguity the
moment the parent-portal sibling test ran a cross-student isolation
probe. This task VERIFIED the fix holds (the `home-work.parent.repository.test.ts`
suite passes 14/14 with zero ambiguity errors); no further change to
the implementation file was required.

The Drizzle branch (which the parent-portal service uses by default
through the transactional path) was already explicit per-column and
needed no change. The fix is scoped to the SELECT list of the
standalone `listForStudent` SQL only (lines 261-267 of
`backend/db/repo/classes/home-work.repository.ts`).

Sub-loop on `backend/db/repo/classes/home-work.repository.ts`: exit 0
(tsgo + oxlint + biome:check + lint:type-aware + check:duplicates all
passed). No regression on the pre-existing home-work tests (21/21 pass).

## Testing Discipline

Per `backend/db/test/AGENTS.md` (repo-test rules) and the carry-forward
from task 2.2 / 2.3:

- Every test body wraps in `runInRollback(async tx => { ... })` — `tx`
  is the LAST parameter on every repo call under test, every
  entity-setup helper, and every direct Drizzle query.
- A separate committed-fixture group covers the STANDALONE executor
  branch (`tx ?? db` or `queryDb`-only). That branch by definition runs
  without a transaction, so the fixture must be committed (an
  uncommitted row is invisible outside the tx); it is registered and
  hard-deleted in `afterAll` (rule 9), keeping the repo/ directory's
  100%-coverage mandate (rule 14) honest.
- No `expect(...).rejects.toThrow()` inside `runInRollback` — the
  read pairs under test are total and never reject, so the
  try/catch helper is unused here (would deadlock the tx if applied).
- Entities are created ONLY via `backend/db/test/entity-setup.ts`
  helpers (`createTestUser`, `createTestStudent`, `createTestParent`,
  `createTestTeacherRow`, `createTestSession`, `createTestSessionReport`,
  `createTestHomeWork`) plus file-local fixture builders — NEVER seed
  data.
- Hard-delete cleanup in `afterAll` follows FK-dependency order
  (sessions cascade reports/homework; users cascade students/teacher);
  a teardown-proof assertion (`expect(await Repo.method(...)).toBe(0)`)
  confirms the standalone read returns zero after the cascade.

#### Tier 2 — boundary arms

- Empty window — parent with zero linked children / student with zero
  reports / homework / progress rows yields `[]` (lists) or `0`
  (counts), NEVER `null` and NEVER a thrown miss.
- Offset beyond the end of the filtered set yields `[]` next to an
  honest total > 0 (predicate cohesion: the count does not drop with
  the offset).
- `session.started_at` NULL ordering — NULLS LAST pins scheduled
  sessions (no `started_at`) AFTER live sessions in the DESC scan
  (report + homework pairs).
- Same-instant `started_at` rows deterministic by the `id DESC`
  tiebreak across pages (report + homework pairs).
- `listLinkedChildrenByParentId` — explicit `createdAt` timestamps
  drive the ASC ordering (oldest first); same-instant rows
  deterministic by the `id ASC` tiebreak.
- Fully-null Jadid/Madi track blocks survive the projection verbatim
  (no fabricated zeros — every nullable column preserved as `null`).

#### Tier 3 — chaos

- Cross-student / cross-parent isolation — a child linked to parent B
  never appears in parent A's list; a report / homework row whose
  session belongs to a DIFFERENT student is NOT surfaced (the INNER
  JOIN predicate guarantees this); a different student's progress rows
  never inflate this student's count.
- Concurrent inserts via `Promise.allSettled` against one parent /
  student inside one transaction cannot corrupt a window — every
  settled write lands, no duplicates, no lost rows. Verified for all
  four repos.
