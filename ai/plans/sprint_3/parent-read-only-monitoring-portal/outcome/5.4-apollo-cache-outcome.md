## Summary

Registered the six no-`id` GraphQL portal types from plan §3.1 in the
Apollo `InMemoryCache` `typePolicies` registry, opting each out of
normalization via `keyFields: false`. This prevents Apollo's
"Cache data may be lost" warnings when these embedded shapes are
written to the cache via different parent objects, and preserves the
per-entity cache identity of the `id`-carrying `*Entry` row objects
nested inside each `*Page` wrapper's `items` array.

The four `id`-carrying portal types (`ParentLinkedChild`,
`ParentAttendanceEntry`, `ParentReportEntry`, `ParentHomeworkEntry`)
are deliberately NOT registered — they keep Apollo's default
`id`-based normalization so each row normalizes into its own cache
identity (the load-bearing mechanism for cross-query row reuse and
per-child cache isolation).

To keep the factory function under the oxlint
`max-lines-per-function` budget (75 executable lines, comments and
blank lines skipped), the entire `typePolicies` registry was hoisted
out of `createApolloCache` into a single module-level
`apolloCacheTypePolicies: TypePolicies` const. The factory now reads
as a one-liner, and the registry reads as a flat, comment-anchored
table of every no-`id` opt-out in the codebase. All existing entries
and their inline comments are preserved verbatim (only the indentation
nesting changed).

## The `keyFields: false` policy explanation

Apollo's `InMemoryCache` normalizes every object that flows through
its responses by default, using a `__typename` + `id` (or
user-supplied `keyFields`) tuple as the cache key. When an object
type lacks an `id` field, normalization either falls back to index
paths (and emits "Cache data may be lost" warnings when the same
shape is written through different parents) or — worse — silently
collapses distinct embedded rows that happen to share field values.

The parent monitoring-portal read model ships six no-`id` GraphQL
types (plan §3.1). They fall into two structural buckets, both
correctly handled by `keyFields: false`:

1. **Pagination wrappers** — `ParentAttendancePage`,
   `ParentReportPage`, `ParentHomeworkPage`. Each is a small envelope
   (`{ items: [...Entry!]!, totalCount, page, pageSize }`) whose
   normalizable entities are the `id`-carrying `*Entry` rows inside
   `items`. The wrapper itself has no `id` and is re-emitted wholesale
   on every refetch (page / pageSize / filter changes legitimately
   yield different arrays). Marking the wrapper `keyFields: false`
   keeps Apollo from trying to normalize the envelope, while the
   nested `*Entry` rows still normalize normally into their own cache
   identities.

2. **Embedded value objects** — `ParentHomeworkTrack`,
   `ParentHomeworkPosition`, `ParentChildProgress`. Each is a
   composite read view cached inline under its enclosing query field
   (`parentChildProgress`, `parentChildHomework`) or its parent
   object (`ParentHomeworkEntry.jadid` / `ParentHomeworkEntry.madi`).
   They carry no `id` and are replaced wholesale on every refetch. The
   parent's per-child reads are re-keyed by the `studentId` argument,
   so embedded rows never leak across children — `parentChildProgress`
   for student A is stored under a different cache reference than for
   student B (the query field's `variables` feed the cache key path).

This pattern is the established convention for every no-`id` type in
the codebase — see `NotificationListPage`, `AdminAuditLogPage`,
`HandshakeCodeLookup`, `HealthCheck`, the `PlatformAnalytics*`
family, and `OnlineMeetingInfo` (all preserved verbatim in this same
file).
