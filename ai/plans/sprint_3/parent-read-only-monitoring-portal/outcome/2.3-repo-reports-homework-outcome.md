## Summary

Added the `listForStudent` / `countForStudent` read pair to both `ReportRepository` and `HomeWorkRepository`, scoped to a parent's gated student via an INNER JOIN onto the owning `session` row. Each pair shares ONE module-scope JOIN-condition builder (`buildParentScopedReportJoinCondition` / `buildParentScopedHomeWorkJoinCondition`) so the paged window and the honest total can never describe different filtered sets — the count cannot drift from the list. The join folds the relationship predicate (`reports.session_id = session.id` / `home_work.session_id = session.id`) and the tenancy predicate (`session.student_id = $studentId`) into a single ON clause; because both foreign keys are NOT NULL with `ON DELETE CASCADE` and carry UNIQUE constraints, the INNER JOIN cannot fan out, so no cross-student row can ever surface.

Both repos return RAW select rows; the parent-shaped projection mapping (raw `reports ⋈ session` row → `ParentReportEntryReturnType`, raw `home_work` row → `ParentHomeworkEntryReturnType` with jadid/madi track blocks) happens in the service helpers (plan §4.2 / task 2.4) — never in the repo. The existing `HomeWorkRepository.findLatestByStudentId` (the D3 reuse target that feeds `ParentHomeworkPositionReturnType`) is left UNCHANGED — verified by grep-diff (zero `-`/`+` lines mention it).

Ordering is `session.started_at DESC NULLS LAST, <table>.id DESC` on both pairs — the NULLS LAST clause pins scheduled-but-not-started sessions after live sessions in the newest-first scan, and the id tiebreak keeps same-instant rows deterministic across pages. Pagination is offset-based via bound LIMIT/OFFSET parameters; an offset past the end yields an empty array next to the true total reported by the count companion.

## The shared predicate extract

### Report pair — `buildParentScopedReportJoinCondition`

```typescript
/**
 * ONE module-scope JOIN-condition builder shared by `listForStudent` and
 * `countForStudent`: folds together the relationship predicate
 * (`reports.session_id = session.id`) and the tenancy predicate
 * (`session.student_id = $studentId`). Both methods apply this exact
 * fragment as the INNER JOIN's ON clause, so the paged window and the
 * honest total describe the same filtered set — the count can never
 * diverge from the list.
 *
 * Because `reports.session_id` is NOT NULL with `ON DELETE CASCADE` and
 * carries a UNIQUE constraint, the INNER JOIN cannot fan out — one report
 * row matches exactly one session row — so the count over the JOIN equals
 * the count over the bare `reports` table scoped by the same tenancy
 * predicate. No cross-student row can ever surface: the tenancy equality
 * is fused into the JOIN condition itself.
 */
function buildParentScopedReportJoinCondition(studentId: number): SQL {
  return sql.join([eq(session.id, reports.sessionId), eq(session.studentId, studentId)], sql` and `);
}
```

The `sql.join([...], sql\` and \`)` pattern returns a non-undefined `SQL` fragment (matching the `session.repository.helpers.ts` `buildParticipantPredicate` precedent), avoiding any `!` non-null assertion that would trip `no-unsafe-type-assertion`. Both the list and the count call the SAME builder with the SAME `studentId` argument — the predicate is mechanically incapable of drifting between the two.

## The JOIN + ORDER BY

### Report pair

**List (Drizzle transactional branch):**
```typescript
tx
  .select({
    id: reports.id,
    sessionId: reports.sessionId,
    teacherNotes: reports.teacherNotes,
    studentRatingByTeacher: reports.studentRatingByTeacher,
    createdAt: reports.createdAt,
    updatedAt: reports.updatedAt,
    sessionStatus: session.status,
    sessionStartedAt: session.startedAt,
  })
  .from(reports)
  .innerJoin(session, buildParentScopedReportJoinCondition(studentId))
  .orderBy(sql`${session.startedAt} DESC NULLS LAST`, desc(reports.id))
  .limit(limit)
  .offset(offset);
```

**List (standalone queryDb branch):**
```sql
SELECT r.id, r.session_id AS "sessionId", r.teacher_notes AS "teacherNotes",
       r.student_rating_by_teacher AS "studentRatingByTeacher",
       r.created_at AS "createdAt", r.updated_at AS "updatedAt",
       s.status AS "sessionStatus", s.started_at AS "sessionStartedAt"
FROM reports r
INNER JOIN session s ON s.id = r.session_id AND s.student_id = $1
ORDER BY s.started_at DESC NULLS LAST, r.id DESC
LIMIT $2 OFFSET $3
```
Params: `[studentId, limit, offset]`.

**Count (standalone queryDb branch):**
```sql
SELECT count(*) AS "value"
FROM reports r
INNER JOIN session s ON s.id = r.session_id AND s.student_id = $1
```
Params: `[studentId]`.

## Notes on convention adherence

- **Shared predicate pattern** mirrors `session.repository.helpers.ts`'s `buildParticipantPredicate` (one module-scope function consumed by both `listParticipantSessions` and `countParticipantSessions`). The `sql.join([...], sql\` and \`)` form returns a non-undefined `SQL` (vs. `and(...)` which returns `SQL | undefined`), avoiding any `!` non-null assertion that would trip `no-unsafe-type-assertion`. This is the same idiom the session repository uses.
- **Raw row interface precedent** matches `audit-trail.repository.ts:75`'s `AuditTrailEntryRow` — a module-local `export interface` describing the raw JOIN row, with the service layer owning the raw-row → ReturnType mapping. The `sessionStatus: SessionSelectType["status"]` typing carries the raw pgEnum string union (NOT the `SessionStatus` TS enum), matching how `AuditTrailEntryRow.actionType: string` carries the raw pgEnum string; the service's fail-closed guard narrows it.
- **INNER JOIN vs EXISTS semi-join** — the existing `findLatestByStudentId` uses an EXISTS semi-join (`WHERE EXISTS (SELECT 1 FROM session s WHERE s.id = home_work.session_id AND s.student_id = $1)`). For the list/count pair, I use INNER JOIN because (a) the task description explicitly mandates "INNER JOIN reports ⋈ session ON session_id AND session.student_id = $1", and (b) the list needs the joined session's `status` and `started_at` columns for projection (report) and ordering (both), which a semi-join cannot surface. The count uses the same INNER JOIN (not a bare-table count) so the predicate is mechanically identical between list and count — no drift surface.
- **NULLS LAST ordering** — `session.started_at` is nullable (scheduled sessions have no `started_at` yet). PostgreSQL's default for `DESC` is `NULLS FIRST`, which would float not-yet-started sessions to the top of the newest-first scan. The `NULLS LAST` clause pins them after live sessions — the parent portal's "newest session first" UX contract. Drizzle's `desc()` helper does not emit `NULLS LAST`, so the ORDER BY uses a `sql\`${session.startedAt} DESC NULLS LAST\`` template fragment (raw SQL) for the transactional branch and the literal `DESC NULLS LAST` in the standalone SQL.
- **`findLatestByStudentId` UNCHANGED (D3)** — verified by grep-diff (zero `-`/`+` lines touch it). Its EXISTS semi-join ordering (`created_at DESC, id DESC`) is the homework-stamp-first convention for the latest-row probe; my new `listForStudent` uses session-stamp-first ordering (`session.started_at DESC NULLS LAST, id DESC`) per the task spec. The two orderings serve different purposes (latest-by-creation vs chronological-by-session-start) and do not conflict.
