## The `authScopes` conjunction (load-bearing)

```typescript
const parentOnlyAuthScopes: { $all: { authenticated: true; role: UserRole[] } } = {
  $all: {
    authenticated: true,
    role: [UserRole.Parent],
  },
};
```

Every field references this single shared const so the conjunction
cannot drift between registrations (the rationale
`query/classes/session-lifecycle.query.ts` applies for factory-style
deduplication of the auth expression). The `$all` conjunction is
load-bearing:

- A PLAIN `{ authenticated: true, role: [UserRole.Parent] }` map (no
  `$all` wrapper) is WRONG in @pothos/plugin-scope-auth's default
  strategy — Pothos combines the keys of ONE scope map with ANY
  semantics, so ANY authenticated caller would pass through the first
  satisfied scope and non-parents would be granted access.
- The `$all` wrapper makes BOTH conditions mandatory: anonymous
  callers hit the `authenticated` scope's `UnauthorizedError` throw
  (extensions.code `UNAUTHORIZED` / 401 — explicit scope throws pass
  through `builder.ts`'s `unauthorizedError` mapping VERBATIM), while
  authenticated callers with a wrong role (admin, teacher, student)
  fail the `role` scope into the canonical localized `ForbiddenError`
  (`FORBIDDEN` / 403, mapped at `builder.ts:111-121`).
- `UserRole` is imported as a VALUE (not `import type`) — it is
  referenced in the runtime scope expression `[UserRole.Parent]`.
- The const is declared WITHOUT `as const` so the `role` member
  widens to `UserRole[]` (the type slot Pothos's `AuthScopes` accepts).
  A `readonly [UserRole.Parent]` tuple would fail the field-scope
  assignment (tsgo error TS2322 — verified by the first sub-loop run
  during this task).

## The `if (!ctx.user)` narrowing branch (per plan §3.2 template)

Every resolver carries the identical TypeScript-narrowing branch
(matching the verbatim pattern in plan §3.2 and the sibling
`query/parents/parent-link.query.ts:74-77`):

```typescript
resolve: async (_root, args, ctx) => {
  // The `$all { authenticated: true }` scope guarantees a verified
  // user row at resolution time (anonymous callers never get past
  // the scope step). This branch exists purely for TypeScript
  // narrowing — the repo-wide no-non-null-assertion rule forbids
  // dereferencing the nullable context directly. Unreachable in
  // practice; per the resolver-i18n rule the message flows through
  // ctx.t (its en copy is identical to builder.ts's `authenticated`
  // scope literal).
  if (!ctx.user) {
    const tErrors = await ctx.t("errorsTranslations");
    throw new UnauthorizedError(tErrors.unauthorized);
  }
  return ParentMonitoringService.listChildReports(
    ctx.user.id,
    args.studentId,
    { page: args.page ?? undefined, pageSize: args.pageSize ?? undefined },
    ctx.locale
  );
},
```

The branch is **reachable** in the type system (anonymous callers
would reach it if the scope layer were bypassed — defense-in-depth),
but **unreachable in practice** because the `$all { authenticated: true }`
scope throws `UnauthorizedError` before the resolver body executes.
The thrown message is localized via `ctx.t("errorsTranslations")` —
`ctx.t` is bound to `ctx.locale` in `gqlContextFactory.ts:236`, so
both `en` and `ar` clients receive the localized `unauthorized`
string from the canonical `ErrorsLabels` namespace
(`shared/locale/types/errors/labels.ts:43`).

## Notes on convention adherence

- **Shared `parentOnlyAuthScopes` const** mirrors the
  `session-lifecycle.query.ts` factory rationale ("the authScopes
  conjunction is built HERE and only here, so the explicit
  `$all { authenticated, role }` semantics can never drift between
  registrations"). The const is referenced by every field's
  `authScopes: parentOnlyAuthScopes` — single source of truth for
  the conjunction. A full factory extraction (the
  `registerParticipantSessionsField` precedent) was considered but
  rejected: the three list-page fields differ in their return types
  (`ParentAttendancePageReturnType` / `ParentReportPageReturnType` /
  `ParentHomeworkPageReturnType`), so a generic factory would require
  `ObjectRef<TReturn>` typing that adds complexity without reducing
  the duplication meaningfully (the resolver bodies are 6-line
  narrowing + delegation blocks, not the 30-line boilerplate that
  warranted the session-lifecycle factory). The shared const +
  inline narrowing matches the sibling `parent-link.query.ts`
  convention exactly.
- **`??` undefined coercion** on `args.page` / `args.pageSize` — the
  Pothos `t.arg.int()` produces a nullable `Int` arg whose runtime
  value is `number | null | undefined`. The service's
  `ParentPageInput` shape uses optional members (`page?: number`),
  which accept `number | undefined` but NOT `null`. The
  `args.page ?? undefined` coercion normalizes `null` to `undefined`
  without falsy-coercing a legitimate `0` (page 0 is a valid client
  input — the service clamps it to 1). This mirrors the
  `session-lifecycle.query.ts:146` pattern
  (`args.page ?? 1`).
- **Per-student `studentId: t.arg.int({ required: true })`** — the
  plan §3.2 template's exact arg shape. The `required: true` makes
  the arg non-null (`Int!`), so GraphQL validation rejects
  non-integer inputs BEFORE the resolver ever runs (BOLA defense at
  the schema layer). A malformed integer (≤0) reaches the resolver
  and is forwarded to the service, where `requireLinkedChild`'s
  `!Number.isSafeInteger(studentId) || studentId <= 0` arm denies
  with the constant 403 shape (oracle posture — task 2.4).
- **`ctx.t("errorsTranslations")`** — the resolver-i18n rule
  (`backend/graphql/AGENTS.md`): direct errors in resolvers MUST use
  `ctx.t("<namespace>")` (already bound to `ctx.locale` in
  `gqlContextFactory.ts:236`), NOT `getServerTranslations` or
  `next-intl`. The `errorsTranslations` namespace carries
  `unauthorized` and `forbidden` keys
  (`shared/locale/types/errors/labels.ts:43-44`). The
  `if (!ctx.user)` branch throws the localized `UnauthorizedError`
  via `tErrors.unauthorized`.
- **No `try/catch` in resolvers** — per the
  `backend/graphql/AGENTS.md` masking rule, the boundary finalizer
  (`finalizeGraphqlErrors`) owns masking + the single correlated log
  line. DomainErrors thrown deeper (the service's `ForbiddenError`
  from `requireLinkedChild` or `requireActor`) propagate uncaught —
  the finalizer classifies them as domain pass-through so
  `extensions.code = FORBIDDEN` survives serialization.
- **Static imports only** — per the Bun ESM rule
  (`backend/graphql/AGENTS.md` and `.agents/instructions/backend.instructions.md`):
  dynamic `await import(...)` expressions in resolver trees are
  prohibited (they mark the module tree as async ESM, breaking
  CommonJS `require()` consumers of `graphql`). All imports are
  top-level STATIC.
