## Summary

Added two new read-only repository methods backing the parent-monitoring
portal's linked-children list and child-progress count surfaces. Both
methods are pure data-access — zero permission logic, zero writes, zero
business rules — matching the namespace-member style, `tx`-last
convention, and dual-executor pattern established by the sibling repos
in the same directories.

- `StudentRepository.listLinkedChildrenByParentId(parentId, tx?)` —
  joins `students → users` on the shared PK, scoped by the `parent_id`
  grant and severed by `users.is_deleted = false`. Returns rows
  projecting directly to `ParentLinkedChildReturnType` (id, fullName,
  createdAt). Stable order `created_at ASC, id ASC`.
- `ProgressRepository.countForStudent(studentId, tx?)` — counts
  `progress` rows by `student_id`, mapped to a JavaScript `number` on
  both executor branches.

## Exact SQL Predicates & Column Lists

### `StudentRepository.listLinkedChildrenByParentId`

**Drizzle select branch** (`tx ?? db`):
```typescript
(tx ?? db)
  .select({ id: students.id, fullName: users.fullName, createdAt: students.createdAt })
  .from(students)
  .innerJoin(users, eq(users.id, students.id))
  .where(and(eq(students.parentId, parentId), eq(users.isDeleted, false)))
  .orderBy(asc(students.createdAt), asc(students.id));
```

**Predicate (both branches):** `students.parent_id = $parentId AND users.is_deleted = false`
**Column list (explicit, no `SELECT *`):** `students.id`, `users.fullName`, `students.createdAt`
**Order:** `students.created_at ASC, students.id ASC` (stable; id tiebreak guarantees determinism)
**Index:** rides `students_parent_id_idx` (`students.ts:41`) for the `parent_id` equality scan
**Severance guard:** `users.is_deleted = false` excludes soft-deleted children from the list
**Return type:** `Promise<ParentLinkedChildReturnType[]>` — rows structurally match the projection; the service layer applies the readonly projection mapping (spread + freeze, no enum re-typing needed)

### `ProgressRepository.countForStudent`

**Transactional branch** (Drizzle):
```typescript
tx.select({ count: sql<number>`count(*)`.mapWith(Number) })
  .from(progress)
  .where(eq(progress.studentId, studentId));
```

**Non-transactional branch** (raw SQL via `queryDb`):
```sql
SELECT count(*) AS count FROM progress WHERE student_id = $1
```

**Predicate:** `progress.student_id = $studentId`
**Index:** rides `progress_student_id_idx` (`progress.ts:33`)
**Count mapping:** `.mapWith(Number)` on the Drizzle branch; `Number(...)` on the raw-SQL branch — both convert PostgreSQL's bigint-as-string `count(*)` result to a JavaScript `number`
**Return type:** `Promise<number>`

## Design Decisions & Deviations

### Decision 1: `listLinkedChildrenByParentId` uses `tx?: DBTransaction` + `(tx ?? db)` pattern (not `tx?: DBQueryExecutor` + dual-branch `queryDb`)

**Task spec said:** `tx?: DBQueryExecutor`, "bare reads go through
`queryDb(tx)`".

**Implemented:** `tx?: DBTransaction`, `(tx ?? db)` Drizzle-select
pattern (no `queryDb` raw-SQL branch).

**Rationale:**
1. The sibling `listDirectory` method in the SAME file (lines 565-607)
   — the only other JOIN-query read in `student.repository.ts` — uses
   `tx?: DBTransaction` + `(tx ?? db)` with the Drizzle builder. My
   method is also a JOIN query (students ⋈ users), so matching the
   `listDirectory` pattern is the established sibling convention for
   join-projected reads.
2. The `queryDb` dual-branch pattern (used by `findById`,
   `findHandshakeCodeByStudentId`) is reserved for simple
   single-equality lookups in this file. The task instruction to "READ
   sibling repos to match the EXACT pattern they use" resolves in
   favor of the `listDirectory` pattern for JOIN queries.
3. The file was at 293/300 code lines (oxlint `max-lines: 300,
   skipComments: true, skipBlankLines: true`). The `queryDb`
   dual-branch pattern adds ~18 code lines (exceeding the budget);
   the `(tx ?? db)` single-branch pattern adds ~7 code lines (fitting
   the budget at 300/300). The compact `(tx ?? db)` pattern was
   necessary to avoid extracting to a sibling helpers file (which
   would violate the "only 3 files" scope restriction).
4. **Practical behavior is identical**: the service layer (task 2.4)
   passes `DBTransaction` (from `withTransaction`) or `undefined` —
   never a raw `Pool` or `PoolClient`. The `DBTransaction` type is a
   subset of `DBQueryExecutor`, so the service's existing
   `withTransaction` callback (which yields a `DBTransaction`) passes
   through without narrowing. The `findById` method (which takes
   `DBQueryExecutor`) is unchanged — callers that need the wider
   union still have it.

### Decision 2: `countForStudent` uses `tx?: DBQueryExecutor` + dual-branch `queryDb`/Drizzle pattern

**Task spec said:** `tx?: DBQueryExecutor`, `SELECT count(*) FROM
progress WHERE student_id = $1`, `.mapWith(Number)`.

**Implemented:** Exactly as specified — dual-branch pattern with
`queryDb` on the non-transactional branch and Drizzle select on the
transactional branch. The count is mapped to `number` via
`.mapWith(Number)` (Drizzle branch) and `Number(...)` (raw-SQL branch).

**Rationale:** `progress.repository.ts` is a new file with no
max-lines pressure. The dual-branch `queryDb`/Drizzle pattern matches
the task spec exactly and is consistent with the sibling
`report.repository.ts` / `home-work.repository.ts` simple-lookup
methods (`findBySessionId`, `existsReportForSession`).

### Decision 3: No separate `ParentLinkedChildRow` interface — return type is `ParentLinkedChildReturnType` directly

**Task spec said:** "rows projecting to `ParentLinkedChildReturnType`".

**Plan §4.1 said:** `Promise<ParentLinkedChildRow[]>`.

**Implemented:** `Promise<ParentLinkedChildReturnType[]>` — no
separate row interface.

**Rationale:**
1. The select columns (`id`, `fullName`, `createdAt`) match the
   `ParentLinkedChildReturnType` projection shape exactly — there is no
   column-name aliasing, no enum re-typing, no Omit of forbidden
   fields. A separate row interface would be structurally identical to
   the projection type.
2. The 2.1 outcome carry-forward said "the repo returns the raw select
   columns (`id`, `fullName` via `users.fullName`, `createdAt`)" and
   "the mapping (Drizzle row → readonly projection) happens at the
   service layer". Since the shapes are identical, the "mapping" is a
   no-op — the service can use the rows directly as
   `ParentLinkedChildReturnType` (readonly fields are covariant, so a
   mutable Drizzle row is assignable to a readonly projection type).
3. Defining a separate `ParentLinkedChildRow` interface would add 5
   code lines to `student.repository.ts`, pushing the file over the
   300-code-line `max-lines` budget. Using the projection type
   directly avoids this.
4. The `AdminStudentDirectoryRow` precedent (inline row interface at
   line 116) exists because that row has DIFFERENT field names than
   its projection (`name` vs `fullName`, plus extra columns). My case
   has no such divergence, so no separate row type is needed.

### Decision 4: `countForStudent` uses `sql<number>\`count(*)\`.mapWith(Number)` (not `count(*)::int`)

**Task spec said:** `.mapWith(Number)`.

**Codebase pattern:** `sql<number>\`count(*)::int\`.as("count")` (20+
occurrences across `student.repository.ts`, `audit-trail.repository.ts`,
`teacher.repository.ts`, `applicant.repository.ts`,
`admin-user.repository.ts`, `platform-analytics.repository.ts`).

**Implemented:** `sql<number>\`count(*)\`.mapWith(Number)` on the
Drizzle branch; `Number(result.rows[0]?.count ?? 0)` on the raw-SQL
branch. No `::int` cast in either branch.

**Rationale:** The task explicitly specified `.mapWith(Number)`. The
`AGENTS.md` doc states "Avoid raw database-specific casts (like
`CAST(... AS INTEGER)`) in SQL" and recommends `.mapWith(Number)`.
While the codebase has legacy `::int` casts, the doc-compliant
approach is `.mapWith(Number)`. Both approaches produce the same
result (a JavaScript `number`); the `.mapWith(Number)` approach is
provider-agnostic (no PostgreSQL-specific `::int` syntax). The
raw-SQL branch uses `Number(...)` in JavaScript (not a SQL cast) to
achieve the same result without a database-specific cast.

## Carry-forward knowledge for task 2.4 (ParentMonitoringService)

### Calling `listLinkedChildrenByParentId`
- Import: `StudentRepository` from `@/backend/db/repo` (or deep-import
  from `@/backend/db/repo/students/student.repository`).
- Signature: `listLinkedChildrenByParentId(parentId: number, tx?:
  DBTransaction): Promise<ParentLinkedChildReturnType[]>`.
- The `parentId` is the parent actor's user id (`ctx.user.id` from the
  GraphQL context, or the service's `parentActorId` parameter).
- The method returns rows that ARE `ParentLinkedChildReturnType`
  (structurally identical) — the service can return them directly
  without a mapping step. If the service wants to enforce readonly at
  runtime, it can spread + `Object.freeze` each row, but this is
  optional (the TS type system already enforces readonly at compile
  time).
- The method accepts `tx?: DBTransaction` (not `DBQueryExecutor`).
  Inside the service's `withTransaction` callback, pass the `tx`
  directly. For the zero-arg `listLinkedChildren` service method
  (which has no per-student gate), the service can call
  `listLinkedChildrenByParentId(parentActorId)` without a `tx` (the
  method falls back to the global `db` handle).

### Calling `countForStudent`
- Import: `ProgressRepository` from `@/backend/db/repo` (or
  deep-import from `@/backend/db/repo/classes/progress.repository`).
- Signature: `countForStudent(studentId: number, tx?:
  DBQueryExecutor): Promise<number>`.
- The method accepts `DBQueryExecutor` (the wider union). Inside the
  service's `withTransaction` callback, pass the `tx` (which is a
  `DBTransaction`, a subset of `DBQueryExecutor`).
- Returns a plain `number` — use it directly as
  `progressRowCount` in `ParentChildProgressReturnType`.

### `tx` type mismatch between the two methods
- `listLinkedChildrenByParentId` takes `tx?: DBTransaction` (narrower).
- `countForStudent` takes `tx?: DBQueryExecutor` (wider).
- Inside the service's `withTransaction(async tx => { ... })`, the `tx`
  is a `DBTransaction`. It can be passed to BOTH methods without
  narrowing (DBTransaction is assignable to both `DBTransaction` and
  `DBQueryExecutor`).

### Gate ordering (D11 TOCTOU seal)
- For `getChildProgress`: open ONE `withTransaction`, run
  `requireLinkedChild(parentActorId, studentId, locale, tx)` first,
  then `StudentRepository.findById(studentId, tx)` (for the child
  echo) + `ProgressRepository.countForStudent(studentId, tx)` +
  `HomeWorkRepository.findLatestByStudentId(studentId, tx)` (for the
  latest positions) — all inside the same transaction snapshot.
- For `listLinkedChildren` (zero-arg, no per-student gate): call
  `listLinkedChildrenByParentId(parentActorId)` without a `tx` (no
  transaction needed — the method reads the parent's own children, no
  gate required; `requireActor(parentActorId, UserRole.Parent, locale,
  undefined, false)` is the only auth check).
