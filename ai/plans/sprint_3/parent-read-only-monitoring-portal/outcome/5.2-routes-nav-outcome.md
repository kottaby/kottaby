## The guard pattern (verbatim)

Both route files use the SAME `withPageAuth` invocation, mirroring the
handshake-route precedent (`app/(dashboard)/parent/handshake/page.tsx:33-36`):

```ts
await withPageAuth({ roles: [UserRole.Parent], redirectTo: "/parent/children" });
```

`withPageAuth` (in `frontend/lib/auth/withPageAuth.ts`):

1. Calls `getServerUserContext()` to read the httpOnly `access_token`
   cookie (the redirect-loop fix — never rebuilds an absolute URL off
   `localhost`).
2. If the caller is anonymous → redirects to
   `/login?redirect=<currentPath>` (or the `redirectTo` option).
3. If `roles` is supplied and the caller's `ctx.role` is NOT in the
   whitelist → redirects to the caller's ROLE-SPECIFIC dashboard via
   `roleDashboardRoute.ts` (never the bare `/dashboard` dispatcher —
   avoids the preview-gateway trailing-slash loop).
4. Otherwise → returns `{ userId, user, role }` (the verified user
   context). The route shells in this task do NOT consume the return
   value — the guard's side-effect (redirect-on-fail) is the only
   thing the shell needs.

Non-parent roles (Admin / Teacher / Student) NEVER reach the portal
views: `withPageAuth` redirects them to their own role dashboard
before the page body runs.

## The async-params / searchParams contract (Next.js 16)

Verified against `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/dynamic-routes.md` + `page.md` before writing any code:

- **`params`** is a `Promise<{ studentId: string }>` — must be awaited
  (`const { studentId } = await params`). The dynamic-segment value
  arrives as `string` (broad type — users can enter any URL).
- **`searchParams`** is a `Promise<{ [key: string]: string | string[] | undefined }>`
  — must be awaited. Each value can be a single string, an array of
  strings (repeated param), or `undefined` (absent).

The route shells type their props inline as:

```ts
interface ParentChildrenPageProps {
  readonly searchParams: Promise<Record<string, string | string[] | undefined>>;
}

interface ParentChildDetailPageProps {
  readonly params: Promise<{ readonly studentId: string }>;
  readonly searchParams: Promise<Record<string, string | string[] | undefined>>;
}
```

The `Record<string, string | string[] | undefined>` form for
`searchParams` mirrors the audit-trail route precedent
(`app/(dashboard)/audit/page.tsx:128-130`). The
`Promise<{ readonly studentId: string }>` form for `params` mirrors
the admin user-detail route precedent
(`app/(dashboard)/admin/users/[id]/page.tsx:29-31`).

## The integer-coercion + redirect posture (detail page)

The `[studentId]` path segment arrives as `string`. The server shell
coerces it via `Number(rawId)` and validates:

```ts
const parsedId = Number(rawId);
if (!Number.isSafeInteger(parsedId) || parsedId <= 0) {
  redirect("/parent/children");
}
```

Behavior matrix (verified by reading the `Number` / `Number.isSafeInteger`
contract):

| Raw `studentId` | `Number(rawId)` | `isSafeInteger && > 0`? | Action |
|---|---|---|---|
| `"123"` | `123` | `true` | Render container with `studentId={123}` |
| `"0"` | `0` | `false` (`0 > 0` is false) | redirect `/parent/children` |
| `"-5"` | `-5` | `false` (`-5 > 0` is false) | redirect `/parent/children` |
| `"abc"` | `NaN` | `false` (`isSafeInteger(NaN)` is false) | redirect `/parent/children` |
| `"12.5"` | `12.5` | `false` (`isSafeInteger(12.5)` is false) | redirect `/parent/children` |
| `""` | `0` | `false` | redirect `/parent/children` |
| `"9999999999999999"` (exceeds `MAX_SAFE_INTEGER`) | `10000000000000000` (float-rounded) | `false` | redirect `/parent/children` |

This is the same fail-closed posture the service-layer
`requireLinkedChild` gate enforces for malformed / foreign / nonexistent
ids — the route shell never trusts an uncoerced param value, and a
malformed id redirects to the portal root rather than rendering an
error page (the constant-shape denial contract from plan §4.2).

The link-gate authorization (the parent IS the student's `parentId`)
is enforced by every backing GraphQL resolver — NEVER trusted to the
route shell. A probe against a foreign / unlinked id returns the
constant FORBIDDEN shape, rendered as `PermissionDeniedFallback` by
the client container.

## Security & tenancy audit (5.2.SEC)

**Guard composition verified — non-parent roles never reach portal views.**

- Both pages call `withPageAuth({ roles: [UserRole.Parent],
  redirectTo: "/parent/children" })` BEFORE any rendering logic. The
  guard's side-effects (anonymous → `/login?redirect=...`,
  role-mismatch → caller's role dashboard) fire before the page body
  runs. Admin / Teacher / Student callers are redirected to their own
  role dashboard and never reach the `ParentChildrenRootContainer` or
  `ParentChildDetailContainer` JSX.
- The `withPageAuth` guard is the ONLY authorization boundary at the
  route layer. Per `app/AGENTS.md` §"Page-level access control (auth ≠
  permission)", permission-gated pages must call
  `requirePermissionForPage` in `page.tsx` — but the portal routes do
  NOT use AppPermission-level gating (parent role membership IS the
  gate; the link-gate `requireLinkedChild` runs at the resolver layer
  on every backing query, enforcing INV-P1 "the student row IS the
  grant"). This is the established pattern for parent-scoped routes
  (precedent: `app/(dashboard)/parent/handshake/page.tsx`).

**No param value trusted without server-side coercion.**

- `[studentId]` path segment: coerced via `Number(rawId)`, validated
  via `Number.isSafeInteger && > 0`. Malformed values redirect to the
  portal root — the route shell NEVER forwards an uncoerced or
  invalid id to the client container. The client container receives
  only `studentId: number` (post-validation).
- `?student=` (root page): forwarded as `string | null`. This value
  is NOT trusted as an identity — it's URL state the client container
  uses to track the active selection. The actual identity check
  (parent owns this child) runs at the resolver layer.
- `?tab=` / `?session=` (detail page): forwarded as `string | null`.
  The client container validates the tab key (unknown values fall
  back to the default tab) and parses the session id (a non-numeric
  value is dropped). The server does NOT trust these as identity.

**Constant-shape denial posture preserved.** A probe against a
foreign / unlinked / nonexistent `studentId` (one that passes the
integer-coercion check but is not the parent's child) reaches the
client container, which calls the GraphQL resolvers — the resolvers
enforce `requireLinkedChild` and return the constant FORBIDDEN shape,
rendered as `PermissionDeniedFallback` by the container. The denial
bytes are identical across nonexistent / foreign / never-linked /
severed cases (D10 oracle posture, plan §4.2).
