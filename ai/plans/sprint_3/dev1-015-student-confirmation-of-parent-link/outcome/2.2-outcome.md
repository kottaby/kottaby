## 4. Cells added (names + justification)

### Cell A — `Tier 4 — governance PRE-TX ordering on the decision mutation: the governed actor's respond denies BEFORE any transactional work (repo spies: zero calls past the gate)` (S L2048)

- **Justification:** REQ-022 + plan.md L180/L198/L334 (D9a: `requireActor` is invoked BEFORE the
  tx opens) had no ordering proof — the existing governed cell pinned zero row WRITES only,
  which cannot distinguish "gate ran pre-tx" from "gate ran after harmless reads". The service
  ordering (service.ts L260 `requireActor(...)` → L262 `withTransaction`) is now pinned
  behaviorally: call-through spies over EVERY post-gate collaborator (`respondToPendingForStudent`,
  `findById` [the classifier oracle], `linkParentIfUnlinked`, `expireSiblingPendingsForStudent`,
  `findIncomingRowById`, `markExpiredIfPending`, `findLocalesByIds`, `emitForUser`) record ZERO
  invocations, while the gate's OWN fresh actor read (`UserRepository.findById`) records EXACTLY
  the two sanctioned reads in call order — proving identity re-derivation from `actorUserId`
  alone. Also pins: governed denial ≡ role-mismatch denial (byte fingerprint, no branch
  disclosure) and the actor-gate log shape (`{ code: "FORBIDDEN", entity: "users", locale }`,
  one per denial).
- **Mechanics:** `runInRollback` + `tx` passed as the service's `outerTx`; `expectRecheckDenial`
  (try/catch `expectRepoError` idiom — no `rejects.toThrow`); all spy assertions placed BEFORE
  `mockRestore()` (bun's `mockRestore` clears mock state — the file's documented convention);
  every spy restored in `finally`.

### Cell B — `Tier 1/3 — sequential double-respond idempotency (own-commit): the replay answers the constant ALREADY_RESOLVED conflict and the parent holds EXACTLY ONE notification total` (S L1079)

- **Justification:** REQ-013's idempotency half had only the concurrent (real-Postgres) pin and
  a repo-level denial-shape pin. The missing assertion — the COMMITTED sequential replay through
  the real service (in-tx emit → post-commit publish on decision #1; zero-row claim →
  classification → typed conflict on decision #2) — now pins: the replay emits NOTHING
  (parent inbox filtered by `relatedEntityId` stays at EXACTLY ONE row with the acceptance
  title/body in the parent's persisted locale), NO second publish (`publishCount` stays 1), the
  row keeps its single terminal state with the FIRST `respondedAt` byte-identically, the link
  write is untouched, and the student's inbox gains nothing. Also extends REQ-024 arm coverage:
  the already-resolved denial logs EXACTLY ONCE with
  `{ code: "PARENT_LINK_REQUEST_ALREADY_RESOLVED", entity: "parent_link_requests", entityId, locale }`.
- **Mechanics:** committed-fixture convention (dedicated `student-decide-twice` fixture in its
  own committing `db.transaction`, tracked in `trackedRequestIds`; FK-safe `afterAll` teardown +
  zero-residue probes already in the file) — the service owns the commit boundary on both
  decisions, so `runInRollback` cannot host this cell (mirrors the existing accept/reject
  own-commit cells). Denial asserted via `expectConflict` (try/catch); parent-inbox assertions
  use the file's delta/filter convention (cast-member inboxes accumulate across suites).
