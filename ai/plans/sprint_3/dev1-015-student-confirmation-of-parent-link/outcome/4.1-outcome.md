## 1. What was done

The drawer's row-anchor `href` was refactored from the hard-coded `"/notifications"` literal to a keyed route-resolution seam (minimal, switch-shaped; zero drawer re-architecture):

- **ONE shared route constant** `STUDENT_LINK_REQUESTS_ROUTE = "/student/link-requests"` exported from **one definition site**: `frontend/components/ui/useNotificationDrawerActions.ts:18`. Tasks 4.2 (dashboard card CTA) and 4.4 (nav entry pin) consume THIS export — three consumers, one constant, zero drift.
- **Keyed mapping** `NOTIFICATION_ROUTE_BY_ENTITY_TYPE: Readonly<Record<string, string | undefined>>` keyed by the **backend `NotificationType` enum member** (`NotificationType.ParentLinkRequest` — import from `@/backend/enum/notifications/notification-type.enum`; its VALUE `"parent_link_request"` is exactly what the persisted `related_entity_type` varchar carries per `PARENT_LINK_RELATED_ENTITY_TYPE` in `backend/services/parents/parent-link-request.helpers.ts:60` and the GraphQL `t.exposeString` passthrough). NO bare string literal in the mapping; `undefined` values model the runtime miss (the `PAYLOAD_TYPE_TO_CACHE_TYPE` precedent in `frontend/hooks/notifications/use-notification-realtime.helpers.ts`).
- **Pure resolver** `resolveNotificationRoute(relatedEntityType: string | null): string` — known entity type → its decision route; unknown/`null` → `"/notifications"` (module-private `NOTIFICATIONS_FEED_ROUTE`), i.e. the pre-4.1 behavior, unchanged and never throwing.
- **Consumer edit** in `frontend/components/ui/NotificationDrawerBody.tsx`: row `ListItemButton` `href="/notifications"` → `href={resolveNotificationRoute(item.relatedEntityType)}` (one line; navigation stays native via the real `next/link` anchor — no router call, no drawer contract change).
- `handleOpenNotification` itself is UNCHANGED (mark-read-when-unread + close); deep-linking rides the anchor href.

### Why the backend enum (not the codegen enum) keys the map

The wire `relatedEntityType` is a free String (raw varchar, snake_case value `"parent_link_request"`) while the codegen `NotificationType` enum carries PascalCase GraphQL wire names (`'ParentLinkRequest'`) and applies to the `type` field only. The backend enum's VALUE domain matches the persisted varchar exactly, and `@/backend/enum/*` imports are an established frontend pattern (`frontend/views/dashboard/home/RoleDashboardPage.tsx:2` imports backend `UserRole`). Test fixtures use BOTH: codegen member for `type`, backend member for `relatedEntityType`.
