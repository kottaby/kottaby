## 1. Findings (by severity)

### [LOW] frontend/components/ui/useNotificationDrawerActions.ts:31-33 — parent-recipient decision notifications deep-link to a route the parent's role cannot open (authorization intact; broken deep-link UX)

The delta's generic type→route map sends EVERY `relatedEntityType === "parent_link_request"` row to the student-only `STUDENT_LINK_REQUESTS_ROUTE` (`/student/link-requests`). But the respond/cancel decision notifications are emitted to the **PARENT** (`parent-link-request.service.ts:308-318` — `emitForUser({ userId: claim.parentId, …, relatedEntityType: PARENT_LINK_RELATED_ENTITY_TYPE })`), and the request-creation notifications to the STUDENT (wire cell `parent-link.wire.test.ts:1086-1093`). A parent tapping a decision notification in the drawer therefore navigates to `/student/link-requests`, whose page guard `withPageAuth({ roles: [UserRole.Student], redirectTo: … })` (0.2 §item 10) bounces them to `/dashboard` — the behavior 4.4 already observed and screenshotted (`browser-evidence/4.4-parent-redirect-to-parent-dashboard.png`).

- **Security impact: NONE.** The server-side guard redirects; the zero-argument `myIncomingParentLinkRequests` query derives identity from `ctx.user.id` and would deny a parent FORBIDDEN at the pre-resolver role scope (`parent-link.query.ts:89-94`) even if the redirect were bypassed. `relatedEntityId` is never interpolated into any URL (see check 5), so no IDOR channel exists.
- **Impact is UX/deep-link correctness** for the parent recipient (introduced by the delta: pre-delta every row went to `/notifications`). No test pins the parent-recipient deep-link path.
- **Suggested fix (deferred/forward — NOT fixed in 6.4):** make the seam recipient-aware (map the decision-event notification to the parent's surface, e.g. `/parent/handshake`, or key the map on `type`+recipient role), or split the notification type; add a drawer-test cell for a parent recipient. Non-blocking for Phase 7 — the student-facing deep-link (the delta's sanctioned target) is correct and authorization-safe for every role.

### [INFO] Pre-existing, OUTSIDE the delta (filtered per format, recorded for completeness) — no global GraphQL query-depth/complexity/alias limiter in the gateway

`backend/` grep finds only the per-object REQ-069 flatness posture (`backend/graphql/test/sdl-static-assertions.test.ts:50,416`) and error-redaction depth (`backend/lib/errors/…`); there is no gateway-wide depth/complexity rule. **Not delta-introduced:** the codegen differential is byte-identical with **zero new root fields** (`3.1-outcome.md:32`; re-verified `5.1-outcome.md:42`), the delta's objects are flat six-key rows, and both lists are zero-argument, service-capped (50, newest-first), so no batching/amplification surface was added. No action required in this ticket.
