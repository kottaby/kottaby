## 5. Test defects found & fixed (test-side only — ZERO production defects)

### 5.1 Symptom
First execution: 33 pass / 2 fail — BOTH locale-propagation tests failed with `Expected: <arabic message> Received: <english message>` (the `ar` request returned the `en` message).

### 5.2 Root cause (test defect — Apollo Client request deduplication)
The two tests issued their `en` and `ar` calls CONCURRENTLY via `Promise.all` with the IDENTICAL query document AND identical variables — only the per-request context headers differed. Apollo Client deduplicates identical in-flight operations by document+variables WITHOUT the context, so the `ar` call rode the in-flight `en` request and received its `en` response. Supporting evidence: the earlier sequential single-locale failure-cell test PASSED; the concurrent Tier-2 cells with differing variables PASSED; a raw-fetch control probe (§5.3) returned Arabic correctly; and a shared-client probe with the exact same headers returned Arabic when issued alone.

### 5.3 Fix + production exoneration
Both locale tests now issue their two calls SEQUENTIALLY (with a comment documenting the hazard). The server-side locale threading was PROVEN correct before touching the test: a throwaway diagnostic probe (raw `fetch` + the shared `testClient`, both with `Accept-Language: ar`) returned the Arabic `handshakeCodeInvalid` message over the live wire — `extractLocale` → `createGraphQLContext` → `ctx.locale` → service `getServerTranslations` chain is sound. **Production defect verdict: NONE.** (Probe deleted from the tree afterward; §6.3 records the diagnostic discipline.)

## 6. Deviations & operational findings

### 6.1 Documented deviations (with rationale)
1. **Locally `parse`d documents instead of shared `TypedDocumentNode`s** — the applicant-profile precedent: `@/backend/db` fixture imports flip bun's module conditions and crash `graphql-tag`'s UMD build; the shared handshake documents are Phase 4.1's deliverable (REQ-063), so this suite pins the wire shape with local, explicitly-typed documents until they exist (swap-in is a Phase-4 nicety, not a contract change — the selection sets are identical).
2. **Tier-4 spy section executes the built schema in-process** — cross-process spying on the live dev server is impossible without test-only server code (prohibited). The in-process tier exercises the SAME scope-auth plugin + resolvers the server serves; the wire tier separately proves the same denials end-to-end over real tokens (12-cell matrix + 3 substitution tests). Documented in the file header.
3. **Direct-DB fixture section inside a live-wire suite** — sanctioned by the applicant-profile precedent (fixtures, never assertions; all assertions go over the wire). Uses the entity-setup builders rather than raw inserts (stronger than the precedent).
4. **`beforeAll` at file scope + cast module variable** (not per-test `describe` blocks) — needed because the 12-cell matrix and all tiers share ONE fixture cast; mirrors the applicant-profile registration pattern lifted to a shared cast. QL/lint gates all green on the shape.

### 6.2 Operational (recurrence of the 3.1/3.2 hazard, now root-caused)
- **`killListenersOnPort` is a silent no-op in this sandbox:** `lsof -t -iTCP:3066 -sTCP:LISTEN` exits 1 with no output even while `ss -tlnp` shows the listener — so the runner's startup kill AND teardown kill both no-op, and every `run-server-tests.ts` run leaks its `next dev` + `next-server` pair (the wrapper SIGKILLs only its direct child). Observed concretely: the first suite run leaked the pair (next-server wedged at 91% CPU) and the second run died with `EADDRINUSE 0.0.0.0:3066` exactly as 3.2 predicted. **Binding for Phase 4 live-wire/browser tasks: check `ss -tlnp | rg 3066` + `ps aux | rg "next-server|next dev"` before AND after every server-touching run; `kill -9` BOTH pids (the `next dev` wrapper pid AND the `next-server` pid).**
- **Sandbox shell reaps background processes between invocations** — a server booted with `&`/`nohup`/`disown` is gone by the next tool invocation. Any manual warm-server workflow must boot → poll → run → kill inside ONE shell invocation. (The mandated runner is unaffected — it spawns and tears down within a single process.)
- The `--bail=1` default in `run-server-tests.ts` stops the suite at the first failure — use a direct `bun test` against a warm server (or read the wrapper's summary) to see ALL failures in one pass when debugging.
