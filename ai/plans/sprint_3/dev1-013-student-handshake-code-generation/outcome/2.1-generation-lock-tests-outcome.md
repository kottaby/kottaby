## 5. ❌ The production defect (HALT cause)

**Failing test:** `absorption lock: after a 23505 collision, the bounded retry's fresh-code insert on the SAME transaction must succeed with a valid-format code` (`handshake-code-generation-locks.test.ts:434-469`).

**Empirical chain (from the run log):**
1. Attempt 1: `StudentRepository.createForRegistration(registrant.id, "KSB-C0FFEE01", tx)` → rejected with `23505` / `students_handshake_code_unique` (asserted green at :446-448).
2. Attempt 2 (fresh code `KSB-A7ECD7A8`, same call shape the production retry loop uses — `registration.service.ts:367`): rejected with **`25P02` — "current transaction is aborted, commands ignored until end of transaction block"** (pg error object in log: `code: "25P02"`, `routine: "exec_parse_message"`). Assertion `expect(retryFailure).toBeUndefined()` at :464 fails.
3. Control (diagnostic test, same flow + explicit per-attempt savepoint bracket + `ROLLBACK TO SAVEPOINT`): attempt 2 SUCCEEDS with a valid-format code — isolating the missing-bracket root cause.

**Why this is a production defect, not a test defect:** the test models the production retry byte-faithfully — `createStudentWithHandshakeRetry` (`backend/services/auth/registration.service.ts:347-387`) catches a 23505 (:369-382) and re-inserts on the SAME `tx` with NO per-attempt savepoint. PostgreSQL aborts the transaction on the failed INSERT (verified: no implicit per-statement savepoint exists — same finding documented by DEV1-002's own harness note at `registration.service.test.ts:591-598`), so a real collision makes attempt 2 fail with 25P02; `isUniqueViolation` (:103-118) classifies 25P02 as NON-collision and rethrows (:370-374); `translateDbError` (:181-185, :181) passes it through untranslated → **the entire student registration fails with a raw `DrizzleQueryError`**. The retry never absorbs even one collision.

**Contracts falsified:** `docs/auth/user-registration.md` §2.2 ("retries **inside the same transaction**" on 23505), `specs.md` REQ-041 ("the existing retry loop can absorb collisions"), `plan.md` §4.3 row 1 ("bounded in-transaction retry (≤5) absorbs it") — i.e. the premise of design decision D1.

**Risk framing:** natural collisions are ~16⁻⁸ per registration pair (negligible operationally), but the spec-mandated verification FAILS, and tasks.md 2.1.TE is explicit: "if ANY lock fails against the existing implementation, STOP: record ❌ in `deferred-items.md` citing the defective DEV1-002/DEV1-001 surface and halt dependent tasks." Weakening the absorption lock to a bracketed flow-model to force green would mask the defect and defeat the D1 verification promise — not performed. The absorption lock is left in place, RED, as the permanent regression lock: it will go green with ZERO test changes once the DEV1-002 surface is fixed.

## 6. Decisions & interpretations (recorded for reviewers)

1. **Uniqueness "translated-message substring" (REQ-012):** asserted in two layers — (a) the pg cause-chain human-readable message + constraint name (`duplicate key value violates unique constraint` / `students_handshake_code_unique`) proves the CONSTRAINT fired (never a raw i18n key); (b) the collision-path race test drives the production translator itself (`translateDbError(loserError, <message>)` → asserts `ConflictError` / `extensions.code === "CONFLICT"` / message equality), satisfying "translated 23505 path" without calling the translation loader directly (AGENTS.md rule 19).
2. **NOT NULL via column omission:** the Drizzle insert type requires `handshakeCode` (itself part of the not-null contract), so the null-forcing insert is a raw parameterized `insert into students (id) values ($1)` — at SQL level an omitted NOT NULL column with no default IS a NULL insert; 23502 + "violates not-null constraint" + "handshake_code" asserted.
3. **Rollback purity modeled with the registration SHAPE, not the service:** forcing a service-internal child failure would require monkey-patching (forbidden by 2.1.SR); the test therefore replays the exact production shape — `UserRepository.create` + `StudentRepository.createForRegistration` inside ONE `tx.transaction` savepoint — and forces the child insert to fail on the occupied code (its natural DB-level failure mode).
4. **Format lock N=50 through the REAL service** (not `createForRegistration` backstop): `registerUser(input, locale, tx)` supports the documented `outerTx` test seam (savepoint per registration) — the strongest available verification of REQ-010.
5. **Race harness:** `Promise.allSettled` on two colliding inserts bracketed by ONE explicitly-named savepoint and rescued by `ROLLBACK TO SAVEPOINT` as the first command after settling — the exact pattern proven deterministic by DEV1-002's own duplicate-email race test (`registration.service.test.ts:586-618`), which also documents WHY (single session FIFO serialization; no implicit per-statement savepoints; drizzle sibling-savepoint name collisions under concurrency).
6. **Immutability-scan placement:** an fs-based static-assertion test has no DB dependency, but tasks.md 2.1 explicitly mandates it inside the sanctioned `backend/db/test/` logic tree — co-located with its sibling lock suite; it boots zero server code and touches no DB.
